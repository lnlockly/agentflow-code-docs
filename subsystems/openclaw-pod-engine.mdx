# OpenClaw Pod Engine (Phase 1)

## TL;DR
OpenClaw is a third hosted-device engine next to `goose` and the legacy `coder`
daemon. A device created with `template:'openclaw'` (gated by `FF_OPENCLAW`)
runs the `agentflow-openclaw` image: it boots OpenClaw's loopback Gateway, wires
the agent LLM to our flow router, and runs an in-pod bridge that speaks the
existing devices-ws task protocol — so a `dispatch_task` round-trips to OpenClaw
and streams the agent's reply back. Phase-1 proves boot + reachability; the full
`/live` wrapper + skills are later phases. Reversible: delete the device → gone.
Goose/coder defaults are untouched.

## Data flow
```
POST /me/hosted-devices { template:'openclaw' }   (FF_OPENCLAW=1 or → 403)
  → resolveDaemonImage('openclaw') → ghcr.io/lnlockly/agentflow-openclaw:latest
  → STS in af-tenant-<userId> vcluster, env: OPENCLAW_GATEWAY_TOKEN (per-pod),
    AGENTFLOW_FLOW_KEY (= device af_live key), AF_API_KEY/AF_DEVICE_ID/...

entrypoint.sh:
  reenroll()       → POST /me/hosted-devices/:id/reenroll {rotation_secret}
                     → fresh AF_ENROLLMENT_TOKEN, clear AF_DEVICE_TOKEN
                     (the one-time token is consumed on the first connect, so a
                      stateless pod must re-mint one on every boot)
  write-config.js  → renders ~/.openclaw/openclaw.json (gateway.mode:local,
                     bind:loopback, flowrouter provider, fail-closed)
  openclaw gateway --bind loopback --port 18789   (background)
  wait /healthz
  main.js (bridge):
    ── devices-ws ──▶  wss://agentflow.website/_agents/_devices/connect
       headers: x-api-key + x-device-id + x-enrollment-token (first) /
                x-device-secret (reconnect, from hello_ack, cached to disk)
    ── loopback   ──▶  ws://127.0.0.1:18789  (operator)

dispatch (live):   devices-ws task_dispatch{task} ──▶ gateway chat.send ──▶ flow LLM
                   task_complete{answer}           ◀── chat state:"final" event
dispatch (queued): cross-replica → device_tasks.status='queued' → bridge polls
                   GET /me/devices/:id/queued_tasks (10s) → same handleDispatch
```

## DB / Env / API
- **Tables:** `hosted_devices.template` (CHECK now includes `'openclaw'`).
- **Env (server):** `FF_OPENCLAW` (canary gate). **Env (pod):**
  `OPENCLAW_GATEWAY_TOKEN`, `AGENTFLOW_FLOW_KEY`, `OPENCLAW_CONFIG_PATH`,
  `OPENCLAW_STATE_DIR`, plus the standard `AF_API_KEY` / `AF_DEVICE_ID` /
  `AF_ENROLLMENT_TOKEN` / `AF_API_URL`.
- **Routes:** `POST /me/hosted-devices {template:'openclaw'}` (201, or 403
  `openclaw_canary_disabled`). Bridge connects `/_agents/_devices/connect`.
- **Model:** flow router at `<origin>/_agents/llm/v1`, alias `flow` (resolved by
  `pickFlowUpstream`). No hardcoded model id — the ref is `flowrouter/flow`.
- **Ports (pod):** 18789 (gateway WS + /healthz, loopback only), 8765 (bridge
  /api/health, the k8s readiness probe).

## Failure modes
| Symptom | Log signature for grep | Where to fix |
|---|---|---|
| Pod boots but gateway never answers | `FATAL: gateway exited during boot` | `openclaw-image/entrypoint.sh` |
| Gateway boots degraded (no model) | `AGENTFLOW_FLOW_KEY missing — refusing to boot` | `src/openclaw-shim/write-config.ts` |
| Create returns 403 | `openclaw_canary_disabled` | set `FF_OPENCLAW=1` on agentflow-agents |
| INSERT rejected on provision | `hosted_devices_template_check` | apply the 2026-05-31a migration |
| Dispatch never completes | `dispatch <id> failed: openclaw_chat_failed` | `src/openclaw-shim/bridge.ts:223` |
| Bridge can't reach loopback gateway | `gateway connect attempt N failed` | gateway not up / wrong token |
| Every chat 403s at the flow facade | `403 Your request was blocked` / `reason=auth` | WAF blocks `OpenAI/*` UA — `config.ts` sets `FLOW_USER_AGENT` header override |
| Connect rejected | `INVALID_REQUEST: invalid connect params` | `client.id`/`mode` must be `gateway-client`/`backend` |
| Dispatch stuck `queued`; bridge loops `devices-ws error: Unexpected server response: 401` then `reconnecting` | `devices-ws error:` + 401 | one-time enrollment token consumed on first connect → stateless pod re-presents it. `entrypoint.sh reenroll()` trades `AF_HOSTED_ROTATION_SECRET` for a fresh token on every boot |
| Cross-replica dispatch stays `queued`, never drains | `queued poll drained 0 task(s)` absent | bridge must poll `GET /me/devices/:id/queued_tasks` — `bridge.ts startQueuedPoll/drainQueuedTasks` |
| Agent answers a "browse" task from memory in ~1s; browser never navigates; `/live` screen blank | `Sandbox mode requires Docker, but the "docker" command was not found in PATH` (code=INVALID_CONFIG) | sandbox shells out to `docker` on every tool call; pod has no Docker → `config.ts` must render `agents.defaults.sandbox.mode: "off"` (#1070). Verify: agent `toolSummary.failures` must be `0` |
| `/live` screenshot poll errors while no page is open | `live screen: screenshot skipped (request rejected: ... browser request timed out)` | expected when the agent has no active browser page yet — only surfaces once a tool call actually opens chromium; not an error if sandbox is `off` and the agent browses |

## Security
- Gateway binds **loopback only**; 18789 never leaves the pod. The bridge uses
  OpenClaw's break-glass `gateway.controlUi.dangerouslyDisableDeviceAuth` + a
  per-pod shared token — safe ONLY because the WS is loopback inside an
  already tenant-isolated pod. Hardening follow-up: switch to the signed
  device-client (`packages/gateway-client`) so the flag is unnecessary.
- Flow key (`AGENTFLOW_FLOW_KEY`) is an env-ref in `openclaw.json` (never the
  literal on disk); a missing key fails the gateway closed.
- `agents.defaults.sandbox.mode: "off"` (#1070). OpenClaw's sandbox runtime
  shells out to `docker` for every isolated execution — including each agent
  tool call. The pod ships no Docker (it is itself the k8s tenant-isolation
  boundary), so any other mode fails the gateway closed (`INVALID_CONFIG`) the
  instant the agent uses a tool, and the agent silently falls back to answering
  from memory. `off` is correct here precisely because the pod boundary already
  provides the isolation a sandbox would.

## What Phase 1 ships vs. remains
Ships (verified live on ff-france 2026-05-31): image builds (1.85GB),
gateway boots + `/healthz` live, `agent model: flowrouter/flow` wired, engine
selection behind `FF_OPENCLAW`, and the **full `dispatch_task` round-trip** —
`POST /me/devices/:id/dispatch_task {task:"ответь PONG"}` → bridge → OpenClaw
agent → flow LLM → `device_tasks.status='done'` + `device_action_log`
`task_complete {"answer":"PONG"}`. Verified across all three cases: live
(same-replica push), re-enroll resilience (pod restart with a consumed token →
no 401-loop), and cross-replica queued (drained by the 10s poll, no restart).
Root causes resolved: (1) the flow WAF 403s the OpenAI-SDK `User-Agent` →
`config.ts` overrides it to `AgentFlow-OpenClaw/1.0`; (2) the one-time
enrollment token is consumed on the first devices-ws connect → `entrypoint.sh
reenroll()` re-mints one every boot; (3) cross-replica dispatches → `bridge.ts`
polls `queued_tasks`.
Remains: `/live` ApprovalBar + screen feed, OpenClaw skills library
(af-autopost/digest/...), channel onboarding, PVC-persisted `~/.openclaw` state,
the signed device-client.
