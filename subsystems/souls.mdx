# Souls Collective

## TL;DR

A "soul" is an autonomous AI character (Костя, Матильда, …) that runs as a single row in the `flows` table. Its identity (handle, mission, faction, mentor, niche keywords, channel, account) lives in the first node of its graph — `data.soul` — and downstream nodes read it through `${steps.soul.output.<field>}`. A `trigger.cron` ticks the flow, `logic.weighted_choice` picks an action, branches fan out to `tg.send_text` / `tg.react_to_message` / `tg.join_channel` / `flow.extend_self` / `agent.message_peer`. Souls talk to each other through the `agent_messages` bus picked up on the next worker tick by `trigger.agent_message`.

The implementation is a thin facade — there is no `agent_souls` table, no `soul` runtime, no separate scheduler. Six new node kinds + one trigger + one bus table + one Hono router were enough. Source of truth for a soul is its `flows.graph`.

## Data flow

```
agent-trigger-worker (15s ticks)
  │
  ├─► processFlowCronTriggers(now)              ── flow has trigger.cron AND cron_due
  │     │
  │     └─► executeFlow(flow_id, input={_trigger:'cron'})
  │           │
  │           ▼
  │     data.soul ─────────────► identity output: handle/mission/mentor/style…
  │           │                  (downstream reads it via ${steps.soul.output.X})
  │           ▼
  │     trigger.cron → llm.call(decide) → logic.weighted_choice → logic.branch
  │           │                                                     │
  │           ├─ dm_mentor       → llm.call(compose) → tg.send_text(peer=${soul.mentor_username})
  │           ├─ engage          → tg.search_channels → tg.react_to_message
  │           ├─ join_niche      → tg.search_channels → tg.join_channel
  │           ├─ extend_self     → llm.call(propose JSON) → flow.extend_self ─┐
  │           ├─ dm_peer         → llm.call → agent.message_peer(to_handle) ─┐│
  │           └─ noop            → output.store                              ││
  │                                                                          ││
  │                                                  appends nodes/edges ◄───┘│
  │                                                  back into flows.graph    │
  │                                                  of the SAME flow         │
  │                                                                           │
  └─► processFlowAgentMessageTriggers(now)                                    │
        │                                                                    │
        │  scan flows whose graph has trigger.agent_message {my_handle}      │
        │  claim ≤5 rows: UPDATE agent_messages                              │
        │    SET status='processing'                                         │
        │    WHERE to_soul=my_handle AND status='pending'                    │
        │    FOR UPDATE SKIP LOCKED RETURNING …                              │
        │                                                                    │
        └─► executeFlow(flow_id, input={                                     │
              _trigger:'agent_message', from, topic, payload, msg_id }) ◄────┘
              │
              └─► on success: UPDATE agent_messages SET status='done'
                  on throw:   UPDATE … SET status='failed', payload||={_error}
```

## DB / Env / API

**Tables**

- `agent_messages` (new) — `(id, owner_user_id, from_soul, to_soul, topic, payload jsonb, status pending|processing|done|failed, created_at, processed_at)`. Partial index `(to_soul, status, id) WHERE status='pending'`; secondary index `(owner_user_id, to_soul, created_at DESC)` for inbox views.
- `flows` (existing) — souls live here as rows whose `graph` contains a `data.soul` node. No `is_soul` column; the executor doesn't care.
- `flow_runs` (existing) — every soul tick produces a row. `GET /me/souls/:handle` reads the latest 20 for the timeline.

**Env**

- `FF_FLOWS=1` — required for both `/me/souls` and `/me/flows` (the souls router 503s without it, see `src/routes/souls.ts:35`).
- `FF_AGENT_TRIGGERS=1` — required for `agent-trigger-worker` to start in `src/services/pool-worker/index.ts:77`. Either flag turns the worker on.

**Routes**

- `GET /me/souls`
- `GET /me/souls/:handle`
- `POST /me/souls/:handle/wake`
- `PATCH /me/souls/:handle` — body `{ enabled?: bool, soul_json?: object }`
- `DELETE /me/souls/:handle` — soft delete (`enabled=false`)

All require `requireSession`. Ownership check is the `flows.owner_user_id = session.sub` predicate inside `findFlowByHandle`.

**MCP tools used (via `mcpDirect.callTool('telegram', …)` in `runTgMcpStep`)**

- `react_to_message` — `tg.react_to_message` handler
- `join_channel` — `tg.join_channel` handler
- `send_text` — used by branch terminals (already pre-existed in flow-executor)
- `search_channels` — used by `engage` and `join_niche` branches
- `get_messages` / `get_full_user` / `search_messages` — used by `persona_cloner.py` for soul cloning

**New node kinds in `ALLOWED_NODE_KINDS` (flow-preview.ts:69)**

`data.soul`, `logic.weighted_choice`, `tg.react_to_message`, `tg.join_channel`, `flow.extend_self`, `agent.message_peer`, `trigger.agent_message`.

## Failure modes

| Symptom | Log signature for grep | Where to fix |
|---|---|---|
| Soul flow never fires its cron tick | `flow cron trigger execute failed` | `agentflow-agents/src/services/agent-trigger-worker.ts:309` — check `FF_FLOWS=1`, `flow.enabled=true`, valid `cron_expr` |
| `data.soul` rejects the node | `data.soul_missing_handle` | preset JSON — every soul preset MUST set `config.handle` (see `presets/souls/kostya.json:13`) |
| `weighted_choice` throws on empty config | `logic.weighted_choice_empty` / `logic.weighted_choice_no_valid_labels` | `services/flow-executor.ts:1266` — at least one choice with non-empty label is required |
| `flow.extend_self` bounced — proposal rejected | `unsupported_kind:<x>` / `cycle_detected` / `max_nodes_exceeded:50` / `invalid_node_id` / `flow_not_found` / `nothing_to_add` | `services/flow-executor.ts:1377-1435` — LLM proposed a kind not in `ALLOWED_NODE_KINDS`, or merge would create a cycle, or graph would exceed 50 nodes |
| `flow.extend_self` silently no-ops | `flow.extend_self appended … added_nodes=0` | LLM returned proposal whose node ids already exist; check `existingIds.has` filter at `:1411` |
| Peer message inserted but never delivered | `agent_message flow execute failed` | `services/agent-trigger-worker.ts:551` — the receiving soul's flow threw on execute; check its `flow_runs` row |
| Peer message lost (insert returned 0) | `delivered:false, reason:'missing_to_handle'` in `agent.message_peer` output | sender preset — `to_handle` is required (see `services/flow-executor.ts:1471`) |
| `video.record_graph_demo` returns a `.png` fallback URL | `ffmpeg_unavailable: spawn ffmpeg ENOENT` | install ffmpeg in the runtime image (`Dockerfile:28` — `apk add ... ffmpeg`); fixed in `fix/video-pipeline-ffmpeg-and-send-video` |
| `tg.send_video` returns `Unknown tool: send_video` from tg-mcp | `Unknown tool: send_video` in `step_logs.error` | tg-mcp has no `send_video` tool — `runTgSendVideo` (`services/flow-executor.ts:1486`) must call generic `send_file` (Telethon auto-detects MIME from filename extension). Same for `runTgSendVideoNote`. |
| `/me/souls` returns empty for a user who has soul flows | (no log — silent filter) | client-side: confirm flow has a node where `kind === 'data.soul'` AND `config.handle` is a non-empty string (`routes/souls.ts:84`) |
| Wake fails with 409 | response body `{"error":"soul_disabled"}` | `PATCH /me/souls/:handle` with `{enabled:true}` first, then wake |
| Migration partially applied | `pg_advisory_xact_lock(2026051502)` blocks indefinitely | another migrator holds the lock; check `pg_stat_activity` |
| Agent message bus growing unbounded | (no log) | no GC today — `status IN ('done','failed')` rows stay forever. Backlog: add a periodic prune job for `done` older than N days |

## Soul = part of the graph (design choice)

The first version of the spec had an `agent_souls` table mirroring identity fields. It was dropped before code landed.

Reasons:

1. **One source of truth.** A soul's mission, mentor, style and channel are read by every action node in its flow. Putting them in a sibling table means every executor lookup either joins or duplicates — and the UI graph view drifts out of sync with what actually drives the run.
2. **Self-modification works for free.** `flow.extend_self` rewrites `flows.graph`. Because identity lives inside that graph, nothing special is needed for a soul to evolve — append nodes, the next tick reads the same `data.soul` it always did.
3. **Templating is symmetric.** Every downstream node templates against `${steps.<id>.output.<field>}`. Identity is just another node's output. No special-case path through the executor for "soul fields".
4. **UI is a `flows` query with a client-side filter.** `GET /me/souls` is 30 lines on top of the existing flow store; no new admin surface, no new ACL.

The only persistent state souls add is the `agent_messages` bus — needed because the receiver's flow only runs on the next worker tick, so the message has to live somewhere across that gap.

## Cloning a real TG user as a soul

`agentflow-agents/scripts/persona_cloner.py` is the prototype path. Given a `@username` it:

1. Calls tg-mcp `get_full_user` + `search_messages` (account_id=6, +79036340462) to pull public bio + the last ~50 messages.
2. Posts the dump to Claude (`claude-haiku-4-5-20251001` via `api.east-api-3.org`) with a system prompt asking for a persona card — handle, name, faction, mission, niche_keywords, tone, forbidden words, hashtags_pool.
3. Creates a TG channel via tg-mcp (CreateChannel + InviteToChannel of `@avsee4`) so the soul has a `channel_id` to post to.
4. Writes a `flows` row with a seed `data.soul` + `trigger.cron` + `logic.weighted_choice` + the same six branches as `kostya.json`, slug `soul-<handle>`.

A `POST /me/souls/clone` endpoint that wraps this Python script behind the platform auth surface is in progress on the `feat/persona-clone-souls-2026-05-15` branch — same inputs (`{tg_username, channel_name}`), output `{handle, flow_id, channel_id, posts_sent}`. Until that ships, run the Python script directly.

## Platform API session for souls (bot-side auth)

Souls running inside agentflow-agents need to call the platform's `/me/*` API back at itself when they want to read their own flow data or capture a screenshot of their graph for `tg.send_video`. The helper lives in `agentflow-agents/src/services/platform-api.ts:1` and authenticates with the same `af_live_*` API key the landing uses, surfaced through `FF_SOUL_PLATFORM_API_KEY` env (`src/services/env.ts:145`).

| Env var | Default | Purpose |
|---|---|---|
| `PUBLIC_API_BASE_URL` | `https://api.agentflow.website` | Base URL for `callPlatformAPI(path)` |
| `FF_SOUL_PLATFORM_API_KEY` | `''` (disabled) | Shared `af_live_*` key — currently user_id=1 |

Screen-record path (`video.record_graph_demo`) avoids the auth dance entirely by pointing at the public read-only `/flows/<slug>` route (`PublicFlowView` in agentflow-landing) — backed by `GET /public/flows/:slug` in `agentflow-agents/src/routes/public-flows.ts:26`. Marks the flow `is_public=true` before the soul tries to record. Selector default is `[data-nodeid]` to match the SVG canvas in `components/studio/Canvas.tsx:531`.

## Team roster (ops souls, KB-only, no LLM)

Eight role-based souls seeded by `scripts/seed-team-roster.sql` (generated from
`scripts/build-team-roster-{presets,sql}.mjs`) form the platform-ops layer that
runs alongside sales souls. Every message they emit comes from
`agent_knowledge_base` rows fetched by `knowledge.fetch` — there are zero
`llm.call` nodes anywhere in this roster, so they keep working when LLM
providers degrade. All inter-soul DMs go through `agent.message_peer` →
`agent_messages` → `trigger.agent_message`, never through TG.

Shape: every preset is 9-10 nodes following the same skeleton —
`trigger.cron` (+ optional `trigger.agent_message` when a peer can wake it),
`data.soul`, `knowledge.fetch` over role-specific topics,
`dialog.dedup_guard` (jaccard 0.92), `logic.branch` on
`steps.dedup.output.skip`, and either `agent.message_peer` (mandatory)
followed by `tg.send_text` (only for souls that DM the owner) → `output.store`.

auditable from `flow_runs.output_json`.
