# kwork-connector

## TL;DR

The Kwork connector is a thin adapter over the `kwork-inbox` MCP server. Every
read tool (`list_dialogs`, `list_wants`, `list_my_kworks`, `get_dialog`) returns
typed errors as data — including auth/cookie failures. Without classification an
expired session collapses into `[]` and looks identical to a genuinely empty
inbox: the Пульт shows «пока пусто» when the real reason is «Kwork cookies
истекли». The connector detects auth errors via `kworkReauthError`, throws
`ConnectorError('reauth_required', 'kwork')`, and the browse route surfaces a
typed `needsReauth:true, reason:'reauth_required'` empty state.

## MCP envelope unwrap (the always-empty bug)

`mcpDirect.callTool('kwork-inbox', …)` does NOT return the bare tool envelope
(`{ok, wants}`). The JSON-RPC MCP server wraps every result as a `CallToolResult`
— `{ content: [{ type:'text', text: JSON.stringify(out) }], isError }`
(`src/mcp-servers/jsonrpc.ts:228`). The connector MUST unwrap that with
`unwrapMcpResult` (`src/services/graph-executor/mcp-unwrap.ts`) before parsing.
Without the unwrap, `kworkReauthError(raw)` and the parsers read fields off the
`{content:[…]}` wrapper, find nothing, and return `[]` for EVERY kind
(`exchange`, `dialogs`, `my_gigs`) regardless of auth state — and an auth failure
never surfaces as reauth. This was the live "Биржа / Диалоги / Мои кворки all
empty even when active" bug; fixed by unwrapping at each `callTool` site.

## Current server-rendered inbox parsing (2026-06)

Kwork's `/inbox` is now a server-rendered Vue shell - there is **no
`__INITIAL_STATE__` blob and no clean JSON dialogs endpoint**. The dialog list
is inlined into the page as `window.chatList=[...]`, and the authenticated owner
id sits in `window.USER_ID="<n>"`. The `kwork-inbox` MCP parses this directly:

- `list_dialogs` -> `parseChatListFromInboxHtml(html)` walks `window.chatList`.
  Each row maps: `user_id` -> `dialog_id` (the PEER id - **not** `member_id`,
  which is the owner's own id), `username` -> peer login, `message` /
  `lastMessage.message` -> preview, `time` (unix sec) -> ISO, `unread_count`,
  `pic` -> absolute members-CDN avatar URL. The legacy
  `__INITIAL_STATE__`/`stateInbox` heuristic (`normaliseDialogs`) stays wired
  as a fallback for older layouts.
- `get_dialog` -> the `/inbox/<id>` page carries no message blob; messages come
  from `POST /inbox_more_messages {userId,allUnread,csrftoken}` ->
  `{success:true,data:{messages:[...]}}`. `parseMoreMessagesEnvelope(payload,
  ownerId)` flips rows where `MSGFROM === window.USER_ID` to `role:'me'` and
  lifts `files.*.url` into attachments. The page-state-marker scrape +
  rendered-DOM scrape stay as fallbacks. **csrftoken is required** on this POST
  (the `csrf_user_token` cookie === the page `window.csrftoken`).
- `send_message` -> `POST /sendmessage` with `message_body`, `submg=1`,
  `msgto=<dialog_id>`, `csrftoken=<cookie>`. The form `action` and hidden
  `csrftoken`/`submg`/`msgto` fields are confirmed in the live inbox HTML.
- `executeAction('send', {entityId:<dialog_id>, payload:{text}})` on the
  connector routes a dialog reply through `send_message`; `executeAction
  ('respond', ...)` still routes a public-want offer through `respond_to_want`.

Parsers are pure + exported for unit coverage in
`tests/mcp-servers/kwork-parse-current-inbox.test.ts` (synthetic fixture - no
real cookies / private message content committed).

## Cookie-refresh requirement

Kwork sessions are stored as cookies (raw header or Playwright `storage_state`
JSON) under `KWORK_SESSION_JSON`, resolved by `resolveSessionCookies`. Kwork
cookies expire — when they do, the MCP gets a `/login` redirect or the «Вход на
сайт» HTML on an authenticated path, which `kworkRequest` maps to the
`auth_expired` signal. There is no silent refresh: the owner re-pastes a fresh
session via **`POST /me/integrations/kwork/connect`** (the in-Пульт reconnect
flow). Until they do, every kwork read returns `needsReauth` and no live data —
by design, so the UI never renders stale or fake dialogs.

## Credential resolution — vault-first, with connect mirror (#1110)

The read path resolves cookies through `resolveSessionCookies` →
`resolveCredential(ownerUserId,'kwork')`, which treats the **`user_credentials`
vault as the PRIMARY source** and only falls back to `project_secrets` when the
vault has no active row (`credential-resolver.ts:4`). Before #1110,
`POST /me/integrations/kwork/connect` wrote the freshly-pasted cookies **only**
to `project_secrets.KWORK_SESSION_JSON`. If the owner had an older active vault
row (e.g. user 1's 2026-05-27 row) it **shadowed** the fresh project_secrets
write: the resolver kept returning the stale 7-day-old cookies, kwork served a
logged-out `/inbox`, `window.chatList` was absent, and `list_dialogs` returned
`[]` — even though `parseChatListFromInboxHtml` worked on the live HTML in
isolation. #1110 makes connect **mirror** the same payload into the vault via
`saveUserCredential(sub,'kwork',…)` (`me-integrations-kwork.ts:330`), which
revokes the stale active row and makes the freshly-connected session the one the
resolver returns. The vault write is best-effort — a failure logs
`[kwork/connect] vault mirror failed` but does not 500 (the project_secrets
write already recorded the connect).

## Datacenter-IP CAPTCHA (prod-empty, residential-works)

In production the kwork pod can return entities `[]` even with fresh, valid
cookies because **kwork serves an interstitial CAPTCHA to the datacenter IP**
the cluster egresses from. `kworkRequest` flags a 403 with a
`captcha|recaptcha|hcaptcha` body as `signal:'captcha'`
(`kwork-inbox.ts:292`); on the CAPTCHA-HTML 200 path `window.chatList` is
absent, so `parseChatListFromInboxHtml` returns `[]`. The same cookies on a
residential IP succeed. **Fix = route kwork egress through a residential proxy**
(see [proxy-pool](/subsystems/proxy-pool)); this is an IP-reputation problem,
not a session, parser, or fetch-header bug.

## Data flow

```
Web ─GET /me/accounts/kwork:<id>/connector/entities?kind=dialogs─▶ me-accounts.ts
  browseEntities() → getConnector('kwork').listEntities('dialogs')
    mcpDirect.callTool('kwork-inbox','list_dialogs', {KWORK_SESSION_JSON})
      ├─ valid cookies   → {ok,dialogs:[…]} → parseDialogs → Entity[]
      ├─ expired cookies → {error:'auth_expired'} → assertAuthed
      │     → throw ConnectorReauthError('kwork','reauth_required')
      │     → browseEntities catches → {ok:true, entities:[], needsReauth:true,
      │        reason:'reauth_required'}   ← UI shows «Переподключите Kwork»
      │        → owner POST /me/integrations/kwork/connect re-pastes cookies
      └─ transient err   → {error:'rate_limited'|'http_error'|…} → []  (degraded:true)
```

`auth_expired`, `session_secret_not_found`, `session_secret_unseal_failed`, and
the other secret-resolution errors classify as reauth. `rate_limited`, `banned`,
`captcha`, `http_error`, `network_error` stay on the degrade-to-empty path
(transient / platform-side, not a session problem).

## DB / Env / API

- Tables: `user_credentials` (PRIMARY vault, one row per `owner+kind='kwork'`,
  sealed cookies); `project_secrets.KWORK_SESSION_JSON` (legacy read-fallback).
  Resolver = `credential-resolver.ts` (vault-first).
- Secrets: `KWORK_SESSION_JSON` — the session cookies (raw header or Playwright
  `storage_state`). Refreshed by the owner, never auto-rotated.
- Routes:
  - `GET /me/accounts/:id/connector/entities?kind=` → `{ ok, entities, degraded?, needsReauth?, reason? }`
  - `GET /me/accounts/:id/connector/entities/:eid/thread?kind=` → `{ ok, thread, degraded?, needsReauth?, reason? }`
  - `POST /me/integrations/kwork/connect` — re-paste session after «Kwork cookies истекли»; writes `project_secrets` AND mirrors into the `user_credentials` vault (#1110)
- MCP tools wrapped: `list_dialogs`, `list_wants`, `list_my_kworks`,
  `get_dialog`, `respond_to_want` (kwork-inbox server).
