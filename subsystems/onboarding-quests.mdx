# Onboarding Quests

## TL;DR

`/start` (frontend page `OnboardingPage.tsx`) walks a new user through real
first actions and credits a small USDF reward for each. Quests are listed
from `GET /me/quests`; rewards land as `referral_earnings` rows
(type='quest') that the user sweeps with `POST /me/earnings/claim`. New
quests (2026-05-24) are completed server-side from the action sites — the
frontend cannot self-claim them by calling `/complete`.

## Data flow

```
                            user action
                                │
                                ▼
  POST /me/projects                              ──┐
  POST /me/projects/:id/approve                  ──┤
  POST /me/hosted-devices  (201)                 ──┤
  WS  /_devices/connect    (hello_ack)           ──┼─► maybeCompleteQuest(userId, '<id>')
  POST /me/matrix/send     (200)                 ──┤        │
  POST /me/tg-accounts/confirm-code (active)     ──┤        │
  POST /me/marketplace/:slug/hire                ──┤        ▼
  POST /me/quests/preview-opened/:projectId      ──┘   ┌────────────┐
                                                       │ user_quests│ (idempotent insert)
                                                       └─────┬──────┘
                                                             │ first time
                                                             ▼
                                                  ┌──────────────────┐
                                                  │ referral_earnings│  type='quest', claimed=false
                                                  └─────────┬────────┘
                                                            │
                                            user sweeps via POST /me/earnings/claim
                                                            │
                                                            ▼
                                                     creditUser(USDF)
```

## Failure modes

| Symptom | Log signature for grep | Where to fix |
|---|---|---|
| Quest hook silently no-ops | `[quest-events] maybeCompleteQuest failed:` | `src/services/quest-events.ts:95` |
| `connect_device` not granted on hosted-device create | `[hosted-devices] apply failed` | `src/routes/me-hosted-devices.ts:300` |
| `open_preview` rejected with `preview_not_ready` | check `projects.preview_url` is non-empty | `src/routes/gamification.ts:222` |
| Reward credited twice | should be impossible — `user_quests (user_id, quest_id)` is unique | `src/db/schema.ts` userQuests definition |
| Quest visible in UI but never grantable | quest id present in `seed-quests.ts` but no hook call site | grep `maybeCompleteQuest(.*'<id>')` |

## Adding a new quest (3-step checklist)

1. Add a row to `QUESTS` in `agentflow-agents/src/db/seed-quests.ts`
   (id, title, titleRu, reward, sortOrder).
2. Run the seeder against the prod DB:
   `kubectl -n franchise-factory exec deploy/agentflow-agents -- npx tsx src/db/seed-quests.ts`.
3. Call `maybeCompleteQuest(userId, '<id>')` from the route handler that
   represents the real action. Use `void` so the primary response is not
   blocked. Add an icon + i18n entry + route in
   `agentflow-landing/src/pages/OnboardingPage.tsx`.

## Anti-spoof rules

- `connect_device` requires a valid WS handshake (auth check happens in
  `devices-ws.ts` before `bindConnection`) or a real `hosted_devices` row
  pinned to the user's vcluster.
- `create_first_project` only fires after the row is in `projects` —
  paywall + idempotency happen first.
- `open_preview` requires ownership/collaborator membership AND
  `preview_url` non-empty in the DB.
- `send_chat_message` only fires on bridge 200 — bridge errors do not credit.
- All grants are idempotent through the `user_quests` unique key.
