# Agents — provision + taxonomy

## TL;DR

An agent is one row in the `agents` table. Most agents are spawned through `provisionAgent` (`src/services/agent-provision.ts:63`) which takes a `CharacterInput`, normalises plugins/system/secrets via `buildCharacter`, inserts the row, then creates + starts the agent in the remote Eliza runtime. Frontend gates key off the top-level columns (`category`, `keywords`, …) — not off the JSONB `character` blob — so those columns **must** mirror the corresponding fields from the preset / input character at insert time.

## The invariant

> **`agents.category` (column) === `character.category` (JSONB field)** for every fresh insert.

The same rule applies to `agents.keywords`. If the input has no `category`, the column is explicitly `NULL` (not `undefined`, which drizzle would drop). If the input carries garbage (non-string, non-array), the row falls back to `NULL` / `[]` — defence-in-depth so a bogus preset cannot corrupt the column.

`CharacterInput` (`src/services/character.ts:35`) does **not** list `category` or `keywords` as known fields — those are preset-level taxonomy, mirrored onto the DB row by the insert path. `buildCharacter` does not propagate them into its return value either; only `provisionAgent` and the per-insert path in `routes/agents.ts:1657` (hire-from-preset) handle the mirror.

## Data flow — preset hire

```
me-presets POST /me/from-preset/:slug
       │
       ▼
load preset JSON (presets/<slug>.json)
       │  preset.category === 'researcher'
       ▼
provisionAgent({ character: preset as never, … })
       │
       ▼ src/services/agent-provision.ts:63
buildCharacter(input, secrets, …)
       │   ⮕ drops category / keywords from JSON payload
       │   ⮕ returns { name, bio, system, settings, plugins, … }
       ▼
db.insert(agents).values({
  …,
  character,                       // JSONB — has system, plugins, settings
  category: presetCategory,        // ← mirror from input.character.category
  keywords: presetKeywords,        // ← mirror from input.character.keywords
})
       │
       ▼
GET /me/agents/:slug → row.category === 'researcher'
       │
       ▼
AgentWorkspace.tsx:151 → KnowledgeSidebar renders
```

## DB / Env / API
- Tables: `agents` (columns of interest: `category text`, `keywords text[]`)
- Indices: `agents_category_idx`, `agents_owner_category_rating_idx`
- Env: none (taxonomy is JSON-driven)
- Routes touching the mirror: `POST /me/from-preset/:slug`, `POST /me/marketplace/:slug/hire`, `POST /me/marketplace/:slug/fork`, `POST /agents` (architect MCP)
- MCP tools: `architect.create_agent` (via `mcp-servers/architect.ts`)

## Failure modes

| Symptom | Log signature for grep | Where to fix |
|---|---|---|
| Researcher agent has no knowledge sidebar | (frontend) `agent.category === 'researcher'` returns `false` for a row where `character.category === 'researcher'` | Check the insert path that created it — mirror missing. |
| New row lands with `category=NULL` despite preset taxonomy | `psql -c "SELECT id, slug, category, character->>'category' FROM agents WHERE category IS NULL AND character ? 'category'"` returns rows | `services/agent-provision.ts:81` — verify the typeof guard and the values({…}) call still pass `category:`. |
| TS error after touching `provisionAgent` insert payload | `tsc` complains about `presetCategory: string \| null` | The type pin in the helper variable is intentional — keep it. |

## Backfill

When the mirror was first added, existing rows in prod needed a one-off backfill:

```sql
UPDATE agents
SET category = character->>'category'
WHERE (character ? 'category') AND (category IS NULL OR category = '');
```

Run **after** the code fix is deployed (otherwise the next preset hire re-introduces a `NULL` for any row created in the gap).
