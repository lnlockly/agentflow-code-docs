# Agents — provision + taxonomy

## TL;DR

An agent is one row in the `agents` table. Most agents are spawned through `provisionAgent` (`src/services/agent-provision.ts:63`) which takes a `CharacterInput`, normalises plugins/system/secrets via `buildCharacter`, inserts the row, then creates + starts the agent in the remote Eliza runtime. Frontend gates key off the top-level columns (`category`, `keywords`, …) — not off the JSONB `character` blob — so those columns **must** mirror the corresponding fields from the preset / input character at insert time.

## The invariant

> **`agents.category` (column) === `character.category` (JSONB field)** for every fresh insert.

The same rule applies to `agents.keywords`. If the input has no `category`, the column is explicitly `NULL` (not `undefined`, which drizzle would drop). If the input carries garbage (non-string, non-array), the row falls back to `NULL` / `[]` — defence-in-depth so a bogus preset cannot corrupt the column.

`CharacterInput` (`src/services/character.ts:35`) does **not** list `category` or `keywords` as known fields — those are preset-level taxonomy, mirrored onto the DB row by the insert path. `buildCharacter` does not propagate them into its return value either; only `provisionAgent` and the per-insert path in `routes/agents.ts:1657` (hire-from-preset) handle the mirror.

## Data flow — preset hire

```
me-presets POST /me/from-preset/:slug
       │
       ▼
load preset JSON (presets/<slug>.json)
       │  preset.category === 'researcher'
       ▼
provisionAgent({ character: preset as never, … })
       │
       ▼ src/services/agent-provision.ts:63
buildCharacter(input, secrets, …)
       │   ⮕ drops category / keywords from JSON payload
       │   ⮕ returns { name, bio, system, settings, plugins, … }
       ▼
db.insert(agents).values({
  …,
  character,                       // JSONB — has system, plugins, settings
  category: presetCategory,        // ← mirror from input.character.category
  keywords: presetKeywords,        // ← mirror from input.character.keywords
})
       │
       ▼
GET /me/agents/:slug → row.category === 'researcher'
       │
       ▼
AgentWorkspace.tsx:151 → KnowledgeSidebar renders
```

## Backfill

When the mirror was first added, existing rows in prod needed a one-off backfill:

```sql
UPDATE agents
SET category = character->>'category'
WHERE (character ? 'category') AND (category IS NULL OR category = '');
```

Run **after** the code fix is deployed (otherwise the next preset hire re-introduces a `NULL` for any row created in the gap).

## Listing endpoints — `/agents` vs `/me/agents`

Two routes return the caller's owned agents:

| Route | Envelope | Row shape | Use case |
|---|---|---|---|
| `GET /agents` | `{ ok, items: [...] }` | `publicAgent` — slim: id/slug/name/state/engine/secret_keys | Legacy sidebar, MyAgentsV2 page |
| `GET /me/agents` | `{ ok, agents: [...], count }` | `summaryAgent` — rich: bio/topics/emoji/category/keywords/owner_id/published/hire_count/rating | Cabinet tile, profile listing, picker dropdowns |

Both filter `state != 'tombstoned'` and `owner_user_id = session.sub`. The hire endpoint (`POST /me/agents/hire`) stamps `ownerUserId = sub` on the new row, so "owned" and "hired" collapse into the same WHERE predicate — no JOIN against a separate namespace table.

## Secrets — provision + upsert

Per-agent secrets live in `agent_secrets` (PK = `agent_id`, one row per agent, all keys sealed together as a single AES-256-GCM payload — see `services/seal.ts::sealSecrets`). Plaintext never touches disk; the master key is env `AGENTS_MASTER_KEY` (base64, 32 bytes).

Two write paths:

| Path | When | File |
|---|---|---|
| Bulk seal on agent create | First insert via `provisionAgent` | `agentflow-agents/src/services/agent-provision.ts:233` |
| Incremental upsert (one or more keys) | Owner-facing edits from the workspace Settings panel | `agentflow-agents/src/routes/me-agents-secrets.ts` |

`PATCH /me/agents/:slug/secrets` reads the existing sealed row, unseals into `Record<string, string>`, layers the new keys on top, re-seals, and `onConflictDoUpdate(agentSecrets.agentId)`. Required because the PK is `agent_id` (single row) — naive insert hits unique-violation on every retry. Returns `{ ok, set, failed, secret_keys }`. Validation: ASCII key regex (`/^[A-Za-z_][A-Za-z0-9_]{0,119}$/`), value ≤16 KiB. 404 on slug not owned, 410 on tombstoned, 500 if existing payload unsealable (key rotated — refuses to overwrite).

Both `publicAgent` (returned by `GET /agents`, `GET /agents/:slug`) and the `/agents/:slug/settings` payload include `required_secrets` (mirrors `agents.requiredSecrets` jsonb column from the hire-from-preset contract) and — on the settings endpoint — `secret_keys` (the `keyIds` array from `agent_secrets`, so the workspace panel renders ✓ Set badges without an extra round-trip).

- `agentflow-agents/src/routes/agents.ts:107` — `publicAgent` carries `required_secrets`.

## Chat attachments — owner directive 2026-05-17

`POST /agents/:slug/chat` accepts an optional `attachments[]` array alongside `text`. Each entry is `{ filename, mime, data_base64 }`. Images render as Anthropic vision content blocks on the first user message of the turn; text files are inlined inside `<attachment filename="…">` envelopes. Vision needs the big model — turns route through `useModel(ModelType.TEXT_LARGE)` which is already vision-capable (no hardcoded model).

### Policy

| Class | MIME allow-list | Per-file cap |
|---|---|---|
| Image | `image/png`, `image/jpeg`, `image/webp` | 5 MB decoded |
| Text | `text/plain`, `text/markdown`, `application/json` | 200 KB decoded |

Per-turn cap: 6 attachments. Raw POST body cap: 8 MB (returns `413 payload_too_large` above that — covers a 5 MB image plus base64 inflation plus headers).

### Persistence — placeholder, not bytes

`chat_messages.content` stores only `[file: shot.png 320 KB]` lines next to the user's text. The actual base64 bytes only live in the LLM context for that turn, so DB rows stay small and history reload doesn't re-ship megabytes to the browser. A `meta.attachments[]` summary (filename / mime / kind / bytes) is persisted alongside so admin tooling can audit what was attached.

### UI rendering — inline images, no raw `[file: …]` text

`AgentChatPanel` reads `meta.attachments[]` off the stored row and renders each entry inline on the user bubble:

- `kind: 'image'` with a `data_url` → `<img>` thumbnail at max 240×240 (`object-fit: contain`), wrapped in an anchor that opens the full image in a new tab.
- `kind: 'image'` without `data_url` (history reload — backend doesn't round-trip the bytes) → filename chip with size.
- `kind: 'text'` (md / json / txt) → filename chip with size.

The `data_url` is only populated on the optimistic just-sent bubble: the composer builds `data:${mime};base64,${data_base64}` from the staged payload before sending, so the user sees their image instantly without waiting for the server echo. On reload the chip path takes over.

`storedToTurn` strips the trailing `[file: name 320 KB]` placeholder lines from the bubble text when real attachments rehydrate — otherwise the bubble would show both the chip AND the raw text (owner flagged this 2026-05-17 as «глупо»). The persistence layer keeps the placeholder so plain-text history exports stay self-describing.
