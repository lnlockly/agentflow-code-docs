# Billing balance (FLOW)

## TL;DR

User balance lives in two Postgres tables. `flow_ledger` is the append-only journal — every credit/debit writes a row, and the user's balance equals `SUM(amount)` over their rows. `flow_balances` is a writer-maintained aggregate (one row per user, kept in sync by `creditUser()` / `debitUser()` inside the same TX as the ledger insert) used by the charge hot path under `SELECT ... FOR UPDATE` so concurrent turns don't race. Read-side helpers (`getBalance`, `isPaidUser`) sum the ledger directly so a stale or missing `flow_balances` row never lies to the user.

## 3-API balance parity (May 2026 fix)

After PR #310 switched `getBalance()` to `SUM(flow_ledger)`, three balance endpoints returned three different numbers for the same user:

| Endpoint | Repo / file | Pre-fix source | Symptom |
|---|---|---|---|
| `GET /auth/me` | `agentflow-agents/src/routes/auth-password.ts:386` | hard-coded `balance_micro: 0` | AuthProvider bootstrap stuck at 0 |
| `GET /_api/me` | `agentflow-api/src/routes/me.ts:39` | `SELECT balance FROM flow_balances` | shows writer-aggregate, misses ledger-only entries |
| `GET /_agents/me/balance` | `agentflow-agents/src/routes/billing.ts:95` | `getBalance()` + user_credits | correct |

Owner saw `-2458 USDF` on one rail, `+99.77` on another. Root cause: pre-#310 top-ups bumped `flow_balances` but never inserted a `flow_ledger` row, so the SUM-based read returned the wrong number for legacy users.

Reconcile: a one-shot SQL inserts a `reconcile_legacy_balance` ledger row equal to `flow_balances.balance - SUM(flow_ledger.amount)` for every user where the diff exceeds 0.001 USDF and no prior `reconcile_legacy_balance` row exists. After reconcile, both `flow_balances.balance` and `SUM(flow_ledger.amount)` converge for legacy users.

Fix (PRs `lnlockly/agentflow-agents#352` + `lnlockly/agentflow-api#2`): both `/auth/me` and `/_api/me` now compute `balance_micro` from `SUM(flow_ledger.amount)` (the same path `getBalance()` uses). `/_agents/me/balance` also exposes `balance_micro` so all three endpoints publish the same integer field for the same authenticated session.

## Data flow

```
                 deposit / promo / settle
                          │
                          ▼
                ┌──────────────────────┐
                │  creditUser/debitUser│  (single TX)
                └──────────┬───────────┘
                           │
        ┌──────────────────┴──────────────────┐
        ▼                                     ▼
  INSERT flow_ledger                  UPSERT flow_balances
  (append-only journal,               (cached aggregate, one
  every row has kind+amount)          row per user, used by
                                      settle() with FOR UPDATE)

read path
─────────
  GET /me/balance ─► getBalance(userId) ─► SUM(flow_ledger.amount)
  GET /auth/me    ─► getBalance(userId) ─► SUM(flow_ledger.amount)
  GET /_api/me    ─► SUM(flow_ledger.amount) (post-PR #352)
  isPaidUser(userId)                   ─► SUM(flow_ledger.amount WHERE kind IN paid_kinds)
```

## DB / Env / API

- Tables: `flow_ledger(user_id, amount, kind, ref_id, created_at, …)`, `flow_balances(user_id PK, balance NUMERIC(18,6))`
- Env: none specific to balance read; schema detection via `flowSchemaReady()` (`flow-meter.ts:155`)
- Routes: `GET /me/balance`, `GET /auth/me`, `GET /_api/me`, `POST /internal/users/:id/balance` (internal-secret guarded)
- MCP tools: none direct; balance is exposed via `agentflow-mcp-server` `/me/balance` proxy

## Invariants

- Every balance mutation goes through `creditUser()` / `debitUser()` (or `settle()` / `applyInvoicePaid()` / promo redeem, all of which update both tables in one TX). Raw `INSERT INTO flow_ledger` bypasses the `flow_balances` UPSERT and breaks any code path still reading the aggregate.
- `getBalance()` and `isPaidUser()` use the same predicate family (sum of `flow_ledger.amount`). When they disagree, the ledger is right.
- The three public balance endpoints (`/auth/me`, `/_api/me`, `/_agents/me/balance`) must all expose `balance_micro` derived from `SUM(flow_ledger.amount)`. A divergence is a bug.

## Buy subscription from balance (May 2026)

Owner directive 2026-05-17: payments must go through balance first. The old
direct `/subscriptions/checkout` path is still available but no longer
surfaced in the frontend. Users top up USDT first (CryptoBot / BEP-20 /
Platega, all unchanged) then spend balance on a tier:

| Route | Repo / file | Purpose |
|---|---|---|
| `POST /subscriptions/buy-from-balance` | `agentflow-api/src/routes/subscriptions.ts:239` | Debit balance + activate sub atomically in `db.transaction`. Single `flow_ledger` row `kind='debit_subscription_buy'`. No grant credit — `flow_balances.balance` is the FLOW-credits column and the tier value is captured in `meta.grant_flow` for audit. |
| `GET /me/flow-balance` | `agentflow-api/src/routes/subscriptions.ts:601` | Read balance + last 20 ledger rows |
| `GET /me/subscription` | `agentflow-api/src/routes/subscriptions.ts:560` | Latest sub row (status-priority ordered) |
| `agentflow-landing/src/pages/AccountSubscription.tsx` | landing | UI for the two-step flow at `/account/subscription` |
| `agentflow-landing/src/main.tsx:521` | route registration | `<Route path="/account/subscription" …>` |

Tier matrix (`flow-credits.ts:125-138`): `plus=$20→20 USDF`, `pro=$100→100`,
`max=$200→200`. The route inserts the subscription row with
`payment_method='balance'` for audit.

Insufficient-balance path returns HTTP **402** with
`{ balance, required, topup_url:'/me/topup' }`. The frontend renders an
inline "Не хватает X USDT" hint per tier card and offers a
"Пополнить баланс" button that links to `/account/billing` (the existing
top-up flow).

| Symptom | Log signature for grep | Where to fix |

The grant pathway only applies to off-platform USDT payments via the legacy `/subscriptions/checkout` route (cryptobot/platega/bep20 webhook), where there's a separate USDT-in event. |
