# Accounts Pult V2 — entity browser + contact resolution + history

## TL;DR
V2 adds three backend surfaces on top of the V1 `/cabinet/accounts` backend:
(1) a **generic entity browser** — list a connected account's dialogs / channels
/ contacts / gigs / wants and read one entity's message thread; (2) **contact
resolution** so the command loop turns «напиши Косте» into a concrete
`@username`/id before drafting a send; (3) **persisted command history** reusing
the copilot store so a reload replays the transcript and the loop keeps context.
Still MCP-first and platform-generic — every entity-kind is one data row in a
registry (`PLATFORM_ENTITY_REGISTRY`), zero `if (platform === …)` in routes/core.

## Data flow
```
ENTITIES  GET /me/accounts/telegram:4/entities?kind=dialogs
            → requireSession (owner=session.sub)
            → resolveOwnedAccount("telegram:4")  // owner-scope verify
            → fetchEntities(platform=telegram, accountId=4, kind=dialogs)
                → getEntityKind → def.source.argsFrom → mcpDirect.callTool(
                    'telegram','get_dialogs',{owner_user_id,account_id,limit})
                → def.source.normalize(raw) → Entity[]
            → { ok, kind, entities:[{platform,account_id,kind,id,title,
                subtitle,meta,unread}] }

THREAD    GET /me/accounts/telegram:4/entities/dialogs/<peer>/messages
            → fetchEntityThread → def.thread → get_messages
            → { ok, kind, entity_id, messages:[{id,role:me|them,text,ts,meta}] }

RESOLVE   POST /me/accounts/telegram:4/command { text:"напиши Косте привет" }
            → runAccountCommand injects resolve_contact into tools[]
            → model calls resolve_contact{query:"Костя"}
            → resolveContact → get_dialogs → fuzzy-rank → candidates[]
            → model picks @username → drafts send_message → owner approval gate

HISTORY   POST …/command also: ensureAccountThread(acct:telegram:4) +
            seed loop from loadAccountThread + append every turn.
          GET …/thread → loadAccountThread → { ok, account_id, messages }
```

## DB / Env / API
- Tables: REUSE `copilot_threads` / `copilot_messages` (no migration), thread id
  `acct:<platform>:<account_id>`, `agent_slug='account-pult'`. Entities are live
  MCP reads — never persisted.
- Routes: `GET /me/accounts/:accountId/entities`,
  `GET /me/accounts/:accountId/entities/:kind/:entityId/messages`,
  `GET /me/accounts/:accountId/thread`.
- MCP tools: telegram `get_dialogs` / `get_messages`; kwork `list_dialogs` /
  `get_dialog` / `list_my_kworks` / `list_wants`. Bridge =
  `mcpDirect.callTool(server, tool, args, { ownerUserId })`.
- Kwork tools key on `account_session_secret_key` (default `KWORK_SESSION_JSON`),
  not `owner_user_id` — owner is pinned into the MCP URL `?owner=`.

## Failure modes
| Symptom | Log signature for grep | Where to fix |
|---|---|---|
| Entities list empty for a live account | (no log — silent degrade) returns `{ok:true,entities:[]}` | `services/account-entities/index.ts:106` (catch → `[]`) |
| 404 on entities | `account_not_found` | `routes/me-accounts.ts:103` (owner-scope miss) |
| 400 on entities | `unknown_kind` | `services/account-entities/index.ts:87` (kind not in registry) |
| Thread read returns `[]` after reload | thread owned by another user | `services/account-thread.ts:115` (userId guard) |
| `resolve_contact` returns no candidates | (silent — loop asks owner to clarify) | `services/account-contact-resolver.ts:145` (score ≥ 0.3 cut) |
