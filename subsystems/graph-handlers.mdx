# Graph executor — node handlers

## TL;DR

The walker resolves each `WorkflowNode.id` to a typed handler via
`defaultRegistry.resolve(kind)`. 22 unique node ids ship across the 5
seeded boilerplates; each has a handler under
`src/services/graph-executor/handlers/<group>.ts`. Deterministic work
(deploy, scrape, smoke-test, request_token) wraps an existing service in
≤20 LOC. Generative work (pick_theme, scaffold_*, *_flow) goes to a
per-node coder-delegate with a tight `OUTPUT_EXPECTED` envelope so the
walker can validate the result.

Contract: [`architecture/graph-executor.mdx`](/architecture/graph-executor).

## Data flow

```
WorkflowSchema (from agent_boilerplates row)
        │
        ▼
walker.run({ projectId, workflowSchema })
        │
        ▼ Kahn topo sort, parallel where in_edges = 0
NodeKind ── resolveHandler(kind) ──► defaultRegistry.resolve
                                          │
        ┌─────────────────────────────────┴──────────────────────────────────┐
        ▼                                                                    ▼
deterministic handler                                           coder-delegate handler
  (deploy, scrape_tg, smoke_test,                                 (pick_theme, scaffold_*,
   request_token, deploy_caddy, …)                                 booking_flow, …)
        │                                                                    │
        ▼                                                                    ▼
wraps existing service                                          ctx.coderInvoke({
(runtime-supervisor.deploy,                                       slug, brief,
 auto-bot.autoCreateTelegramBot,                                  expects: [files...],
 bot-auto-tester.runBotSmokeTest,                                 timeoutMs })
 build-node-wrappers.run*)                                                  │
        │                                                                    ▼
        │                                                          coder-tg-bot / coder-landing /
        ▼                                                          coder-spa / coder-backend
output validated against handler.outputSchema (zod)
        │
        ▼
ctx.emit({ kind: 'node_finished', payload: { output } })
```

## DB / Env / API

- Tables: none new — uses `project_events`, `projects`, `project_secrets`, `pipeline_runs` view.
- Env:
  - `BOT_TOKEN_POOL` — read inside `request_token` → `auto-bot.autoCreateTelegramBot` only. Handlers never touch process.env directly.
  - `FF_AUTO_BOT_CREATE_BOTFATHER` — same.
  - `RUNTIME_SUPERVISOR_ENABLED` — gates the `flag_gated` path used by `deploy_landing`.
- Routes: none new. Events stream via `GET /me/pipelines/:id/events` SSE (consumed by `CanvasLive`).
- MCP tools called by handlers: `code-exec.expose_public` (deploy_caddy), `code-exec.exec` (transitively via wrappers).

## Failure modes

| Symptom | Log signature for grep | Where to fix |
|---|---|---|
| Node falls through to coder-fallback in prod | `[graph-executor] handler missing for kind=<id>, delegating to coder-agent` | Add handler under `handlers/<group>.ts` and re-run `tests/unit/graph-executor/handlers/registry-coverage.test.ts` |
| `request_token` returns assigned=true but bot has no `BOT_TOKEN` secret | `[auto-bot] pool empty and FF_AUTO_BOT_CREATE_BOTFATHER off, skipping` | Refill pool OR set the flag; see [bot-pool](/architecture/bot-pool) |
| `smoke_test` output has `report.skipped` | `bot_smoke_skipped` in `project_events` | Tester unavailable (no TG account). Configure a tester account; not a handler bug |
| `self_heal_loop` returns task_created=false skipped=`no_smoke_report_in_steps` | `no_smoke_report_in_steps` (literal in handler) | Upstream `smoke_test` didn't run before `self_heal_loop` — fix the edge in `agent_boilerplates.workflow_schema` |
| `scrape_tg` rejects with `scrape_tg_requires_username_or_brief` | grep handler source | Node config must include `username` or `brief` — fix the seed |
| Coder reply missing `files_written` array | handler returns `files_written: []` and walker per-kind policy decides | If kind is `fail-fast` on this node, brief was too broad — tighten `output_expected` in the registration |
| Duplicate handler registration on boot | `duplicate_handler:<kind>` thrown at module load | Two registrations for one `kind` — remove the second one |
