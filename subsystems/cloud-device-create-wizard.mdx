# Cloud device create wizard (hosted/new)

## TL;DR

`/cabinet/devices/hosted/new` is a guided multi-step wizard (one simple choice
per step, progress bar) for creating a cloud device. For an AI-agent (daemon)
device the steps are Тип → Мощность → Движок и софт → Разрешения → Готово; for
a plain Linux device the engine + permissions steps drop out (Тип → Мощность →
Готово). The create POST is unchanged (`/me/hosted-devices`). The permissions
step's chosen scope is applied **inline after create** via
`devicesApi.updateScope(user_device_id, scope)`, best-effort.

This is a sibling of [device-create-wizard](/subsystems/device-create-wizard)
(the unified `/cabinet/devices/new` funnel) — different route, different page.

## Data flow

```
/cabinet/devices/hosted/new
  └─ CabinetHostedDeviceNew (wizard)
       Тип ─ Мощность ─ [Движок+софт] ─ [Разрешения] ─ Готово
                                                          │
       «Включить агента 24/7» ──► POST /me/hosted-devices { name,size,kind,preinstall,template? }
                                     │  201 { device: { id, user_device_id } }
                                     ▼
       daemon + user_device_id?  ──► POST /me/devices/<user_device_id>/scope { scope }   (best-effort)
                                     │  (failure is swallowed — backend safe default stays)
                                     ▼
       navigate → /cabinet/devices/hosted/<device.id>
```

Why `user_device_id` and not `device.id`: the `/me/devices/:id/scope` route
runs `UPDATE user_devices ... WHERE id = :id` — it does NOT resolve a
`hosted_devices.id`. `device.id` (returned for the `/cabinet/devices/hosted/:id`
detail route) is the `hosted_devices.id`. The create response carries both, so
the wizard sends the scope to `device.user_device_id`.

## Permissions step

Plain-RU framing «Что агенту можно». Reuses `PERMISSION_BUNDLES` /
`bundleStateFor` / `applyBundleToggle` from `CabinetDevicePermissions` so the
bundle → scope-id mapping never drifts (labels localised via i18n keyed by
bundle id). A bundle ON means its scope ids are absent from
`scope.confirm_before` (agent runs without the per-call confirm gate). The
«спрашивать перед важными действиями» toggle maps to `shell.exec` in
`confirm_before`; the spend-limit chips set `scope.budget_usd` (default $2). The
wizard opens on `WIZARD_DEFAULT_SCOPE` (all bundles ON, shell.exec gated) so it
never starts on a «mixed» badge.

## DB / Env / API

- Tables: `user_devices` (scope_json), `hosted_devices`
- Routes: `POST /me/hosted-devices` (create), `POST /me/devices/:id/scope` (scope apply)
- i18n keys: `cabinet.hosted.wiz.*` in `agentflow-landing/src/i18n/{ru,en,zh}.json`

## Failure modes

| Symptom | Log signature for grep | Where to fix |
|---|---|---|
| Cloud create returns 404 (service not deployed) | `cabinet.hosted.unavailable_title` shown | `CabinetHostedDeviceNew.tsx` 404 branch in `submit()` |
| Goose engine rejected (canary off) | `goose_canary_disabled` | `submit()` 403 branch → reverts to coder, returns to engine step |
| Permissions not applied after create | (silent — try/catch around `updateScope`) | owner re-applies at `/cabinet/devices/:id/permissions` |
| Sticky «Далее» hidden behind mobile tab bar | n/a (visual) | footer `bottom-[60px] md:bottom-0`, `CabinetHostedDeviceNew.tsx:819` |
