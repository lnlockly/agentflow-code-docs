# Matrix Bots

## TL;DR

Eight service bots (`@af-helper`, `@af-research`, `@af-image`, `@af-claude`, `@af-tg-poster`, `@af-poster`, `@af-spec`, `@af-ops`) are registered on the Dendrite homeserver via shared-secret registration and run a per-bot `/sync` long-poll loop inside `agentflow-agents`. Handlers cover a static help menu, URL→TL;DR summarisation, text→image generation, Claude chat, Telegram posting (v1 stub), multi-network cross-posting (`@af-poster` — TG + VK in v1, IG deferred), spec-from-brief writing, and the owner-only ops console with constrained tool-use (see @af-ops below). Triggered on DM or `@mention`; gated by `MATRIX_BOTS_ENABLED=1`.

## Data flow

```
agentflow-agents pod (RUN_WORKERS=true)
   │
   ├─ bootstrap → startMatrixBotsRunner()
   │     ├─ ensureAllBots() — per slug:
   │     │      POST /_matrix/client/v3/login (m.login.password, password=HMAC(BOT_KEY, slug))
   │     │      ├─ 200 → reuse access_token, upsert
   │     │      └─ 403 → GET  /_synapse/admin/v1/register (nonce)
   │     │              POST /_synapse/admin/v1/register (nonce, slug, password, mac)
   │     │              200 → upsert access_token + device_id
   │     │              PUT  /profile/<user>/displayname (cosmetic)
   │     └─ for each bot → detached runBotLoop()
   │
   └─ runBotLoop(bot):
         while true:
           GET /sync?timeout=25000&since=<next_batch>
              ├─ rooms.invite → POST /rooms/<id>/join
              └─ rooms.join.timeline.events:
                    skip if sender === bot.mx_user_id
                    skip if event_id already seen
                    isDm = joinedMembers(roomId).length === 2
                    mentioned = body contains @<slug>(:<server>)?
                    if isDm || mentioned:
                       command = parseCommand(body, slug, server)
                       handler[slug](ctx, { roomId, eventId, body, isDm, command })
           UPDATE matrix_bots SET next_batch=…, last_synced_at=NOW()
```

## DB / Env / API

### Postgres
- Table: `matrix_bots` — one row per bot. PK `slug`. `next_batch` is the `/sync` cursor; `mx_password` is the HMAC so re-login is deterministic. Migration `2026-05-21c-matrix-bots.sql`.

### Env (agentflow-agents)
- `MATRIX_BOTS_ENABLED` — `1` to start the runner, anything else (default) skips it.
- `MATRIX_BOT_KEY` — 32-byte random hex; HMAC key for per-bot password derivation. Must stay constant; rotation invalidates existing bot logins until each row's `mx_password` is rewritten.
- Reuses existing matrix-chat vars: `MATRIX_HOMESERVER_URL`, `MATRIX_SERVER_NAME`, `MATRIX_REGISTRATION_SHARED_SECRET`.

### Matrix endpoints used
- `POST /_matrix/client/v3/login` — per-bot login
- `GET / POST /_synapse/admin/v1/register` — shared-secret first-time provisioning
- `GET /_matrix/client/v3/sync` — long-poll (25s)
- `POST /_matrix/client/v3/rooms/{id}/join` — invite auto-accept
- `GET /_matrix/client/v3/rooms/{id}/joined_members` — DM detection
- `PUT /_matrix/client/v3/rooms/{id}/send/m.room.message/{txn}` — text + image events
- `POST /_matrix/media/v3/upload` — image upload (af-image)
- `PUT /_matrix/client/v3/profile/{user}/displayname` — first-provision cosmetic

## @af-image — multi-model slash commands

`@af-image` exposes three command families. They mix freely:

| Family | Verbs | Effect |
|---|---|---|
| Aspect | `/wide`, `/tall`, `/square` | Sets the output size (`1792x1024`, `1024x1792`, `1024x1024`). Default is square. |
| Model | `/dalle3`, `/flux`, `/gpt-image` | Sets the DesignAPI model id (`dall-e-3`, `flux-pro`, `gpt-image-1`). Default is router-picked from `IMAGE_MODEL_CASCADE`. |
| Help | `/help`, `/start` | Returns the full command list + supported model ids. |

The user picks one command per message. Mixing two slashes in one body (e.g. `/dalle3 /wide ...`) is not supported — the leading slash wins. Model commands always render at square aspect; for a wide DALL·E image, use `/dalle3` first, then re-render with `/wide`.

When a model command is set, the handler passes `model` to `useModel(ModelType.IMAGE, …)`. On DesignAPI rejection (typical signal: `model_not_found` / `group_no_image_access`) the handler retries once without the `model` field so the router walks its cascade, then posts a `Модель <name> временно недоступна, использую дефолт.` notice in the room. Hard failures still surface as `Image generation failed: …`.

## @af-research follow-ups — 📄 / 🔗 / 💾 reactions

After @af-research posts a TL;DR, it pre-attaches three reactions on its own message. Owner taps one to drive a follow-up without re-pasting the URL:

| Reaction | Action |
|---|---|
| 📄 | Longer expansion (TEXT_LARGE, 8-12 sentences with one counter-argument + practical takeaway). |
| 🔗 | 5 related resources / sub-topics (TEXT_SMALL numbered list). |
| 💾 | Save article into the owner's knowledge base — ingests into the most recent `category='researcher'` agent (fallback: most recent agent of any category). Reply confirms `agent_slug` + chunk count. |

Reactions on the af-research bot's sync stream are dispatched through `parseAnnotationReaction(ev)` from `mode-c.ts:90` → `handleResearchFollowup` in `src/services/matrix-bots/handlers/research-followups.ts:213`. Auth boundary: only `@user-<digits>:<serverName>` mxids may trigger (same `parseOwnerMxid` gate Mode C uses). Bot self-reactions, TG puppets, and non-followup emojis fail closed.

Payload cache: TL;DR payload (`url`, `title`, `summary`, `articleText`) is keyed by the TL;DR event id in a 200-entry FIFO `Map`. Cache miss (runner restart) replies «Не нашёл оригинал TL;DR в кеше — пришли ссылку ещё раз» instead of failing silently.

Idempotency: `(roomId|originalEventId|sender|key)` recorded in a 200-entry `Set` — re-delivered reactions never double-post.

Save-to-KB target resolution lives in `findIngestTargetAgent(afUserId)` and reuses the same `ingestForAgent` / `chunkText` / `resolveAgentUuid` helpers `/me/agents/:slug/knowledge/url` uses, so saved articles show up in retrieval immediately.

| Cache miss after runner restart | `[af-research-followup] payload_missing` | Owner re-pastes URL — payload cache is in-process |
| Owner has no agents to ingest into | `[af-research-followup] save_failed_no_agent` | Create an agent in /agents — KB ingest is per-agent |

## Mode C — send-as-owner via reaction

When `@af-claude` finds itself in a room that contains at least one TG-puppet member (`@telegram_<tgid>:agentflow.website`), the owner is using it as a hint assistant inside a TG-bridged dialog. Workflow:

1. Bot generates the reply as usual.
2. Body is prefixed with `💡 Предложение: ` and sent as plain text (no markdown so the eventual forward to TG is clean).
3. Bot immediately `PUT`s its own `m.reaction` with `key: '👍'` annotating its message.
4. Owner taps the 👍 (the count increments from 1 → 2).
5. The runner spots the `m.reaction` on the next `/sync` batch, calls `handleModeCApprove`, which:
   - parses the reactor's mxid via `parseOwnerMxid` (`@user-<id>:<server>` only; puppets and bots fail closed),
   - fetches the bot's original message via `GET /rooms/<id>/event/<id>`,
   - strips the suggestion prefix,
   - mints a fresh Matrix token for that AF user through `issueMatrixTokenForAfUser` (same helper Element SSO uses),
   - `PUT /rooms/<id>/send/m.room.message` as the owner.
6. mautrix-telegram observes the owner-sent message and forwards it via the owner's TG login as a normal user message — the TG contact sees no `AF Claude:` prefix.

Idempotency: `roomId|originalEventId|sender` is cached in a 200-entry FIFO so re-delivered reactions never double-post.

Auth scope: only `@user-<digits>:<serverName>` mxids may trigger. Bridge bots, TG puppets, and manually registered accounts (e.g. `mlm808`) are silently dropped with `[mode-c] sender_not_authorized`.

| Failure | Log signature for grep | Where to fix |
|---|---|---|
| Reactor isn't an AF owner | `[mode-c] sender_not_authorized` | Expected — only owners forward |
| Bot's pre-attached 👍 leaks into approval | (no log — `sender === bot.mxUserId` early-return) | n/a |
| Original suggestion not found (redacted) | `[mode-c] original_event_not_found` | Owner re-asks Claude for a new suggestion |
| Reaction targets a non-suggestion message | `[mode-c] original_event_not_a_suggestion` | Expected — only `💡 Предложение: …` is forwardable |
| Token issue fails | `[mode-c] token_issue_failed` | Same root causes as `/me/chat/tg/login` — bridge env misconfig |
| Owner send fails | `[mode-c] owner_send_failed` | Inspect `err` — typically `send_403` if user is not joined to room |

## Voice → text via ElevenLabs Scribe (@af-claude)

When `@af-claude` receives an `m.room.message` with `msgtype: m.audio` (Telegram voice notes forwarded through mautrix-telegram, or native Matrix voice messages from Element), the handler:

1. Pulls the MXC bytes via the authenticated v1 endpoint — `GET /_matrix/client/v1/media/download/<server>/<mediaId>` with `Authorization: Bearer <bot_token>` (`downloadMedia` in `src/services/matrix-bots/client.ts`). The legacy `/r0/media/download/` and `/v3/media/download/` paths are unauthenticated and removed from Dendrite, so v1 is the only working route for bots.
2. Sends the bytes to ElevenLabs Scribe: `POST https://api.elevenlabs.io/v1/speech-to-text` with multipart `file=<bytes>`, `model_id=scribe_v1`, `language_code=auto`. Header `xi-api-key: $ELEVENLABS_API_KEY` (same env the project-pod TTS helper already uses).
3. Substitutes `[voice] <transcript>` as the user-turn body. The `[voice] ` prefix tells the LLM the input was spoken vs typed so it can match register.
4. Caches the transcript by `event_id` in an in-memory LRU (cap 200). The Claude handler walks 30 events of history on every reply, so without the cache one 10-second voice note would re-bill ElevenLabs on every later turn. Empty / failed transcripts are also cached so we don't retry a broken MXC forever.
5. Silent fallback on any failure — no «I can't hear voice» reply. Owner explicitly asked for this; the previous behaviour broke a real 2026-05-21 TG-bridged conversation.

Files:
- `agentflow-agents/src/services/matrix-bots/stt.ts` — `transcribeAudio`, `transcribeAudioEvent` (LRU-cached), `extractAudioFromContent`.
- `agentflow-agents/src/services/matrix-bots/client.ts:200` — `downloadMedia` helper.
- `agentflow-agents/src/services/matrix-bots/runner.ts` — pulls `content.url` + `content.info.mimetype` off `m.audio` events and threads them through `IncomingMessage.audioUrl/audioMime`.
- `agentflow-agents/src/services/matrix-bots/handlers/claude.ts` — live audio dispatch + historical audio walk.

Env: `ELEVENLABS_API_KEY` (already injected via `agentflow-agents-env` Secret; absent key logs `[claude-stt] api_key_missing` once and skips silently).

## @af-ops — owner remote-control bot

Seventh bot, distinct from the chat siblings: a Claude-with-tools console that lets the owner DM the AgentFlow cluster from Element on a phone. Auth-gated to `@user-<digits>:<serverName>` mxids only — anyone else gets `[af-ops] sender_not_authorized` logged and dropped.

### Tool-use loop

`src/services/matrix-bots/handlers/ops.ts` runs a max-10-iteration loop around `useModel(ModelType.TEXT_LARGE, { tools: OPS_TOOLS, … })`. After each model turn:

1. If the response has `tool_use` blocks, dispatch each through `ops-tools.ts` and append a `role: 'user'` `tool_result` block back into messages.
2. If the response is text-only → ship that to the room, end.
3. If the loop hits iteration 10 → one no-tools wrap-up call so the model has to answer with what it has.

The handler never throws to the runner — any exception lands as a one-line failure reply in the room instead.

### Tools + guards

| Tool | What it does | Guard |
|---|---|---|
| `bash` | Runs a one-liner inside the agentflow-workers pod | Prefix allow-list (kubectl get/describe/logs/top, gh pr/run/repo/api, git read-only, curl GET, echo/uname/date/df/free/ps) + deny pattern set (rm, kubectl delete/exec/set/apply, sudo, redirect, curl -X POST, git push) + subshell `$()` / backtick refuse |
| `ssh_ff_france` | Same allow-list, executed on the cluster node via `ssh ff-france '<cmd>'` | Same guard as `bash` |
| `pg_query` | Resolves `agentflow-postgres` pod via label selector, then `psql -U agentflow -d agentflow -At -c '<sql>'` | `guardSqlReadOnly`: must start with SELECT/WITH/EXPLAIN/SHOW; refuses INSERT/UPDATE/DELETE/DROP/TRUNCATE/ALTER/CREATE/etc + multi-statement scripts |
| `gh_pr_merge` | `gh pr merge <N> -R <repo> --squash --admin` | Repo must match `^lnlockly/agentflow-[a-z0-9-]+$` |
| `matrix_read_room` | Reads recent events via `recentMessages` so the bot can answer "что в #lobby обсуждают" | room_id must start with `!`, limit ≤ 100 |

Every refusal returns `{error: 'refused:<reason>'}` JSON so the model can re-plan rather than crash. Output bytes capped at 60 KB per tool call; timeouts default 60 s, max 180 s.

| Tool refused unexpectedly | `[af-ops] tool_call` with `isError:true` and `refused:no_allow_prefix` | Add verb to `SHELL_ALLOW_PREFIXES` after security review |
| SSH fails with Permission denied | tool_call result `stderr` contains `Permission denied (publickey)` | Mount `agentflow-workers-ssh-key` Secret + add pubkey on ff-france |
| Postgres pod resolution fails | tool_call `pg_query` result with `pod not found` | Check `kubectl -n franchise-factory get pod -l app=agentflow-postgres` returns a row |
| Loop hits iteration cap | `[af-ops] tool_call` repeats 10× then "Не успел свести в ответ" | Owner narrows the request |

## @af-poster — multi-network cross-poster

DM-only composer. Owner types one message, bot fans it out to every linked network. Same auth gate as `@af-ops` (`@user-<digits>:<serverName>` only).

### Compose syntax

| Form | Result |
|---|---|
| `to: tg Привет` | TG only |
| `to: vk Привет` | VK wall only |
| `to: tg+vk Привет` | both |
| `to: all Привет` | every linked network (TG + VK + IG) |
| Plain text (no `to:`) | bot caches the body for 5 min, asks "Куда?" — owner replies with `tg` / `vk` / `tg+vk` / `all` |

### Networks (v1 reality check)

| Network | v1 status | How it dispatches |
|---|---|---|
| TG | live | Reads `chat_tg_links.account_labels.default_channel` (owner labels their channel in cabinet) + `primary_login_id` (cast to numeric `account_id`), calls `mcpDirect.callTool('telegram', 'send_message', { owner_user_id, peer, text, account_id })`. No raw TG API client. |
| VK | live | Reads every linked `chat_vk_links` row for the owner, POSTs `wall.post` per row with the stored `access_token`. Token must have `wall` scope; VK error 15 surfaces a friendly hint. |
| IG | deferred (v2) | Always returns `IG: Instagram Graph API требует Business аккаунт + Content Publishing API. Отложено до v2.`. v2 plan: mautrix-meta + IG Business Content Publishing. |

### Failure modes
| Symptom | Log signature for grep | Where to fix |
|---|---|---|
| Bot ignores non-owner DM | `[af-poster] sender_not_authorized` | Expected — owner-only auth gate |
| TG: «не настроен канал по умолчанию» | reply contains `default_channel` | Set `account_labels.default_channel` in `chat_tg_links` (cabinet → Telegram → "Канал по умолчанию") |
| TG: missing account | reply contains `аккаунт не привязан` | Owner links a TG account via mautrix-telegram wizard |
| VK: `error 15` | reply contains `scope \`wall\`` | Re-issue access_token with `wall` scope, update `chat_vk_links.access_token` |
| VK: `error 5` | reply contains `протух` | Token expired — re-link VK in cabinet |
| IG always deferred | reply contains `Отложено до v2` | Expected v1 — wait for v2 IG Business integration |

## @af-tg-poster — v2 login + post

Single-purpose Telegram bot: provision a TG account via the mautrix-telegram bridge wizard, then publish to any channel the owner's primary TG login can post into. DM-only, owner-only (same `parseOwnerMxid` gate as `@af-poster` / `@af-ops`).

### Commands

| Command | Effect |
|---|---|
| `/login` (alias `/connect`, `/connect-tg`) | Calls `bridgeLoginStart(cfg, mxid, 'phone')`, remembers the issued `login_id` + first step descriptor in an in-memory `Map<roomKey, WizardState>` (cap 50, FIFO). Reply prompts for the phone number. |
| Plain text reply during wizard | Treated as the value for `wiz.fieldId`, submitted via `bridgeLoginStep`. Walks phone → code → optional 2FA password until `step.type === 'complete'`, then drops the wizard state. |
| `/cancel` | Calls `bridgeLoginCancel` and clears in-memory wizard state. Idempotent — no active wizard returns a friendly hint. |
| `/accounts` (alias `/channels`) | Calls `bridgeWhoami` for the owner's mxid and renders one bullet per `login.id`. |
| `/post <channel> <text>` | Resolves channel via `parsePostCommand`, calls `postToTelegram(ownerUserId, text, { channelOverride: channel })`. Channel can be `@name`, `name`, or a numeric peer id. On success: `✅ Posted to <channel>`. On failure: `classifyPostError` maps the cross-poster string to one of `not_logged_in` / `channel_not_admin` / `rate_limit` or passes verbatim. |
| `/help` (alias `/start`) | Static Russian command menu. |

### State + persistence

Wizard state lives in process memory only. A pod restart drops the in-flight wizard; the owner re-runs `/login` and the bridge issues a fresh `login_id`. bridgev2 itself is the source of truth for completed logins (queryable via `/accounts`), so post-completion state survives restarts naturally.

The cross-poster path (`/post`) reuses `postToTelegram` from `src/services/cross-poster/tg.ts:111`. A new optional `channelOverride` field on the deps object skips the `account_labels.default_channel` lookup so `@af-tg-poster` can target any channel without forcing the owner to relabel their default. `primary_login_id` still feeds `account_id` so tg-mcp picks the right MTProto session.

| Path | Role |
|---|---|
| `agentflow-agents/src/services/matrix-bots/handlers/tg-poster.ts:1` | v2 handler — wizard state machine, `/post`, `/accounts`, `/cancel`, owner auth gate |
| `agentflow-agents/src/services/matrix-bots/lib.ts:340` | `parsePostCommand` — `<channel> <text>` splitter shared with v1 |
| `agentflow-agents/src/services/matrix-bots/mode-c.ts:60` | `parseOwnerMxid` — mxid → AF user id auth boundary |
| `agentflow-agents/src/services/cross-poster/tg.ts:111` | `postToTelegram` now accepts `deps.channelOverride` for explicit channel targeting |
| `agentflow-agents/src/services/mautrix-tg-bridge.ts:177` | `bridgeLoginStart` / `bridgeLoginStep` / `bridgeLoginCancel` / `bridgeWhoami` — bridge HTTP client used by the wizard |
| `agentflow-agents/tests/matrix-bots/af-tg-poster.test.ts:1` | 24 pure-helper tests (`parsePostCommand`, mxid mapping, wizard step descriptor, prompt picker, error classifier) |

### Wire (data flow)

```
DM in Element (owner mxid `@user-N:agentflow.website`)
  ↓
runner /sync → handleTgPosterMessage
  ↓

  ↓

```

## Non-goals (v1)

- `@af-poster` is the multi-network production path (TG + VK). `@af-tg-poster` is the single-network specialist — owners use it when they want to post to a specific channel without juggling `to:` directives or default-channel labels.
- `@af-poster` IG dispatch is a stub; see "Networks (v1 reality check)" row above.
- No E2EE — bots stay out of encrypted rooms; messages there appear as `m.room.encrypted` and the runner silently skips them.
- ~~No room-create on bot side. Users invite the bot via Element's Start Chat.~~ As of 2026-05-21 the **Element SSO bounce** reads `matrix_bots.access_token` for each enabled row and calls `POST /createRoom` per bot the first time a user lands in Element. See [Element Web SSO bounce](/subsystems/element-web) (Phase 3b) for the gate (`users.chat_onboarded_at`) and failure modes.
- No metrics export — `last_synced_at` per row is the only health signal until prom-client wiring lands.
