# Showcase Kits

## TL;DR

A showcase kit is a small static bundle (`graphs`, `integrations`, optional `hosted`) that POST `/me/showcase/:slug/deploy` materialises into real per-user rows: a `flows` row per template, a `hosted_devices` row when the kit needs a runtime, and a `missing_integrations` list when a provider is `status='never'` so the UI can route the caller to `/account/integrations` and back. Kits live as static TS data in `agentflow-agents/src/services/showcase-kits.ts` — no DB migration, no separate listings table. The catalog is served by `GET /me/showcase` and rendered by `agentflow-landing/src/pages/Showcase.tsx` at the `/showcase` route.

## Data flow

```
[user clicks "Развернуть" on /showcase]
   │
   ▼
POST /me/showcase/:slug/deploy { name?, skip_integrations? }
   │
   ├── lookup kit in showcase-kits.ts (404 if unknown)
   │
   ├── for each graph:
   │     POST /me/flows  (internal app.fetch, same headers)
   │       → returns { flow.slug }   (slug pattern: <template>--<hash>)
   │
   ├── for each integration:
   │     GET /me/integrations → status check
   │       missing[] when status !== 'connected'
   │
   ├── if kit.hosted is set AND missing[] is empty (or skip_integrations=true):
   │     POST /me/hosted-devices { kind:'daemon', size, marketplace_preset_slug }
   │       → returns { device.id }
   │
   ▼
{ ok, deployments: { flow_slugs, hosted_device_ids, missing_integrations }, errors, next_url }
   │
   ▼
landing: toast + redirect to next_url
   next_url = /account/integrations?return_to=/showcase/<slug>   when missing[]
            | /showcase/<slug>/dashboard                          when all wired
```

## DB / Env / API

- **Tables read:** `flows`, `hosted_devices`, `agent_presets`, `project_secrets` (via `/me/integrations`).
- **Tables written:** `flows` (clone), `hosted_devices` + paired `user_devices` (daemon).
- **No new tables.** Kit registry is static TS data, same pattern as `studio-flow-templates.ts`.
- **Routes:**
  - `GET  /me/showcase` — list 8 kits with resolved component status (does NOT check the caller's integrations; that happens at deploy time).
  - `GET  /me/showcase/:slug` — single kit + resolved component refs.
  - `POST /me/showcase/:slug/deploy` — body `{ name?: string, skip_integrations?: boolean }`.
- **Auth:** `requireSession` (cookie or `x-api-key`). All writes scoped to `session.sub`.
- **Internal calls:** `app.fetch(new Request(...))` reuses the same Hono app so the original session middleware runs against the cloned request headers. No duplicate provisioning logic.

## Failure modes

| Symptom | Log signature for grep | Where to fix |
|---|---|---|
| Deploy returns 404 | `[showcase] unknown_kit slug=` | `services/showcase-kits.ts` — slug not in `SHOWCASE_KITS`. |
| Deploy returns `ok:true` but `errors[]` non-empty | `[showcase] flow_clone_failed kit=` | Studio template slug stale; sync with `studio-flow-templates.ts`. |
| Deploy returns `missing_integrations` non-empty | `[showcase] missing_integrations user=` | User has no row in `project_secrets` for the provider; UI sends them to `/account/integrations`. |
| Hosted device stuck in `provisioning` > 5 min | `[hosted-devices] apply failed id=` | `routes/me-hosted-devices.ts` kubectl apply tier — same failure path as marketplace deploy. |
| Preset slug not found | `[hosted-devices] deploy preset_not_found slug=` | `presets/<slug>.json` not seeded on prod; check `bootstrap-presets` log on pod start. |

## Anti-slop note

Kit copy is Russian and avoids the banned vocabulary (no «реально», «просто», «буквально», em-dash dividers, three-item lists, «не Х. Y.» antithesis). The hosted runtime is called «облачный компьютер», the integration secret pane stays «интеграции».
