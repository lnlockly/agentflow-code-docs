# TG MCP (Telethon pool)

## TL;DR

Отдельный Python 3.12 сервис (FastMCP + Telethon) выполняет MTProto-операции над user-owned TG-аккаунтами. Sessions хранятся как Fernet-encrypted blob в SQLite (`accounts.session_blob`); per-account-id lock + LRU `max_size=32` — TelethonPool не может одновременно держать тысячи коннектов. Auth — JWT HS256 (issued агентом-агентов), exempt routes `/health`, `/`, `/sse/messages`, OPTIONS. Все TS-сервисы внутри agentflow-agents ходят через `${TG_MCP_URL}`.

**Warm pool (2026-05-14):** на старте каждый `status='active'` аккаунт прогревается через `pool.warm_all()` — `client.connect()` + `is_user_authorized()` сразу, и фоновая задача каждые 60с делает `get_me()`. Warm-аккаунты исключены из LRU-вытеснения. Первый scrape после deploy экономит 500ms-2s MTProto cold-start.

## Data flow

```
Coder agent / Maestro / service в agentflow-agents
   ↓ MCP client POST ${TG_MCP_URL}/mcp { tool: "send_message", args: {...} }
   ↓ Authorization: Bearer <JWT HS256, sub=owner_user_id, secret=AUTH_JWT_SECRET>
MCPAuthMiddleware (server.py:29)
   ↓ verify JWT → set request.state.caller = Caller(owner_user_id=…)
   ↓ exempt: /health, /, /sse/messages, OPTIONS
FastMCP tool dispatch (_register_tools, server.py:105)
   ↓
TelethonPool.client(owner_user_id, phone)  — telethon_pool.py:57
   ↓ acquire per-account-id lock (no concurrent calls for same account)
   ↓ load Account from sqlite (storage.py)
   ↓ _decode_session (Fernet unwrap, crypto.py:12)
   ↓ TelegramClient(StringSession(...), api_id, api_hash) — connect/reuse
   ↓ run MTProto operation
   ↓ _persist_session (Fernet wrap) — save updated session
   ↓ release lock
   ↓ return tool result
```

**Warm pool flow (startup + steady state):**

```
uvicorn lifespan start
   ↓ storage.init()
   ↓ pool.warm_all()
      └── for row in accounts WHERE status='active' AND session_blob IS NOT NULL:
            ↓ Fernet unwrap → StringSession → TelegramClient.connect()
            ↓ client.is_user_authorized()  ← MTProto handshake paid HERE, not on first request
            ↓ _cache[id] = client; _warm_set.add(id)
   ↓ pool.start_keepalive(interval=60s)  ← background asyncio.Task

every 60s (until stop_keepalive):
   for id in _warm_set:
     client = _cache[id]
     client.get_me()  ← cheap MTProto ping; logs warm_pool_keepalive_failed on error

on real scrape request:
   pool.client(account)  ← cache hit, lock acquired, NO connect/auth round-trip
```

## DB / env / API surface

**SQLite (`DB_PATH`):**
- `accounts` (`owner_user_id`, `phone`, `session_blob BLOB`, `status`, `auth_step`, `created_at`, `updated_at`). Unique (owner_user_id, phone).
- `pending_logins` (`owner_user_id`, `phone`, `account_id`, `session_blob BLOB` (encrypted in-progress StringSession), `phone_code_hash`, `awaiting_password`, `created_at`). PK (owner_user_id, phone). Durable mirror so an add-phone → confirm-code flow survives a pod restart; cleared on successful `confirm_code` (`forget_pending`).

**Env:**
- `TG_API_ID`, `TG_API_HASH` — Telegram developer credentials.
- `FERNET_KEY` — base64 32B key для wrap/unwrap session blob.
- `MCP_AUTH_SECRET` — старый X-MCP-Auth header secret (legacy fallback).
- `AUTH_JWT_SECRET` — shared с agentflow-agents (HS256).
- `AGENTFLOW_AGENTS_URL=http://agentflow-agents:4100` — куда тикает back-callback.
- `INTERNAL_API_SECRET` — for callbacks `/internal/tg-callbacks` в agentflow-agents.
- `SESSION_DIR` — на случай файловой Telethon-session (legacy).
- `MCP_HOST=127.0.0.1`, `MCP_PORT=4500` — bind.
- `WARM_POOL_ENABLED=true` — pre-warm всех active аккаунтов на старте + фоновый keepalive (default on).
- `WARM_POOL_KEEPALIVE_SECONDS=60` — интервал между `get_me()` пингами warm-клиентов.

**HTTP / MCP API:**
- `GET /health` — exempt, returns `{ok: true}`.
- `POST /mcp` — streamable HTTP transport (FastMCP streamable_app).
- `GET /sse` / `POST /sse/messages` — SSE transport (FastMCP sse_app, messages path exempt).
- MCP tools (~30) — см. `_register_tools` (server.py:105). Channel-admin set: create_channel, invite_to_channel, promote_channel_admin, set_channel_photo, link_discussion, toggle_channel_forum, create_channel_topic.
- MCP tools registered in `_register_tools` (server.py:105+); channel-admin tools include `create_channel`, `promote_channel_admin`, `set_channel_photo` (server.py:567), `link_discussion` (server.py:591).

**Callbacks → agentflow-agents:**
- `POST /internal/tg-callbacks` (`agentflow-agents/src/routes/internal.ts:49`) — после получения нового сообщения через Telethon.

## Failure modes

| Симптом | Лог-строка для grep | Где починить |
|---|---|---|
| `401 invalid_token` от MCP | `mcp_auth_jwt_invalid` | `server.py:29` (MCPAuthMiddleware) |
| Session blob не расшифровался | `fernet_decrypt_failed` | `telethon_pool.py:39` (_decode_session) |
| Несколько параллельных вызовов на один аккаунт | `account_lock_timeout` | `telethon_pool.py:32` (per-account lock) |
| Pool переполнен | `telethon_pool_evict` (LRU eviction normal) | `telethon_pool.py:20` (max_size=32) |
| Warm-client упал на keepalive | `warm_pool_keepalive_failed` | `telethon_pool.py:180` (`_keepalive_loop`) |
| Warm не стартовал на boot | `warm_pool_bootstrap_failed` | `server.py:624` (lifespan) |
| Session мёртвая — `warm()` зашумел | `warm_authorize_failed` | `telethon_pool.py:111` (`warm`) |
| Warm пропустил аккаунт (нет session_blob) | `warm_pool_skip` | `telethon_pool.py:131` (`warm_all`) |
| Phone code expired | `phone_code_expired` | `_register_tools` (auth tools, server.py:105) |
| Pod restart between add-phone and confirm-code lost the flow (legacy) | `no pending login for this (owner, phone)` | FIXED: `state.py` `recover_pending` rebuilds from `pending_logins`. If still raised, the durable row was never written — check `persist_pending_failed`. |
| Durable pending-login write failed (disk hiccup) | `persist_pending_failed` | `state.py` `persist_pending` — best-effort, swallowed so the live in-memory login still works; only the restart-recovery path is lost. |
| Pending login recovered after restart | `pending_login_recovered` (info, normal) | `state.py` `recover_pending` — informational, confirms the durable path worked. |
| Callback to agentflow-agents 500 | `tg_callback_send_failed` | `routes/internal.ts:49` |
| `send_file` returns `error=invalid_base64` | `invalid_base64` (literal) | Caller passed non-b64 string. Fix the upstream — `tg.send_file` graph handler always reads via `code-exec.read_file_b64` which returns clean b64. |
| `send_file` returns `error=empty_payload` | `empty_payload` (literal) | Decoded to zero bytes. Source file was empty / pod path mismatch. Check upstream producer node output. |
| `send_file` returns `error=flood_wait, seconds=N` | `flood_wait` from `_structured_error` | Account-level rate limit. tg.send_file handler does NOT retry (idempotent=false) — operator must re-queue manually after the flood window. |
| `set_channel_photo` floods hard after ~10 edits in a burst | `caused by EditPhotoRequest` (Telethon `FloodWaitError`) | `EditPhotoRequest` is one of the most throttled MTProto writes. Bulk-setting avatars across many channels on ONE account trips a global ~700-900s wait after ~5 channels (×2 for channel+chat). Fix: pace to a handful per window and run a resumable driver that sleeps `FloodWaitError.seconds + buffer` and retries the same target. `SetDiscussionGroupRequest` shares the same per-account write budget — do photos and links in one paced pass, not two bursts. |
