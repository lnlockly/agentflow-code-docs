# God-file splits

## TL;DR
Four oversized files were broken into per-domain module folders, each fronted by
a **barrel** (the original file path or its `index`) that re-exports the same
public surface. The splits are **behavior-preserving** — pure reorganization, no
logic change — and every `import { … } from '<old path>'` call-site resolves
unchanged. If you `grep` for a symbol and land on a barrel re-export, follow it
into the matching module under the sibling folder.

## Data flow

These splits change **file topology only** — the runtime call graph is
identical. A symbol's resolution path gains one hop through the barrel:

```
import { createProjectForUser } from '.../services/projects.js'
   └─ services/projects.ts (barrel)  export { createProjectForUser } from './projects/bootstrap.js'
        └─ services/projects/bootstrap.ts   ← actual implementation
```

## DB / Env / API
- No new tables, env vars, routes, or MCP tools. Behavior-preserving.
- `schema.ts` split (#1105) is explicitly drift-test-clean — the Drizzle
  introspection drift test and `drizzle.config.ts` read the barrel unchanged.

## Failure modes
| Symptom | Log signature for grep | Where to fix |
|---|---|---|
| `grep` for a symbol lands on a re-export, not the impl | line is `export { X } from './<sub>/<mod>.js'` | follow the re-export into the sibling module folder |
| New import resolves `undefined` after a split | symbol not re-exported from the barrel (projects.ts uses an explicit list, not `export *`) | add the export to the relevant barrel (`projects.ts:2` / `flow-executor.ts:2`) |
| drizzle drift / migration runner can't find a table | a `schema/*.ts` module not re-exported from `schema.ts` | add `export * from './schema/<mod>.js'` to `db/schema.ts:1` |
