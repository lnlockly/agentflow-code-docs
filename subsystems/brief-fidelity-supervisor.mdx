# Brief-Fidelity Supervisor

## TL;DR

The supervisor runs **after** the bot smoke test returns `verdict=pass` (for tg_bot) or after the structural landing gate passes (for landing/spa/tg_profile_bundle). It extracts 3–5 keyword intents from the owner's brief via a cheap TEXT_SMALL call, then checks whether those keywords appear in the bot's reply transcript or the rendered HTML. If fewer than 40% match, a second LLM "judge" call makes the final call. A coder that ships a generic "/book" shell for an "AI Battle Royale" brief will now fail with `reason: brief_behavior_drift`.

Feature-flag gated: `BRIEF_FIDELITY_SUPERVISOR` in `feature_flags` table (default `false`).

## Data flow

```
Bot smoke test / landing gate
        │
        │  verdict=pass / validateLandingPreview ok
        ▼
checkBriefFidelity(brief, productKind, sampleBehaviorTranscript)
        │
        ├─ flag off (default) ──────────────────────▶ {ok:true}
        ├─ brief or sample empty ──────────────────▶ {ok:true}
        │
        ▼
extractIntents(brief)  [TEXT_SMALL, max_tokens=200]
  └─ returns 3-5 lowercase keywords
        │
        ▼
substring hit_rate = matches / total_intents
        │
        ├─ hit_rate >= 0.4 ────────────────────────▶ {ok:true}
        │
        ▼
llmJudge(intents, sample)  [TEXT_SMALL, max_tokens=10]
  └─ "match" | "drift" | "empty"
        │
        ├─ "match" ────────────────────────────────▶ {ok:true}
        │
        ▼
{ok:false, reason:"brief_behavior_drift"}
        │
  (tg_bot)                      (landing)
        │                             │
UPDATE projects                 return {pass:false}
  SET status='failed'             from gateLandingPreview
appendProjectEvent               (prevents done flip)
  kind='brief_fidelity_drift'
createSmokeFixTask
  (self-heal retry)
```

## Upstream prevention — coder-tg-bot brief-imperative guard

The supervisor is a *post-hoc* gate. Cheaper than catching drift after smoke is preventing it inside the coder prompt itself.

`presets/coder-tg-bot.json` opens with a **BRIEF IS LAW** section pinned to the top of the system prompt:

```
Your ONLY product spec is the brief below. Do not produce a generic
booking/appointment/assistant bot regardless of unclear brief. If brief
unclear — ask user for clarification, do NOT default. Read brief 3 times
before writing code.
```

Followed by a 5-step skill chain the agent must execute before any `code-exec.write_file`:

1. `read-brief-3x` — 3 passes, each extracting a different layer (gist → domain objects → actions).
2. `extract-intent-keywords` — 3-5 keywords pinned to the agent's Brief анализ block.
3. `verify-keywords-present-in-code` — `grep` the generated `backend/bot.py` for those keywords; zero hits = drift, rewrite.
4. `code` — write bot logic implementing those keywords.
5. `self-review-vs-brief` — re-read brief, sanity-check each requirement against code before REPLY.

Plus explicit `tg-visitka` template scoping: the `/book` calendar shell is allowed **only** for `kind=tg_profile_bundle`. All other kinds get a hard prohibition.

Unit tests in `tests/unit/coder-presets.test.ts` lock the guard string and skill chain so future refactors can't quietly cut them. If the supervisor still catches drift downstream, that means the upstream prompt was ignored or the brief was genuinely ambiguous — escalate, don't ship a shell.
