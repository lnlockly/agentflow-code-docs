# Device use-cases — recipes + cabinet picker

## TL;DR
Devices get real jobs via a "What should this device do?" picker on the device page.
The owner picks an **outcome**, not a raw prompt. Each outcome is a Goose recipe in the
fork (`agentflow-goose/recipes/devices/<id>.yaml`). Local desktop agents show the L*
catalog (leverages YOU — logged-in sessions/files), cloud pods show C* (leverages TIME —
always-on, scheduled). The picker dispatches through the existing device path with
`tool: 'agent_run_recipe'`; the goose device-bridge turns that into `goose run --recipe`
(or schedules cloud recipes by cron). Anything outbound is approval-gated by default.

## Data flow
```
device page → DeviceUseCasePicker (filters DEVICE_USE_CASES by hosted flag)
  → owner picks outcome + fills params
  → devicesApi.dispatchTask(id, { task:<title>, tool:'agent_run_recipe',
       scope:{ recipe:'l1-inbox-triage', params:{...}, cron?:'0 8 * * *' } })
  → POST /me/devices/:id/dispatch_task        (me-devices.ts, unchanged)
  → coder-shim / goose bridge: goose run --recipe recipes/devices/<id>.yaml --params k=v
       (cloud: manage_schedule with metadata.cron / scope.cron)
  → recipe runs with developer + computercontroller + af_* (stdio) + kwork-inbox exts
  → outbound steps pause for Telegram approval (draft → Saved Messages → wait 'ok')
```

## DB / Env / API
- Tables: none new. Uses the existing `user_devices` dispatch path.
- Dispatch: `POST /me/devices/:id/dispatch_task { task, tool:'agent_run_recipe',
  scope:{ recipe, params, cron? } }`. Tool name regex `^[a-z][a-z0-9_]*$`.
- Recipe LLM: `flow` via the platform gateway — `OPENAI_HOST=https://agentflow.website`,
  `OPENAI_BASE_PATH=/_agents/llm/v1/chat/completions`, owner `af_live_*` key. No
  hardcoded model.
- af_* extension (stdio): `node /opt/agentflow-mcp-server/dist/index.js` with
  `AGENTFLOW_API_KEY` / `AGENTFLOW_BASE_URL=https://agentflow.website/_agents`. Built by
  the agentflow-mcp-server agent; consumed here, not edited.
- kwork-inbox (streamable_http): `/internal/mcp/kwork-inbox` (`list_dialogs`,
  `get_dialog`, `send_message`) — internal-only host.

## Approval gate
No interactive `request_approval` MCP tool exists in af_*. Outbound recipes implement
approval as a Telegram round-trip: `af_telegram_whoami` → send the `DRAFT →` preview to
the owner's Saved Messages → poll `af_telegram_messages` for `ok`/`отправь`/`send` (or an
edit) up to `approval_wait_seconds` → send only on approval. `manifest.json` marks these
`approval: true`; the picker badges them. Verified: L1 drafted a reply, sent it for
approval, and did NOT auto-send when the window elapsed.

## Failure modes
| Symptom | Log signature for grep | Where to fix |
|---|---|---|
| Recipe rejects a declared param | `Unnecessary parameter definitions: <key>` | every declared param must be `{{used}}` in the prompt; cron is `metadata.cron`, not a param |
| Recipe rejects an extension URI var | `Missing definitions for parameters in the recipe file: <key>` | declare any `{{var}}` used in an extension `uri` as a parameter |
| Memory step errors mid-run | `AgentFlow service error (HTTP 500)` (af_recall/af_remember) | af_* memory needs a real device id, not `default`; recipes treat it as non-blocking |
| Kwork source skipped | `Failed to start extension 'kwork_inbox' ... HTTP 404` | kwork-inbox is internal-only; the public host 404s — bridge reaches it on the internal net |
| Dispatch refused | `device_paused` (409) / `not_found` (404) | resume the device / bring it online before running a use-case |
