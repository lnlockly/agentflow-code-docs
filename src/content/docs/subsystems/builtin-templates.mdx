# Builtin templates registry

## TL;DR

`/me/project-foundations/recommend` returns a `builtin[]` array straight from
a module-level constant — no DB, no Redis, no LLM. The modal renders these
cards above the AI-scored GitHub-Search candidates so the owner can pick a
known-good starter instantly, even when the ranker or GitHub Search is down.
When the caller passes `kind_hint`, matching entries are pushed to slot 0
so a Telegram-bot brief doesn't see a landing card first.

### Why these (not the obvious choices)

The previous registry had four broken/suboptimal entries that this revision
fixed (PR `feat/complex-projects-e2e`):

- `lnlockly/agentflow-tg-bot-starter` → was 404 not found upstream in 2026-05-26.
  Created and populated 2026-05-27 (aiogram 3 + Procfile). 2026-05-28: switched
  back to our starter and away from `wakaree/aiogram_bot_template` because
  the wakaree pyproject.toml has `project.authors[0]` as a string, not an
  object — the LLM dep-installer runs `pip install -e .` and crashes before
  aiogram boots. Bot @yogabook2_bot (project 1564) was the live repro.
- `vitejs/vite` → the Vite framework monorepo (~30 MB checkout), not a
  scaffold. Daemons OOM during install. Swapped to a 70 KB single-stack
  starter.
- `fastify/fastify` → the Fastify framework monorepo, not a runnable
  starter. Swapped to a TS scaffold.
- `Telegram-Mini-Apps/telegram-apps` → renamed to `tma.js`, a multi-package
  monorepo. Swapped to the org's official `reactjs-template`.

## Data flow

```
client (modal) ──POST /me/project-foundations/recommend { brief, kind_hint }──▶ projects.ts:733
                                                                                  │
                                                                                  ├─ allBuiltin   = listBuiltinTemplates()        ← module const, no I/O
                                                                                  ├─ if kind_hint: matched = filter(kind == hint)
                                                                                  │                builtin = [...matched, ...rest]
                                                                                  ├─ result      = recommendProjectFoundations()   ← AI + GitHub Search
                                                                                  └─ response    = { ok:true, builtin, ...result }
client (modal) ──renders builtin cards FIRST, then result.candidates──▶
```

## DB / Env / API

- Tables: none — registry is in-process.
- Env: none. Optional `GITHUB_TOKEN` used by the network resolve test to avoid
  unauthenticated rate-limit (60 req/h per IP).
- Routes: `POST /me/project-foundations/recommend` reads it. `POST /me/projects`
  does NOT — that path goes through `pickBestTemplateForBrief` (GitHub
  Search + AI rank) regardless of builtin.
- MCP tools: none.

## Failure modes

| Symptom | Log signature for grep | Where to fix |
|---|---|---|
| Modal shows aiogram repo card → click → daemon clone 404s | `template_pick_failed` in `projects.ts:843` | Update `builtin-templates.ts:46` entry; the daemon honours `template_repo_full` from the AI pick, not from builtin — so 404 here means the AI ranker scored a stale repo. |
| `kind_hint=tg_bot` modal still shows landing first | route doesn't propagate `kind_hint` — assert with curl: `POST /me/project-foundations/recommend {brief, mode:"github_first", kind_hint:"tg_bot"} ⇒ builtin[0].kind === "tg_bot"` | `projects.ts:740-770` ordering block. |
| Network test fails with 403 | `github_search_failed status=403` | Hit rate-limit; export `GITHUB_TOKEN` or rerun with `SKIP_NETWORK_TESTS=1`. |
| Builtin monorepo picked → OOM on `pnpm install` | `pod_oom_killed` event on the project pod | Registry entry must be a single-app repo (< 5 MB). Verify with `curl -s api.github.com/repos/<repo> \| jq .size`. |
