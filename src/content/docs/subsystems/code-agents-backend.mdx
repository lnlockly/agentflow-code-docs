# Code-agent backend registry

## TL;DR

The hosted daemon used to hardcode `aider` in `_default_spawn_aider`.
After PR `feat/swappable-code-agents-backend` the spawn delegates to a
`CodeAgentBackend` looked up by slug, so flipping the editor between
`aider`, `opencode`, or a generic CLI is one env var
(`CODE_AGENT_BACKEND`). Adding a new backend = one new file in
`code_agents/` + one registry line; `agent_brief.py` never changes.

## Data flow

```
agent_dev_brief(brief, slug, project_id, ...)
    │
    ▼
_default_spawn_aider(brief, cwd, env, opencode_bin=, backend=)
    │
    ▼
_resolve_backend_for_spawn(backend, aider_bin, opencode_bin)
    │  precedence: explicit instance > slug arg > legacy opencode_bin
    │             > CODE_AGENT_BACKEND env > AiderBackend default
    ▼
backend.build_command(brief, project_dir, api_key, api_base, model)
    │  returns (argv, env_overrides)
    ▼
spawn_env.update(env_overrides)
subprocess.Popen(argv, env=spawn_env, cwd=project_dir, ...)
```

## DB / Env / API

- **Env (daemon pod):**
  - `CODE_AGENT_BACKEND` — `aider` (default) / `opencode` / `cli`
  - `CODE_AGENT_CLI_CMD` — template string for `cli` backend, supports
    `{brief}` `{project_dir}` `{api_key}` `{api_base}` `{model}` slots.
    `{brief}` MUST be quoted because `shlex.split` runs on the rendered
    template.
  - `CODE_AGENT_CLI_ENV` — optional `KEY=VAL;KEY=VAL` extra env. Same
    slot substitution.
  - `AF_API_KEY` — owner-key for the AgentFlow gateway, layered onto
    `OPENAI_API_KEY` by the aider + opencode backends.
  - `AF_API_URL` — normalised to `…/_agents` and used as the OpenAI
    base.
- **No DB tables touched.**
- **No new API routes.** Existing `agent_dev_brief` MCP tool is the
  only public surface.

## Flipping the backend in production

Edit `agentflow-agents/k8s/agentflow-agents-env` secret (the daemon
inherits its env from the agents pod manifest):

```yaml
data:
  CODE_AGENT_BACKEND: opencode      # base64-encoded in the real secret
```

then `kubectl rollout restart deploy/agentflow-agents`. New daemons
spawned for new projects pick up the change; in-flight projects keep
running whatever backend they started with.

## Adding a new backend (eg Continue)

1. `code_agents/continue_backend.py` — subclass `CodeAgentBackend`,
   implement `build_command` + `healthcheck`. Pin `slug = "continue"`.
2. `code_agents/__init__.py` — add `"continue": ContinueBackend` to
   `_REGISTRY`.
3. Ship the binary in the daemon image (eg `docker/Dockerfile.coder`).
4. Set `CODE_AGENT_BACKEND=continue` in the daemon env.

`agent_brief.py` is not modified.

## Failure modes

| Symptom | Log signature for grep | Where to fix |
|---|---|---|
| Spawn returns `backend_unconfigured` | `[code-agent:cli] starting cmd=<empty>` + `CODE_AGENT_CLI_CMD required` | Set `CODE_AGENT_CLI_CMD` or change `CODE_AGENT_BACKEND` |
| Spawn returns `backend_unconfigured` with `unknown code agent backend` | `unknown code agent backend: 'foo'` | Typo in `CODE_AGENT_BACKEND`; valid slugs in error message |
| Brief got word-split into many argv slots | `shlex` split on whitespace in rendered template | Quote `'{brief}'` in `CODE_AGENT_CLI_CMD` |
| Aider hits gateway 401 | `OPENAI_API_KEY` missing in spawn env | `AF_API_KEY` env not injected into daemon pod |
