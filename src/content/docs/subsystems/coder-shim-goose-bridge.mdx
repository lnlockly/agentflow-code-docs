# coder-shim — Goose device-bridge

## TL;DR
Master-plan v3 replaces the daemon's opencode/aider coder subprocess with
**Goose** (`block/goose`, forked as `lnlockly/agentflow-goose`). `coder-shim` is the
thin device-bridge that speaks AgentFlow's existing devices-ws protocol on one side
and runs `goose run` on the other, so the backend (`devices-ws.ts`) and ~20 cabinet
pages stay unchanged. Phase-0 spike verified: goose builds brief-derived files,
serves over HTTP, ~111 MiB peak RSS (`plans/autonomous/_goose-spike.md`). Opt-in via
`FF_DAEMON_IMAGE` — when unset the resolver keeps the coder image (reversible).

Rollout is **per-device**, not global. A device created with `template:'goose'`
runs the coder-shim image deterministically (the resolver checks the template
before the `FF_DAEMON_IMAGE` override), so one isolated canary can be verified
without flipping the global default for live users. Other templates are
untouched; delete the goose device → the runtime is gone.

**tg_bot runtime (PR feat/coder-shim-tgbot-runtime):** a `tg_bot` project is no
longer build-only — but the platform does NOT run pip/python. **GOOSE installs
the deps and launches the bot itself**, as part of its coder task, the same way
it builds + serves an HTTP app while the platform only probes the port (owner
directive 2026-05-30: the agent does the work, not the platform). The split:
- **Image** ships python3 + a prebuilt aiogram venv (`/opt/botvenv`) with its bin
  PREPENDED to `PATH`, so goose's plain `pip install -r requirements.txt` +
  `python bot.py` resolve to the venv (pip can write — no PEP-668; install is a
  fast no-op when aiogram is present).
- **Platform** injects `BOT_TOKEN` (+ `BOT_USERNAME`/`OWNER_TG_ID`) into goose's
  env (`pipeline.ts` step 2) so goose can write `.env`; it does not write the
  file or launch anything.
- **Goose** (the tg_bot branch of `buildCoderPrompt`) fills the handlers, writes
  `.env` from `$BOT_TOKEN`, `pip install`s, launches `nohup python bot.py &`
  DETACHED (survives the goose session, keeps polling), and self-verifies via
  `pgrep` + `getMe`.
- **Platform probe** (`tg-runtime.ts` `verifyTgBot`, step 4t) gates promotion: a
  `python *.py` process goose detached must be running in the workspace AND
  Telegram `getMe` must validate the token (yielding the AUTHORITATIVE
  `bot_username`). Fail-closed — `bot_token_missing` / `bot_not_running` /
  `getme_failed` → `ok:false`, so a bot goose did not actually launch is `failed`,
  never a silent `running`. Mirrors `probePort` for the HTTP path.

The detached bot keeps polling for the pod lifetime (the daemon pod is
long-lived); a dedicated bot-runtime pod is a follow-up (a build pod is not a
long-lived service host).

The shim exposes **two** direct-tools: `agent_dev_brief` (project coder) and
`agent_run_recipe` (device use-cases — the cabinet "what should this device do?"
picker). `agent_run_recipe` runs a bundled Goose recipe (`recipes/devices/<id>.yaml`)
immediately, or schedules it when a `cron` is supplied (cloud recipes like C2
morning-digest). Scheduling registers with `goose schedule add` for list
visibility AND — under the `FF_BRIDGE_SCHEDULER` flag — with an **in-process
cron in the long-lived bridge** (`scheduler.ts`) that actually FIRES the recipe
on each due minute with its persisted params (a headless pod has no goose
scheduler daemon, so register-only left `Last Run: Never`; PR #1027). The recipe
manifest is the allowlist + the injection boundary.

## DB / Env / API
- Tables: none new. Consumes `projects` via `/internal/projects/:id/clone-status`.
- Per-project DB (step 4a-db): `DATABASE_URL` is **injected by the pipeline at
  runtime**, not a static secret — `postgres://postgres@127.0.0.1:<dbPort>/postgres?sslmode=disable`
  pointing at an embedded **PGlite** (Postgres-in-WASM, file-backed at
  `/workspace/<slug>/.pglite-data`) served over a TCP socket by `pglite-launcher.js`.
  The pod can't `apt install postgres` and we keep everything on our own infra
  (no external managed DB), so this embedded path is the chosen default.
  Deps `@electric-sql/pglite` + `@electric-sql/pglite-socket` ship in the image.
- **Durability (owner decision 2026-05-30 — PGlite STAYS, durable via PVC; no
  switch to cluster-PG):** `.pglite-data` lives under `/workspace`, which is the
  STS `volumeClaimTemplates` 10Gi local-path PVC (`me-hosted-devices.ts`
  `renderDaemonManifest`), so a project's data **survives pod restart / image
  roll / reschedule** — the PVC stays bound and `DbSupervisor.ensureAll()`
  re-spawns PGlite on boot against the same data dir. The supervisor's
  keep-alive (PR #1033) is the accepted permanent runtime cost of this model.
  Data is lost only if the PVC itself is deleted (project teardown).
- Env (pod side, all already on the daemon pod): `AF_API_KEY`, `AF_API_URL`
  (default `https://agentflow.website`), `AF_DEVICE_ID`, `AF_DEVICE_TOKEN`,
  `AF_ENROLLMENT_TOKEN`, `AF_INTERNAL_API_SECRET`, `GOOSE_MODEL` (default `flow`),
  `GOOSE_MAX_TURNS`, `GOOSE_TIMEOUT_MS`, `GOOSE_DISABLE_KEYRING=1`, `WORKSPACE_ROOT`,
  `RECIPES_DIR` (default `/app/recipes/devices` — the bundled manifest + recipe yaml),
  `BOT_VENV` (default `/opt/botvenv` — the prebuilt python venv with aiogram +
  python-dotenv; its bin is on `PATH` so goose's `python`/`pip` resolve to it).
  For a tg_bot scope the pipeline injects `BOT_TOKEN` (+ `BOT_USERNAME`,
  `OWNER_TG_ID` when set) into goose's env so goose writes `.env` + `bot.py`
  reads the token. `OWNER_TG_ID` gates the bot's `/admin` panel; it is optional —
  the user-facing `/start`/`/help`/`/faq`/`/order` handlers work without it.
- Env (server side): `FF_DAEMON_IMAGE` — `goose` → coder-shim image; full ref →
  verbatim; unset → coder (2026-05-28 hotfix path). **GLOBAL — do not flip in prod
  until the matrix is green.**
- Env (pod side): `FF_DB_SUPERVISOR` — default ON; set to `0`/`false`/`no`/`off`
  to disable the embedded-DB keep-alive supervisor (`db-supervisor.ts`). When on
  (the default), each project's PGlite is respawned if it dies and re-hydrated on
  a pod restart, so a DB-backed SERVED app keeps persisting. Reversible; no-op
  when no project on the pod provisioned a DB.
- Env (pod side): `FF_BRIDGE_SCHEDULER` — `1`/`true`/`yes` arms the in-process
  recipe scheduler (`scheduler.ts`) that ACTUALLY fires scheduled recipes (a
  headless pod has no goose scheduler daemon). Off by default → the bridge only
  calls `goose schedule add` (register-only, never fires) — the legacy path,
  byte-for-byte. ISOLATED per-pod flag; set it on one canary device to verify,
  do not flip it fleet-wide until the matrix row is green.
- Env (pod side): `AGENTFLOW_API_KEY` / `AGENTFLOW_BASE_URL` — the recipe
  `agentflow` stdio extension's `env_keys`. The bridge's `recipeEnv()` injects
  them from `AF_API_KEY` + `<apiUrl>/_agents` when not already set on the pod, so
  the bundled `/opt/agentflow-mcp-server` extension starts and outbound steps
  send. `AGENTFLOW_API_KEY` MUST be an `af_live_*` token or the MCP server
  refuses to start. The extension resolves its deps via a `node_modules` symlink
  adjacent to the MCP dir (`/opt/agentflow-mcp-server/node_modules ->
  /app/node_modules`, PR #1029) — **NOT** `NODE_PATH`, which the ESM loader
  ignores (the #1027 bug: `ERR_MODULE_NOT_FOUND @modelcontextprotocol/sdk`).
- Env (server side): `FF_GOOSE_CANARY` — `1`/`true`/`yes` enables provisioning
  `template:'goose'` hosted devices (the isolated per-device canary). When unset,
  `POST /me/hosted-devices {template:'goose'}` returns 403 `goose_canary_disabled`.
  This gate only controls *creating new* goose devices; `resolveDaemonImage` keys
  off the stored row, so an already-provisioned goose device keeps its image even
  if the flag is later unset.
- Env (server side): `FF_BUILD_CODER` — `goose` routes **project builds** onto the
  goose coder-shim instead of the legacy aider coder, WITHOUT a global
  `FF_DAEMON_IMAGE` flip (computer-use device provisioning stays on coder/desktop).
  Read by `resolveBuildCoderTemplate()` in `project-clone.ts`. When `=goose`,
  `triggerProjectClone` picks a daemon with `template='goose'` (never the user's
  coder computer-use daemon) and, if none exists, provisions a dedicated goose
  build-daemon on demand. Unset/any-other value → builds keep the legacy `coder`
  daemon (reversible). Scoped to the build path only. Pairs with the
  `provisionDaemonOnDemand` fallback (warm-pool-independent).
- API: `POST /me/hosted-devices {kind:'daemon', template:'goose'}` → goose device
  (canary-gated). All other create-path behaviour is unchanged.
- WS: connects to `wss://<AF_API_URL host>/_agents/_devices/connect` with
  `x-api-key` / `x-device-id` / `x-device-secret` (or `x-enrollment-token` on
  first run). The `/_agents` prefix is mandatory — the central ingress routes
  `/_agents(/|$)(.*)` to the agentflow-agents service and strips the prefix, so
  the server's mount at `/_devices/connect` (`devices-ws.ts:228`) only sees a
  prefixed public URL. A bare `wss://.../_devices/connect` falls through to the
  landing proxy, which answers the upgrade with HTTP 200 and no `101` — the shim
  loops `reconnecting in 4.0s` and the device stays `offline`.
- LLM: routes through the platform gateway `flow`→codex.sale; model is the alias
  `flow`, never a concrete id (gateway `pickFlowUpstream` resolves it).
- Goose source: forked at `lnlockly/agentflow-goose`. Image bundles goose via the
  Dockerfile `GOOSE_DOWNLOAD_BASE`/`GOOSE_RELEASE_TAG` build-args (defaults to
  upstream `stable` until the fork cuts a release).

## Edit channel (goose projects)
Goose-built projects are iterated from the cabinet chat (`POST /me/projects/:id/daemon-chat`). For a goose project (one with `home_device_id` set) the turn does NOT run the legacy Claude + code-exec loop — it re-dispatches the edit as another goose run in the SAME workspace:

```
POST /me/projects/:id/daemon-chat { text: "<edit instruction>" }
  → runProjectDaemonTurn → (home_device_id set) → runGooseEditTurn
      triggerProjectClone(id, { editText })   // reuses the dispatch machinery
        scope { slug, project_id, brief: editText, port, kind, edit:true }
        flips project running → provisioning (so completion is detectable)
       │ WS task_dispatch agent_dev_brief (edit:true)
       ▼
   coder-shim runCoderTask (edit branch)
        SKIP clone (workspace exists) — edits are incremental over prior state
        goose run -t <buildCoderPrompt({edit:true})>  — the INCREMENTAL edit
          prompt (read existing files → apply only the change → preserve the
          rest), NOT the from-scratch BUILD prompt; same --system guardrail
        restore PROTECTED_CONFIG_FILES, install (devDeps forced, #981),
          build-validate + self-heal
        killProjectDevServer(projectDir)  → startDevServer (next start)
       │ clone-status { ok, port_reachable } → re-promote running/failed
       ▼
   runGooseEditTurn polls projects.status until ≠ provisioning, streams
     progress + the refreshed preview_url over SSE.
```

Each edit accumulates over the last (same `/workspace/<slug>`), so a sequence
"change the headline → add a reviews block → add pricing → change colours"
keeps prior changes. This depends on the `{edit:true}` prompt branch: the
from-scratch BUILD prompt made goose regenerate `page.tsx` from the template
default (re-emitting demo content + unfilled `data-slot` markers, wiping the
brief) — the incremental edit prompt tells it to read + modify in place and
preserve everything else. A failed edit (`build_failed`) leaves the previous
working preview up (the dev server is only killed AFTER the build gate passes).

### Generic chat / triage path (not just daemon-chat)
The SSE `daemon-chat` route is the streaming surface, but the cabinet also posts
plain chat through `POST /me/projects/:id/messages` (route handler) and the
suggestion-approve flow goes through `enqueueOwnerMessage` (pipeline). For a
goose project those legacy paths had NO canonical coder in plan history, so
their chat-iterate / maestro triage was a dead no-op
(`[chat-iterate] no canonical coder for kind=… → falling back to legacy path`
→ maestro `no coder found in plan history`) — a plain chat message did nothing.

Both now short-circuit to the goose edit path via a shared helper
`dispatchGooseEdit` in `project-clone.ts`:

```
POST /me/projects/:id/messages   (or enqueueOwnerMessage)
  → dispatchGooseEdit({ projectId, homeDeviceId, text })
      home_device_id set AND text ≥ 20 chars (OWNER_MESSAGE_SUBSTANTIAL_MIN_CHARS)?
        → triggerProjectClone(id, { editText })   // same dispatch as runGooseEditTurn
          emits coder_dispatched{mode:'goose_edit'} + info; returns { routed:true }
        → handler returns { ok:true, mode:'goose_edit' }
      else → { routed:false } → caller continues its existing routing
```

Short / non-actionable messages (greetings, "ok") stay below the threshold and
fall through unchanged. The helper is fire-and-return (non-blocking): the
clone-status callback re-promotes the project and the chat UI polls events — it
does NOT block on the 7-min build the way the SSE `runGooseEditTurn` poller does.

Files: `agentflow-agents/src/services/project-daemon.ts` `runGooseEditTurn`;
`agentflow-agents/src/services/project-clone.ts` `triggerProjectClone({editText})` + `dispatchGooseEdit`;
`agentflow-agents/src/routes/projects.ts` `/me/projects/:id/messages` (goose short-circuit);
`agentflow-agents/src/services/projects-pipeline.ts` `enqueueOwnerMessage` (goose short-circuit);
`agentflow-agents/src/coder-shim/pipeline.ts` edit branch;
`agentflow-agents/src/coder-shim/dev-server.ts` `killProjectDevServer`.

## Relationship to the in-daemon goose backend
There are two ways to run goose for the coder, and they coexist:
- **In-place (`CODE_AGENT_BACKEND=goose`)** — flips the engine inside the
  existing Python daemon's `agent_dev_brief`, no new image. See
  [Code-agent backend registry](/subsystems/code-agents-backend). Smallest change.
- **coder-shim (this page)** — a standalone Node bridge + image that drops the
  Python daemon for the coder slice entirely. The master-plan v3 target, sourced
  from the `lnlockly/agentflow-goose` fork.

Both speak the same `agent_dev_brief` dispatch contract and the same
`/internal/projects/:id/clone-status` callback, so the backend does not care
which one a given pod runs.
