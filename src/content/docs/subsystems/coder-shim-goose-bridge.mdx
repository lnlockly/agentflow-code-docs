# coder-shim — Goose device-bridge

## TL;DR
Master-plan v3 replaces the daemon's opencode/aider coder subprocess with
**Goose** (`block/goose`, forked as `lnlockly/agentflow-goose`). `coder-shim` is the
thin device-bridge that speaks AgentFlow's existing devices-ws protocol on one side
and runs `goose run` on the other, so the backend (`devices-ws.ts`) and ~20 cabinet
pages stay unchanged. Phase-0 spike verified: goose builds brief-derived files,
serves over HTTP, ~111 MiB peak RSS (`plans/autonomous/_goose-spike.md`). Opt-in via
`FF_DAEMON_IMAGE` — when unset the resolver keeps the coder image (reversible).

Rollout is **per-device**, not global. A device created with `template:'goose'`
runs the coder-shim image deterministically (the resolver checks the template
before the `FF_DAEMON_IMAGE` override), so one isolated canary can be verified
without flipping the global default for live users. Other templates are
untouched; delete the goose device → the runtime is gone.

The shim exposes **two** direct-tools: `agent_dev_brief` (project coder) and
`agent_run_recipe` (device use-cases — the cabinet "what should this device do?"
picker). `agent_run_recipe` runs a bundled Goose recipe (`recipes/devices/<id>.yaml`)
immediately, or registers it with Goose's scheduler when a `cron` is supplied
(cloud recipes like C2 morning-digest). The recipe manifest is the allowlist + the
injection boundary.

## Data flow
```
backend project-clone.ts
  dispatchOrQueueDeviceTask({ tool:'agent_dev_brief', scope:{template_repo_full,
    slug, project_id, brief, port, kind, bot_token?} })
   │ WS task_dispatch   (devices-ws protocol — UNCHANGED)
   ▼
coder-shim bridge.handleCoderDispatch
   │  validateScope → runCoderTask:
   │    git clone --depth 1 -- <repo> /workspace/<slug>
   │    write ~/.config/goose/config.yaml (provider=openai, model=$GOOSE_MODEL,
   │       OPENAI_HOST=$AF_API_URL, OPENAI_BASE_PATH=_agents/llm/v1/chat/completions,
   │       GOOSE_MODE=auto)
   │    goose run --with-builtin developer --no-session --max-turns N
   │         --system <buildCoderSystemPrompt> -t <buildCoderPrompt(brief,kind,port)>
   │      (--system = headless guardrail: never end the turn after only planning,
   │       keep editing + grep-verify before finishing; -t = imperative
   │       "implement the brief by EDITING the cloned files at CWD". Without the
   │       --system guardrail the model plans, says "ready to proceed" and exits 0
   │       with the workspace untouched — headless `goose run` has no second turn)
   │    startDevServer (HTTP kinds): read package.json, pick pm from lockfile,
   │       <pm> install, then spawn `<pm> run dev|start --port <port> --host
   │       0.0.0.0` DETACHED (unref) so it keeps serving — headless `goose run`
   │       exits after editing and leaves NO running server. install_failed /
   │       dev_spawn_failed short-circuit to ok:false (project → failed + tail).
   │    probe 127.0.0.1:<port>  (HTTP kinds; skipped for tg_bot)
   │  POST /internal/projects/:id/clone-status {ok, port, port_reachable,
   │       dev_pid, package_manager, ...}
   ▼  WS task_complete  (or task_error)
backend internal.ts clone-status → flips status, wires Service/Ingress, preview_url
```

### agent_run_recipe (device use-cases)
```
cabinet picker (PR #543) → POST /me/devices/:id/dispatch_task
  { tool:'agent_run_recipe', scope:{ recipe:<id>, params:{k:v}, cron? } }
   │ WS task_dispatch  (devices-ws, UNCHANGED)
   ▼
coder-shim bridge.handleRecipeDispatch
   │  loadManifest(/app/recipes/devices) → validateRecipeDispatch:
   │    recipe ∈ manifest allowlist + path-safe id?
   │    params ∩ recipe's declared param keys (drop the rest)?
   │    cron valid (5/6 fields, digits + */,- only) → normalize 5→6?
   │  ensureGooseConfig (provider=openai, model=$GOOSE_MODEL=flow)
   │  cron set?
   │    YES → goose schedule add --schedule-id <dev>-<id> --cron <6f> --recipe-source <file>
   │          → task_complete "scheduled: <id> (<schedule-id>)"
   │    NO  → goose run --no-session --max-turns N --recipe <file> --params k=v ...
   │          → task_complete (tail) / task_error
   ▼  WS task_complete / task_error  (no clone-status — a recipe is not a build)
```
Injection boundary: the recipe id is the only thing that becomes a file path
(`recipes/devices/<id>.yaml`, id matched `^[a-z0-9-]+$` AND found in the manifest);
params ride as single argv elements (`--params k=v`), never a shell string; cron is
charset-validated before reaching the scheduler.

## DB / Env / API
- Tables: none new. Consumes `projects` via `/internal/projects/:id/clone-status`.
- Env (pod side, all already on the daemon pod): `AF_API_KEY`, `AF_API_URL`
  (default `https://agentflow.website`), `AF_DEVICE_ID`, `AF_DEVICE_TOKEN`,
  `AF_ENROLLMENT_TOKEN`, `AF_INTERNAL_API_SECRET`, `GOOSE_MODEL` (default `flow`),
  `GOOSE_MAX_TURNS`, `GOOSE_TIMEOUT_MS`, `GOOSE_DISABLE_KEYRING=1`, `WORKSPACE_ROOT`,
  `RECIPES_DIR` (default `/app/recipes/devices` — the bundled manifest + recipe yaml).
- Env (server side): `FF_DAEMON_IMAGE` — `goose` → coder-shim image; full ref →
  verbatim; unset → coder (2026-05-28 hotfix path). **GLOBAL — do not flip in prod
  until the matrix is green.**
- Env (server side): `FF_GOOSE_CANARY` — `1`/`true`/`yes` enables provisioning
  `template:'goose'` hosted devices (the isolated per-device canary). When unset,
  `POST /me/hosted-devices {template:'goose'}` returns 403 `goose_canary_disabled`.
  This gate only controls *creating new* goose devices; `resolveDaemonImage` keys
  off the stored row, so an already-provisioned goose device keeps its image even
  if the flag is later unset.
- API: `POST /me/hosted-devices {kind:'daemon', template:'goose'}` → goose device
  (canary-gated). All other create-path behaviour is unchanged.
- WS: connects to `wss://<AF_API_URL host>/_agents/_devices/connect` with
  `x-api-key` / `x-device-id` / `x-device-secret` (or `x-enrollment-token` on
  first run). The `/_agents` prefix is mandatory — the central ingress routes
  `/_agents(/|$)(.*)` to the agentflow-agents service and strips the prefix, so
  the server's mount at `/_devices/connect` (`devices-ws.ts:228`) only sees a
  prefixed public URL. A bare `wss://.../_devices/connect` falls through to the
  landing proxy, which answers the upgrade with HTTP 200 and no `101` — the shim
  loops `reconnecting in 4.0s` and the device stays `offline`.
- LLM: routes through the platform gateway `flow`→codex.sale; model is the alias
  `flow`, never a concrete id (gateway `pickFlowUpstream` resolves it).
- Goose source: forked at `lnlockly/agentflow-goose`. Image bundles goose via the
  Dockerfile `GOOSE_DOWNLOAD_BASE`/`GOOSE_RELEASE_TAG` build-args (defaults to
  upstream `stable` until the fork cuts a release).

## Relationship to the in-daemon goose backend
There are two ways to run goose for the coder, and they coexist:
- **In-place (`CODE_AGENT_BACKEND=goose`)** — flips the engine inside the
  existing Python daemon's `agent_dev_brief`, no new image. See
  [Code-agent backend registry](/subsystems/code-agents-backend). Smallest change.
- **coder-shim (this page)** — a standalone Node bridge + image that drops the
  Python daemon for the coder slice entirely. The master-plan v3 target, sourced
  from the `lnlockly/agentflow-goose` fork.

Both speak the same `agent_dev_brief` dispatch contract and the same
`/internal/projects/:id/clone-status` callback, so the backend does not care
which one a given pod runs.
