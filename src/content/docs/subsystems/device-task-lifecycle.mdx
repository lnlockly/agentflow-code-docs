# Device Task Lifecycle

## TL;DR
The owner (or an MCP caller) POSTs `dispatch_task` against a registered device. The agentflow-agents backend either sends the task live over the device's WebSocket (when a live `conn` is held on the receiving pod) or persists it as `queued` in `device_tasks` for the daemon to drain on its next `hello` handshake. Daemon runs the LLM loop, publishes `task_action` frames per step, and finishes with `task_complete` (or `task_error`). The terminal frame is what flips `device_sessions.status` and writes `tokens_used` + `cost_usd`.

## Data flow

```
client                backend (multi-pod)        device WS / daemon          DB
  │                         │                            │                    │
  │ POST dispatch_task ───→ │                            │                    │
  │                         │ getConnection(id)?         │                    │
  │                         │   yes → dispatchLiveDeviceTask                  │
  │                         │     ├─ INSERT device_sessions (active) ─────→  │
  │                         │     ├─ INSERT device_tasks (dispatched) ────→  │
  │                         │     ├─ recordTaskSession(taskId, sessionId)    │
  │                         │     └─ ws.send({type:'task_dispatch',...}) →  │
  │ ← 202 { task_id, session_id, queued:false }                              │
  │                         │   no  → INSERT device_tasks (queued) ──────→  │
  │ ← 202 { task_id, session_id:null, queued:true }                           │
  │                         │                            │                   │
  │                         │ hello frame from daemon ←  │                   │
  │                         │   drainAndDispatchQueuedTasks                  │
  │                         │   SELECT WHERE status=queued                   │
  │                         │   FOR EACH row: ws.send(task_dispatch)   →    │
  │                         │   UPDATE → status=dispatched ──────────────→  │
  │                         │                            │                   │
  │                         │   task_action frames    ← │                   │
  │                         │   persistTaskRow → resolveTaskSession (cache hit) → INSERT device_action_log
  │                         │                            │                   │
  │                         │   task_complete         ← │                   │
  │                         │   persistTaskRow → insertTaskActionLog (kind=task_complete, tokens_used, cost_usd)
  │                         │   closeTaskSession → UPDATE device_sessions SET status='completed', tokens_used=N, cost_usd=$
  │                         │   finalizeDeviceTask → UPDATE device_tasks SET status='done'
```

## DB / Env / API

**Tables**
- `device_sessions` — one row per task run. `status ∈ {active, completed, aborted}`. `tokens_used` and `cost_usd` set only on `task_complete` frame.
- `device_tasks` — one row per dispatch. `status ∈ {queued, dispatched, done, failed}`. Queued rows drained by `drainAndDispatchQueuedTasks` on the next daemon `hello`.
- `device_action_log` — per-tool-call audit row. `kind` column discriminates `tool_call` / `task_action` / `task_complete` / `task_error`. The full daemon-emitted payload is in `args` JSONB.
- `user_devices` — registration + `last_seen` heartbeat. `last_seen` drives `shouldQueueForOfflineDevice` (60s trust window).

**Routes**
- `POST /me/devices/:id/dispatch_task` — body `{ task: string, scope?: object }` → 202 `{ ok, task_id, session_id, queued? }`. `queued:true` means daemon WS was not local to this pod; row sits in `device_tasks` until drained.
- `POST /me/devices/:id/cancel_task` — body `{ task_id? }` → 202.
- `GET /me/devices/:id/sessions` — paginated list with tokens + cost.
- `GET /me/devices/:id/sessions/:sid/log` — per-tool audit trail.
- `GET /me/devices/:id` — current presence (status, last_seen, scope).
- `wss://agentflow.website/_agents/_devices/connect` — daemon WS. Auth via `device_id + device_secret`. Handles `hello`, `tool_call_result`, `task_action`, `task_complete`, `task_error`, `subscribe_stream`, `stream_frame`.

**Env**
- Daemon: `LOOP_MAX_USD` (default 2.0), `LOOP_MAX_STEPS` (default 50), `FF_BOT_AUTO_TEST`, `ANTHROPIC_API_KEY` (east-api-3).
- Backend: `QUEUE_TRUST_WINDOW_MS=60000` (presence window for queue-vs-409 decision).

**Scope precedence** (daemon-side):
1. Per-task scope from `dispatch_task` body (highest)
2. `~/.agentflow/computer-scope.toml` base (loaded once at daemon boot)
3. Hard-deny paths (`~/.ssh`, `~/.config`, `~/Library/Keychains`, `~/.aws`, `~/.gnupg`) — always enforced

Budget: `max(LOOP_MAX_USD, base_scope.budget_usd)` unless per-task overrides it.

## Failure modes

| Symptom | Log signature for grep | Where to fix |
|---|---|---|
| Session ends `completed` but `tokens_used=0, cost_usd=0` | `[devices-ws] close_task_session_failed` or no row update | Pre-PR-770: `closeTaskSession` only set status/ended_at. Fixed by writing tokens/cost from `task_complete` payload. `agentflow-agents/src/services/devices-ws.ts:705` |
| Dispatch returns `queued:true` even though device looks online | `[device] online user=... device=...` happens on a different pod than the one serving REST | Cross-pod in-memory presence race. Fixed by `drainAndDispatchQueuedTasks` on `hello`. `agentflow-agents/src/services/devices-ws.ts:415` |
| Task aborts with `cost_cap_exceeded: spent $X >= $0.5` | `cost_cap_exceeded` in `device_action_log.tool='task.cost_cap'` | `LOOP_MAX_USD` default too low. Either set per-task `scope.budget_usd` or lift the toml `budget_usd` (which is now the floor via `loop.py:1426`). |
| `shell_whitelist is empty; shell.exec disabled` | exact substring in `code_run_command` result | `~/.agentflow/computer-scope.toml` has empty `shell_whitelist`. Either widen the toml or pass scope inline in `dispatch_task`. |
| `path not in allow_paths: /foo` | exact substring in `code_write_file` result | Same — add path to `allow_paths` (toml or per-task scope). |
| Multiple terminating pods during rollout — fresh task lands on old code | Pod `STATUS=Terminating` in `kubectl get pods -l app=agentflow-agents` | Daemon WS may still be bound to terminating pod. Force daemon reconnect with `launchctl kickstart -k gui/$(id -u)/com.agentflow.desktop`. |
| `task.completion_blocked` after a tool error | `completion_blocked_after_tool_error` in session log | New completion guard. Means daemon tried `task_complete` while the last tool returned `ok:false`. Either fix the tool error or have the LLM acknowledge failure in the answer before completing. `agentflow-computer-mcp/src/agentflow_computer_mcp/driver/loop.py` |
| `finalize_device_task_failed` | console.error in agentflow-agents logs | `device_tasks` row UUID malformed or matched 0 rows (already finalised). Idempotent — usually safe to ignore. |
| Chat composer on `/cabinet/devices/:id/live` shows no reaction after Send; console has `workbox` `no-response` + `Failed to load resource: 409` | Browser console: `Uncaught (in promise) no-response`, `workbox-...js:1` | Pre-2026-05-28: `vite-plugin-pwa` registered a SW with `navigateFallback: '/index.html'` that hijacked cabinet navigations. After deploy the precache mismatched and the SW resolved navigations with `no-response`, killing every in-page fetch. Fixed by disabling VitePWA in `agentflow-landing/vite.config.ts` and shipping a one-shot SW-unregister in `agentflow-landing/src/main.tsx` (PR #532). 409 on dispatch is now surfaced by `CabinetDeviceLive.tsx::handleDispatch` with the actual error code (device_paused / device_offline / busy) instead of the generic "offline" copy. |

## Setup wizard entry point (cabinet UX)

The `/setup-device` route is a standalone linear wizard (auth → API key → install → handshake → done) that owns the cold path from anonymous visitor to a `user_devices` row with `status=online`. It does NOT mint an enrollment token — it provisions a regular API key via `POST /me/api-keys` and the daemon registers itself on first WS connect.

| Path | Role |
|---|---|
| `agentflow-landing/src/pages/SetupDeviceWizard.tsx` | 5-step wizard component |
| `agentflow-landing/src/pages/Desktop.tsx:872` | CTA "Установить и подключить устройство" |
| `agentflow-landing/src/main.tsx` (`/setup-device` Route) | Public route (no `RequireAuth` — step 0 handles login inline) |

Polling: `devicesApi.list()` every 3s for up to 5 min in step 3, baseline snapshot of existing device IDs taken at wizard mount so the handshake fires only for the new row. Telemetry: `setup_device_started`, `setup_device_step`, `setup_device_key_created`, `setup_device_connected`, `setup_device_completed`.
