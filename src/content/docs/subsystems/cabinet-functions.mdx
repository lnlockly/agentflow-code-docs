# Cabinet «Функции»

## TL;DR

`/cabinet/functions` (`CabinetFunctions.tsx`) is the catalog витрина where a
user clicks a ready-function instead of describing an agent. Three functions are
wired to real execution: «Сделать лендинг» reuses the existing projects pipeline
(`createProject` → `approveProject` → poll `getProject` for the live preview
URL), «Написать текст» calls `POST /me/functions/copy` (reuses
`autopost/generate.ts::generatePost`), «Сгенерировать картинку» calls
`POST /me/functions/image` (straight through the ai-router `IMAGE` capability).
«Видео» + «AI-Охотник» are «скоро» placeholders. The catalog lives on the
site/cabinet, never inside a pod.

## Data flow

```
cabinet /cabinet/functions (CabinetFunctions.tsx)
  │
  ├─ «Сделать лендинг»
  │    createProject(brief)             POST /me/projects     → { id, slug }
  │    approveProject(id)               POST /me/projects/:id/approve
  │    poll getProject(id) every 4s     GET  /me/projects/:id
  │      until preview_url set → render <slug>.proj.agentflow.website link
  │    (existing projects pipeline — template scorer + clone + preview-reconciler)
  │
  ├─ «Написать текст»
  │    generateFunctionCopy(brief)      POST /me/functions/copy
  │      → generatePost(brief, ownerUserId)  (useModel TEXT_LARGE)
  │      → { text }                     render + clipboard copy
  │
  └─ «Сгенерировать картинку»
       generateFunctionImage(prompt)    POST /me/functions/image
         → invokeAI(IMAGE, { prompt, cheap:true })
         → designapi cascade /v1/images/generations
         → { url | b64 }                render <img src=url | data:…>
```

## DB / Env / API

- Tables: none new. Landing function writes `projects` via the existing
  pipeline; copy + image are stateless one-shots.
- Env (agentflow-agents pod): `DESIGNAPI_BASE_URL` + `DESIGNAPI_API_KEY`
  (image), the platform LLM router env for `useModel(TEXT_LARGE)` (copy).
- Routes: `POST /me/functions/copy`, `POST /me/functions/image`
  (`requireSession`, owner-scoped). Landing reuses `POST /me/projects` +
  `POST /me/projects/:id/approve` + `GET /me/projects/:id`.
- MCP tools: none. No model strings hardcoded — copy via `useModel`, image via
  `invokeAI(ModelType.IMAGE)`.

## Failure modes

| Symptom | Log signature for grep | Where to fix |
|---|---|---|
| Image card shows `image_provider_unavailable` / 502 for every prompt | designapi returns `model_not_found ... under group rub` for all cascade models; route returns 502 `image_provider_unavailable` | designapi account/key in a group with **no image channel** (`group_no_image_access`). Enable an image channel on the designapi key, OR set a non-empty `OPENAI_API_KEY` so the BYOK-OpenAI IMAGE handler (`llm-providers/byok-openai.ts:88`) serves it. No code change. Observed 2026-05-31: `rub` group blocks images and the pod `OPENAI_API_KEY` was empty. |
| Copy card 400 | route returns 400 `generation_failed` with `autopost_empty_brief` / `autopost_empty_generation` | blank/too-short brief — caller-fixable; the textarea min-length (5) normally prevents this |
| Copy card 502 | route 502 `generation_failed` | LLM router outage or budget cap (`BudgetExceededError`) — retry / raise cap |
| Landing card stuck «Агент работает…» past ~6 min | project `status` stays `provisioning`; preview never sets | cold pod / clone slow — card hands off to the workspace («Открой проект»). See `projects.mdx` failure modes (502 from edge, npm install). |
| Landing card «Сборка не завершилась» | project `status='failed'` | build failed — open the project for the log. See `projects.mdx`. |
