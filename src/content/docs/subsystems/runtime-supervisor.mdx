# Runtime supervisor + preview-health gate

## TL;DR

Every peruser foundation project (kind ∈ {spa, mini_app, landing} with a cloned Next.js boilerplate) keeps running because four invariants hold at all times:

1. `/workspace/<slug>/.ports.env` exists with `PORT=<n>`.
2. `/workspace/<slug>/Procfile` sources `.ports.env` on every supervisor restart.
3. `/workspace/<slug>/.services/web/pid` points at the live web process — adopted from a running PID when missing.
4. `start_service` is idempotent — it returns `already_running` instead of relaunching when (a) the pidfile points at a live PID and (b) any declared port is bound.

Before 2026-05-22 these invariants drifted for legacy projects (Monar / 1292), causing EADDRINUSE relaunch loops, log spam, and preview-503s when `$PORT` expanded empty after a clean-env restart. The reconciler ticker now adopts legacy projects into the contract within ~10 minutes of agent boot.

## Strict preview-health gate (PR agentflow-agents#729, 2026-05-22)

Before flipping `projects.status='done'` the graph-executor finalize path
in `services/projects.ts:3098-3151` runs `probeAndGatePreview` from
`services/pingers/preview-health-strict.ts`. Decision tree, in order:

1. **AgentFlow placeholder title** — `<title>` contains either
   (`Запускаем` OR `Workspace warming up` OR `Coming soon`) AND `AgentFlow`,
   in either order. Catches the ingress fallback page Caddy serves when the
   per-project preview pod has no usable upstream.
2. **Caddy `Workspace ready` stub** — legacy layer, still active.
3. **Tiny body** — `< TINY_BODY_BYTES` (800) without an SPA-shell marker.
4. **SHA-256 deny-list** — `src/config/placeholder-hashes.json` hashes.
5. **Brief-token check** — when the brief produces ≥3 distinctive tokens
   after stopword + len≥4 filtering, the DOM must contain ≥1 of them
   (substring, case-insensitive). Briefs with fewer tokens skip the layer
   (no signal). Algorithm in `services/pingers/preview-placeholder.ts:extractBriefTokens`.
6. **Recent build_failed event** — `project_events` query for `build_failed`
   in the last 180 s with no `build_succeeded` / `deploy_succeeded` /
   `preview_repointed` event after it.

On any hold, the gate emits THREE events into `project_events`:
- `preview_health_failed` with full `diagnostic` JSON (check, http_status,
  body_bytes, dom_sample, brief_tokens_checked, brief_tokens_found,
  latest_build_failed_at).
- `preview_gate_blocked` for back-compat with the legacy workspace UI.
- `log` with a Russian-language reason (`strictGateReasonRu`) so the owner
  sees the failure in the timeline feed.

Status is flipped to `failed`, NOT `done`. `preview_ready_final` is NOT
emitted. `runGraphExecutorPostDoneHooks` is NOT called.

Greppable reasons (used to triage in `kubectl logs deploy/agentflow-agents | grep preview_health_failed`):
- `placeholder_served` (alias group covering `caddy_workspace_ready_title`,
  `agentflow_placeholder_title`, `placeholder_hash_match`, `tiny_body`).
- `no_brief_tokens_in_dom`.
- `build_failed_recent`.
- `http_not_200` / `unreachable` / `non_200_status`.

## Next.js runtime detection (PR agentflow-agents#730, 2026-05-22)

The default AgentFlow project stack is Next.js. Before this PR, `classify`
saw `package.json.scripts.build = "next build"`, took the generic
build-script branch, returned `type='web'` with `port=8080`, and
`writeS6Services` short-circuited — no process bound the per-project
foundation port, the Caddy preview sidecar fell back to the
`<title>Запускаем проект… · AgentFlow</title>` placeholder, and every
fresh Next.js project (#1373..#1381 on 2026-05-22) shipped broken.

Detection rule in `classify` (priority order, FIRST match wins):

1. Fullstack Node + Procfile / multi-process — unchanged.
2. `/workspace/dist/index.html` present → `type='static'`. Preserves static
   exports (`next export`, Vite production builds, etc.) — the Caddy
   sidecar serves the prebuilt artefact and no `next start` runs.
3. **NEW: `package.json.dependencies.next` OR `package.json.devDependencies.next`**
   → `type='nextjs'`, `reason='nextjs_detected'`, port =
   `computePortBase(projectId).port`. Emits a single process named `web`
   running `[ -f .ports.env ] && . ./.ports.env; exec npx next start -H 0.0.0.0 -p "${PORT:-<port>}"`.
4. Generic `package.json.scripts.build` → `type='web'` (Vite/CRA/etc.).
5. Python branches — unchanged.

`writeS6Services` allow-list now passes `nextjs` through to the
`start_service` loop (the static-skip branch at L1577 covers only
`static`/`web`/`unknown`). `pool-worker/post-build.ts` always-on bucket
includes `'nextjs'` so the boot fires without the
`RUNTIME_SUPERVISOR_ENABLED` flag.

Greppable detection signal for postmortems:
- `runtime_detect_shadow` payload contains `"reason":"nextjs_detected"`.
- `runtime_supervisor_deployed` payload `plan.type` = `"nextjs"`.
- `start_service` event with `name='web'` and `port=<computePortBase(projectId).port>`.

## Procfile-driven Next.js (PR agentflow-agents#TBD, 2026-05-22, project 1385 fix)

The `spa.ts` foundation bridge (`services/graph-executor/handlers/spa.ts:817-823`)
writes a self-contained Procfile of the form:

```
web: cd '/workspace/proj-<slug>' && [ -f .ports.env ] && . ./.ports.env; \
     export DATABASE_URL='...' && pnpm install && \
     (npx next build && npx next start -H 0.0.0.0 -p $PORT) || npx next dev ...
```

Before this fix, `classify` took the Procfile single-process branch
(line 458+), set `type='api'` because `proc.name === 'web'`, and
**also** set `buildCmd = defaultBuildFor(snap)` — a SECOND
`pnpm install && npm run build` from `/workspace` root. For foundations
that hoist the actual Next.js app into a subdir (`apps/web`) or use
pnpm workspace protocols, that root-level build failed.

The failure path:
1. `buildPipeline` runs `pnpm install && npm run build` at workspace root.
2. Exit code ≠ 0 → `buildPipeline` returns `{ ok: false, log: <tail> }`.
3. `deploy()` line 1798 emits `build_failed` event with `plan: "api"` and returns.
4. `writeS6Services` is NEVER reached → no `.services/web/` dir → no
   `start_service` call → foundation port stays unbound.
5. Caddy preview sidecar falls back to the AgentFlow placeholder.
6. Strict preview-gate (PR #729) catches the placeholder → `status='failed'`.

Detection rule (`runtime-supervisor.ts:481-517`):

```ts
const isNextProcfile =
  snap.packageJson?.hasNextDep === true &&
  /\bnext\s+(start|dev|build)\b/.test(procLine);
if (isNextProcfile) {
  return {
    type: 'nextjs',
    entrypoint: 'Procfile',
    buildCmd: [],          // ← Procfile handles install+build itself
    startCmd: proc.cmd,    // ← verbatim Procfile line
    port: declaredPort ?? computePortBase(projectId).port,
    reason: declaredPort ? `procfile_nextjs:port=${declaredPort}` : 'procfile_nextjs',
    processes,
    kindHintAgrees: null,
  };
}
```

`buildCmd=[]` makes `buildPipeline` short-circuit at line 1342 with
`no_build_required` — deploy() advances to `writeS6Services`, which calls
`start_service` with the Procfile line + `port=<foundation_port>` for the
idempotency probe.

`type='nextjs'` is already in the always-on `allowedTypes` bucket (PR #732
+ `pool-worker/post-build.ts:599-614`) so the pool-worker auto-deploy call
reaches this branch without `RUNTIME_SUPERVISOR_ENABLED=1`.

Greppable postmortem signals:
- `runtime_supervisor_started` with `source: 'always_on'` event right after `task_done`.
- `runtime_detect_shadow` payload contains `"reason":"procfile_nextjs"` (with optional `:port=N`).
- `runtime_supervisor_deployed` payload `plan.type` = `"nextjs"`, `plan.reason` starts with `procfile_nextjs`.
- `start_service` was called with `name='web'` and `port=<computePortBase(projectId).port>`.
- Inside the pod: `/workspace/proj-<slug>/.services/web/pid` exists and points at a live `next-server` process.

## deploy() observability (PR agentflow-agents#TBD, 2026-05-22)

Before this PR, `deploy()` emitted events only when it succeeded
(`runtime_supervisor_deployed`) or hit a known failure (`runtime_supervisor_failed`,
`runtime_supervisor_skipped`, `auto_start_skipped`). A project that
short-circuited at the `allowedTypes` filter, the snapshot probe, or the
escape-hatch marker left NO trace, making it impossible to tell from
`project_events` whether `deploy()` was even invoked.

Now `deploy()` emits:

1. `runtime_supervisor_started` immediately after the project-row lookup —
   payload `{ plan_type: null, source, allowed_types }`. This is the single
   breadcrumb that proves the function was entered. If it's missing,
   the issue lives upstream in graph-executor / pool-worker, NOT inside
   the supervisor.

2. `runtime_supervisor_short_circuit` on EVERY early-return path, alongside
   the existing kind-specific event. Reason strings (pinned by
   `tests/unit/runtime-supervisor-procfile-nextjs.test.ts`):

   - `no_workspace_project` — projects.workspace_project_name and slug both null.
   - `snapshot_failed` — `detectRuntime` couldn't snapshot the workspace.
   - `unknown_runtime` — snapshot succeeded but `classify` returned `type='unknown'`.
   - `not_in_allowed_types` — pool-worker's `allowedTypes` filter rejected the plan
     (normal — happens on every always-on call that classifies as static/web).
   - `no_auto_start_marker_present` — operator wrote `/workspace/.no_auto_start`
     for debugging.

Postmortem query:
```sql
SELECT created_at, kind, payload->>'reason' AS reason, payload->>'plan_type' AS plan_type
  FROM project_events
 WHERE project_id = <id>
   AND kind IN ('runtime_supervisor_started', 'runtime_supervisor_short_circuit',
                'runtime_supervisor_deployed', 'runtime_supervisor_failed',
                'build_failed', 'preview_gate_blocked')
 ORDER BY id ASC;
```

Expected happy-path sequence for a Procfile + Next.js project:
```
runtime_supervisor_started   {source: "always_on"}
runtime_supervisor_deployed  {plan.type: "nextjs", plan.reason: "procfile_nextjs..."}
```

Expected sequence when the pool-worker double-fires (always-on + flag-gated):
```
runtime_supervisor_started        {source: "always_on"}        ← nextjs accepted
runtime_supervisor_deployed       {plan.type: "nextjs"}
runtime_supervisor_started        {source: "flag_gated"}       ← nextjs rejected
runtime_supervisor_short_circuit  {reason: "not_in_allowed_types"}
runtime_supervisor_skipped        {reason: "not_in_allowed_types"}
```

## Reconcile contract

`runPeruserServicesReconcileTick` is **read-mostly** — never restarts the running web process. Its single mutation is to fill in missing platform metadata:

- `.ports.env` write guarded by `[ ! -f .ports.env ]`.
- `Procfile` rewrite guarded by `! grep -q '[ -f .ports.env ]' Procfile` (sentinel skip when bridge-generated Procfile already has it).
- PID adoption guarded by `[ ! -s .services/web/pid ]` AND `kill -0 "$CANDIDATE"` on the discovered PID.

The script emits one machine-parseable line — `RECONCILE: ports=<0|1> proc=<0|1> pid=<n|none>` — so the agent-side caller records a single structured `project_events.kind='log'` entry without re-grepping stdout.

PID discovery cascade: `lsof -t -i TCP:$PORT -sTCP:LISTEN` → `ss -lntp` (parse `pid=N`) → `/proc/net/tcp` (find LISTEN inode, follow `/proc/<pid>/fd/*` symlinks). The third path is the only one that works in a stripped Alpine-derived workspace image where neither `lsof` nor `ss` ship.

Per-project cooldown: 10 min between attempts. On first success the project lands in the `succeeded: true` slot of the in-memory state map and is skipped forever (until agent restart).

## start_service contract

```ts
{
  project: string,    // peruser slug
  name: string,       // service name (e.g. 'web')
  command: string,    // foreman-style web: line, NOT a full bash script
  cwd?: string,
  port?: number,      // optional — required for the port-bound idempotency check
  mode?: 'idempotent' | 'force', // default 'idempotent'
}
```

**Idempotency probe** runs inside the workspace pod before composing the launch script:

```sh
if [ -f .services/<name>/pid ]; then
  PID=$(cat .services/<name>/pid)
  if [ -n "$PID" ] && kill -0 "$PID" && ( ss -tln | grep ":<port>" || netstat -lnt | grep ":<port>" ); then
    echo "ALIVE:$PID"
  else
    echo "DEAD"
  fi
else
  echo "NOPID"
fi
```

Returns `{ ok: true, status: 'already_running', pid, port }` on `ALIVE:` — no kill, no relaunch. `mode: 'force'` skips the probe and always restarts; use it for code-redeploy / config-change paths.
