# Desktop Firefox driver + per-device memory

## TL;DR

Two paired additions to AgentFlow Desktop:

1. **Firefox driver** — Playwright-driven `firefox_*` tools that launch the
   user's real Firefox via `launch_persistent_context(user_data_dir=<profile>)`
   so already-authenticated sites (kwork.ru, Telegram Web, mail) work
   without re-login. Coexists with the anonymous Chromium `browser_*` tools.
2. **Device memory** — append-only `device_memories` table (kind ∈
   `observation` | `lesson` | `fact`, free-form text, tag array) exposed via
   `POST/GET /me/devices/:id/memories`. The daemon's autonomous loop
   ("Иди зарабатывай") calls `af_recall` at task start to pull lessons and
   `af_remember` at task end to record what worked.

## Data flow

```
Desktop task starts
   │  af_recall(tags=['kwork','earn'], limit=20)
   ▼
AFClient.recall(...)        GET /me/devices/<uuid>/memories?tags=kwork,earn&limit=20
   │                            ▲
   │ x-api-key: af_live_*       │
   ▼                            │
agentflow-agents :3000 ──────── │
                                │
                               postgres-js
                                │  SELECT … FROM device_memories
                                │  WHERE device_id=? AND tags && ARRAY[?,?]::text[]
                                │  ORDER BY created_at DESC LIMIT 20
                                ▼
                          device_memories rows

LLM consumes lessons → drives task (Firefox attached to real profile)
   │
   ▼
firefox_open → firefox_navigate(kwork) → firefox_eval(extract listings)
   │
   ▼
For each viable order: firefox_click(reply) → firefox_fill(offer) → firefox_click(send)
   │
   ▼  task end
af_remember(kind='lesson', tags=['kwork','offer'], text='...')
   │
   ▼
AFClient.remember(...)      POST /me/devices/<uuid>/memories
   │                            { "kind": "lesson", "text": "...", "tags": [...] }
   ▼
INSERT INTO device_memories ... RETURNING *
```

## DB / Env / API

- Tables: `device_memories` (id, user_id, device_id, kind, text, tags[], created_at)
- Indexes: `idx_device_memories_device_created` (device_id, created_at DESC), `idx_device_memories_tags` (GIN on tags)
- Env:
  - `AGENTFLOW_FIREFOX_PROFILE` — absolute path override for the profile dir (otherwise auto-discover per OS)
  - `AGENTFLOW_FIREFOX_BINARY` — non-default Firefox executable (Nightly, Developer Edition)
  - `AGENTFLOW_DEVICE_ID` — daemon-side default for `af_remember` / `af_recall` (otherwise read from `~/.agentflow/auth.json`)
- Routes:
  - `POST /me/devices/:id/memories` — `{kind, text, tags?}` → `201 {ok, memory}`
  - `GET /me/devices/:id/memories?tags=a,b&kind=lesson&limit=50` → `{ok, items[]}` (newest first)
- MCP tools (LLM-facing on the daemon):
  - `firefox_open`, `firefox_navigate`, `firefox_snapshot`, `firefox_click`, `firefox_fill`, `firefox_press`, `firefox_eval`
  - `af_remember(kind, text, tags?, device_id?)` — defaults to the enrolled device when omitted
  - `af_recall(tags?, kind?, limit?, device_id?)` — newest-first

## Failure modes

| Symptom | Log signature for grep | Where to fix |
|---|---|---|
| Daemon errors `firefox profile not found` on first `firefox_open` | `firefox profile not found` | set `AGENTFLOW_FIREFOX_PROFILE` to absolute path; `agentflow-computer-mcp/src/agentflow_computer_mcp/driver/firefox.py:103` |
| `af_remember` returns `{ok: false, error: "no device_id ..."}` | `no device_id (set in auth.json` | enroll device or set `AGENTFLOW_DEVICE_ID`; `agentflow-computer-mcp/src/agentflow_computer_mcp/driver/af_client.py:430` |
| `POST /me/devices/:id/memories` 404 with `device_not_found` | `device_not_found` | device id mismatch or device was soft-deleted; check `user_devices.deleted_at` |
| Tag filter returns nothing despite recent inserts | (no log) | tags are lowercased at write time — pass lowercase tags in `?tags=`; `agentflow-agents/src/routes/me-devices-memories.ts:108` |
| `launch_persistent_context` hangs on launch | hangs without log | another Firefox process owns the same profile; quit the user's Firefox or use a copied profile dir |

## Why Firefox via persistent context (not CDP attach)

Firefox does not support `connect_over_cdp` in Playwright — only Chromium has stable
CDP attach. `launch_persistent_context(user_data_dir=<profile>)` is the supported
equivalent: Playwright spawns a fresh Firefox process pointed at the user's profile
directory, so cookies + extensions + bookmarks are reused, while leaving the user's
own running Firefox window untouched (Firefox tolerates two processes on the same
profile as long as they don't write the same lock file concurrently; for safety the
daemon should run when the user's main Firefox is not open, or against a copied
profile).
