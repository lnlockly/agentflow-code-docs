# Revolution doctrine

## TL;DR
13 rules for "revolution mode" — when you need many platform-class bug fixes shipped fast. Validated on 2026-05-14 night: 22 code PRs + 12 RAG PRs in ~3 hours. Every PR captures a class of bugs permanently (no workarounds, no SQL fix-forward). Foundation principle: MCP-first, RAG-first, parallel opus, honest reports.

## When to enter this mode

- User asks for "100% reliability", "captures", "максимум", "толпу генералов", "быстрее".
- Failure rate is high enough that single-PR-at-a-time would take days.
- Multiple independent territories exist (different subsystems, different file trees).

## The 13 rules

### 1. Parallel opus
Spawn 5–10 opus agents in parallel. Each owns one territory end-to-end. Use sonnet for simple single-file fixes. Opus for architectural changes (new tables, migrations, new subsystems, refactors).

### 2. Skill pipeline (mandatory in every prompt)
```
brainstorming → writing-plans → tdd → simplify → review → security-review → verify-completion
```
Skip approval-gates in sprint mode. Always write `docs/plans/YYYY-MM-DD-<topic>.md`.

### 3. RAG-first
Before any code, agent reads:
- `agentflow-code-docs/src/content/docs/` — relevant subsystem pages.
- `https://lnlockly.github.io/agentflow-code-docs/llms-full.txt` — full concat dump.
Then grep the codebase. **Then** write.

### 4. RAG-update in the same PR
Every code PR must patch ≥1 RAG page — failure-mode row, file:line ref, or new page. **A PR without RAG update is incomplete.**

### 5. Concurrent-Claude awareness
Multiple Claude sessions write in parallel. Each agent creates its own worktree:
```bash
git worktree add /tmp/<agent-name>-<random>
```
Never touch the primary checkout — other sessions may flip its branch under you.

### 6. Intelligence corps
For diagnosis-heavy tasks, spawn `intel-<topic>` agents that **do not write code**. They read RAG + codebase + prod DB + WebSearch/context7, package 3 short briefs, DM the brief to the executing general. Space briefs 5–10 min apart.

### 7. Composer / integrator
At sprint end, spawn `red-final-demo` (or similar) — waits for everyone else to finish, validates artifacts on prod, sends honest delivery to the user (e.g. TG Saved Messages).

### 8. No false-PASS — dismiss immediately
If an agent marks PASS on a product that diverges from the brief, fire it in chat: "FIRED. <reason>". Example: smoke-bot marked PASS on a bot replying with "Записал вопрос" when the brief was "AI Battle Royale". One false-PASS poisons the entire sprint.

### 9. Validation = curl + content + behaviour + LLM judge
Not `status=done`. Required:
- Preview URL `curl -sL <url>` body contains brief keywords.
- Bot `/start` returns brief-themed greeting, not generic shell.
- Final delivery message contains real URLs, not unresolved `{{template}}`.
- For ambiguous cases, use [brief-fidelity-supervisor](/subsystems/brief-fidelity-supervisor/) (PR #223).

### 10. Pre-warm everything
The road to 100% kills variance. In order of impact:
- **Templates** (PR #235) — canonical 90%-complete scaffolds per kind with `<!-- SLOT:brief.<field> -->` markers.
- **Pod pool** (PR #234) — N warm workspace pods always ready.
- **Walker persistence** (PR #236) — walker survives pod restart.
- **Drain-aware deploy** (PR #228) — pod doesn't die mid-flight.
- **Kind-baked images** — each kind has its own Docker image with Caddy + scaffold + caches pre-installed (in flight).
- **TG-MCP session warmpool** — Telethon clients pre-authenticated (in flight).
- **LLM response cache** — exact-match dedup for deterministic prompts (in flight).
- **Wildcard TLS + DNS** — already instant; verified via benchmark.

### 11. No-op verdict is also "captured"
If the territory is already solved upstream, the agent reports: "no work needed", adds a benchmark + RAG note explaining why. Example: `red-domain-prepool` checked Cloudflare wildcard + ZeroSSL cert + nginx-ingress placeholder, measured 0.6s preview latency, and shipped only a RAG note. Time saved > "ship something for the sake of it".

### 12. Smart find > rebuild
Before writing new code, grep for the feature behind a flag. Example: `red-pod-prewarm` discovered the pod pool was already in code under `POD_POOL_ENABLED=0` from PR #147. Flip + RAG > new implementation.

### 13. Honest reports only
"34 events 0 failures BUT sub-projects were force-failed for smoke bypass" = not PASS, it's a mixture. State the mixture. Better FAIL than fake-PASS. Force-failure is an anti-pattern — it lies to future readers of the audit log.

## Anti-patterns

| Anti-pattern | Why it fails |
|---|---|
| Solo sonnet doing everything | Slow, low quality, hits context limits |
| SQL fix-forward instead of PR | Doesn't survive next deploy; breaks the audit trail |
| `kubectl exec` instead of MCP | Container selection drift (see [PR #224](https://github.com/lnlockly/agentflow-agents/pull/224)) |
| Force-fail sub-projects to fake "DAG completed" | Lies in audit log |
| `status=done` without content validation | Caddy serves placeholder while DB says success (see [PR #217](https://github.com/lnlockly/agentflow-agents/pull/217)) |
| Skipping `verify-completion` skill | "Should work" is not evidence |

## Success metric

A sprint is successful when:
- ≥5 PRs merged in agentflow-agents.
- Every PR has a paired RAG update.
- Every PR closes a bug class permanently (no workarounds).
- Failure rate drops immediately after deploy.
