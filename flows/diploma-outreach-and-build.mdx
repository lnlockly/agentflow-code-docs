## TL;DR

One DAG, one screenshot, the whole platform.

The owner picks `TG-outreach → AI-build (diploma)` from the templates
marketplace. The graph wakes up @avsee4 (the owner's own TG session,
account_id=4 in the [tg-mcp pool](/subsystems/tg-mcp)), DMs @MLM808 an
AgentFlow pitch, waits for a reply, classifies intent with TEXT_SMALL,
and — when the reply is "хочу визитку" or "хочу бота" — spawns a child
project of the matching kind ([`tg_profile_bundle`](/architecture/visitka-tg-profile)
or `tg_bot`) whose brief advertises @MLM808 himself. When the sub-project
flips to `status=done`, the parent DAG closes the loop by DMing the
preview URL / bot username back to @MLM808.

That's the demo: outreach (ферма primitives) + AI classification
(flow-executor primitives) + sub-project creation (`/me/projects`
internal call) + delivery (back to TG) — all in one
`workflow_schema` consumed by the
[graph executor](/architecture/graph-executor) and rendered live on
`CanvasLive` while it runs.

## Workflow DAG

```
trigger.manual
  │ (optional: trigger.cron "0 10 * * *" — daily 10:00 outreach)
  ▼
tg.get_user[account_id=4, peer=@MLM808]
  │ output: {username, first_name, bio, photo_url}
  ▼
tg.send_text[account_id=4, peer=@MLM808,
             text="<rendered pitch using {{contact.first_name}}>"]
  │ output: {message_id}
  ▼
tg.wait_reply[account_id=4, peer=@MLM808,
              since_message_id={{steps.tg.send_text.output.message_id}},
              timeout_ms=86_400_000  (24h)]
  │ output: {received, message:{id,text}, waited_ms}
  ▼
llm.classify_intent[message="{{steps.tg.wait_reply.output.message.text}}",
                    taxonomy=["visitka","bot","refuse","ambiguous"],
                    clarify_max=2,
                    clarify_send=tg.send_text(account_id=4, peer=@MLM808)]
  │ output: {intent, confidence, reasoning, clarify_rounds}
  ▼
  ├─ intent == "visitka"
  │     ▼
  │   project.create_sub[kind="tg_profile_bundle",
  │                      brief=<visitka template>,
  │                      parent_project_id={{ctx.projectId}},
  │                      seed={"detail_meta":{"tg_username":"MLM808"}}]
  │     │ output: {sub_project_id, sub_project_slug}
  │     ▼
  │   project.wait_done[project_id={{steps.project.create_sub.output.sub_project_id}},
  │                     timeout_ms=1_800_000  (30 min)]
  │     │ output: {status, preview_url, bot_username?}
  │     ▼
  │   tg.send_text[account_id=4, peer=@MLM808,
  │                text="готова твоя визитка: {{steps.project.wait_done.output.preview_url}}"]
  │     ▼
  │   tg_lead_states.update[stage="booked",
  │                         meta={"asset":"visitka",
  │                               "sub_project_id":{{...}}}]
  │
  ├─ intent == "bot"
  │     ▼
  │   project.create_sub[kind="tg_bot",
  │                      brief=<bot template>,
  │                      parent_project_id={{ctx.projectId}}]
  │     ▼
  │   project.wait_done[...]
  │     ▼
  │   tg.send_text[text="готов твой бот: @{{steps.project.wait_done.output.bot_username}}"]
  │     ▼
  │   tg_lead_states.update[stage="booked", meta={"asset":"bot"}]
  │
  └─ intent == "refuse"
        ▼
      tg_lead_states.update[stage="refused", meta={"reason":<reasoning>}]
```

Branch fan-out uses the [per-kind on-failure policy](/architecture/graph-executor#per-kind-policy)
`fail-fast` on `project.create_sub`/`project.wait_done` (no delivery if
the sub-project never lands) and `continue` on `tg_lead_states.update`
(audit-only, don't fail the demo over a stage write).

The `ambiguous` branch is **not** an edge in the DAG. Per
[graph-executor.mdx — Risks](/architecture/graph-executor#risks--open-questions)
the walker doesn't loop; the `llm.classify_intent` handler absorbs the
clarify loop internally (`clarify_max=2` config), sends the
"визитка или бота?" prompt via the injected `clarify_send` action, and
re-polls `tg.wait_reply` against the same peer. The handler returns a
terminal intent (`visitka` | `bot` | `refuse`) or `ambiguous` after the
cap — in which case the graph terminates with a `node_failed
reason='intent_unresolved'`. No DAG cycle, walker happy.

## Sub-project brief templating

`project.create_sub` renders its `brief` string from the parent
walker's `ctx.steps['tg.get_user'].output` via simple `{{contact.*}}`
substitution. No Mustache, no Jinja — plain `.replace(/\{\{contact\.(\w+)\}\}/g, ...)`.
The walker exposes `ctx.steps` read-only ([`graph-executor.mdx` line 124](/architecture/graph-executor#contract))
so the handler reads + renders deterministically.

### Visitka brief template

```
AI-визитка для пользователя @{{contact.username}}. Сделай ему mini-site:
имя ({{contact.first_name}} {{contact.last_name}}), био
({{contact.bio}}), ссылки из профиля. Внизу — большой блок
"Хочешь так же? Жми → @AgentFlow_bot". Тёмная тема, минимализм.
```

Rendered brief flows into the child `tg_profile_bundle` project's
`projects.brief` column. Its [own DAG](/architecture/kinds#dag--handler-map)
(`scrape_tg → render_landing → deploy_landing` + `scrape_tg →
scaffold_bot → wire_designapi → deploy_bot → booking_flow`) does the
real work. `detail_meta.tg_username='MLM808'` is seeded so
[ProjectCard `KindAccent`](/architecture/kinds#per-kind-ui-surface)
shows `AI-визитка @MLM808` while the build runs.

### Bot brief template

```
Telegram-бот для @{{contact.username}}. Назначение: отвечает на типовые
вопросы клиентов про услуги {{contact.first_name}}, собирает контакты,
рекламирует @{{contact.username}} как эксперта. В каждом ответе —
сноска "Сделано на AgentFlow → @AgentFlow_bot".
```

Flows into the child `tg_bot` project's brief. Its DAG
(`request_token → scaffold_aiogram → smoke_test ↔ self_heal_loop →
deploy`) builds and deploys; the parent waits on `project.wait_done`
which surfaces `projects.bot_username` once `request_token` resolves.

### Outreach pitch (parent DAG)

The `tg.send_text` node config:

```
text: "Привет, {{contact.first_name}}! Делаю эксперимент: AgentFlow —
платформа, которая собирает Telegram-ботов и AI-визитки за минуты.
Хочешь покажу — соберу тебе бесплатно? Скажи 'визитка' или 'бот'."
```

Hard-coded in the boilerplate `workflow_schema` so every demo run uses
the same copy until we A/B test variants.

### Kind decision: why `tg_farm`?

`agent_boilerplates.kind` is the discriminator used by
[`kindToPreset`](/flows/templates-marketplace) to map a template to a
`CreateProjectModal` preset. The diploma DAG isn't a `tg_bot`, isn't a
`landing`, isn't a `tg_profile_bundle` — it's an *action* that spawns
those. The closest existing slot is `tg_farm` (matches the ферма
preset's spirit: an action-kind agent running on a user TG account
that triggers downstream effects).

Caveat: [`kinds.mdx`](/architecture/kinds#per-kind-ui-surface) notes
**`tg_farm` is NOT a value in the project-kind enum** — it's used today
only for the ферма agent slug, not for project creation. Two options:

1. **Add `tg_farm` to the project-kind enum** (small migration) + add a
   tile to `CreateProjectModal`. The diploma project then shows in
   `/projects` like any other kind.
2. **Route the diploma boilerplate through the marketplace hire path**
   (`/me/marketplace/diploma-outreach-build/hire`) instead of
   `/me/projects` — reuses the existing
   [marketplace-hire flow](/flows/marketplace-hire) for required-secrets
   pre-seeding (TG_API_ID/HASH/SESSION already on `account_id=4`, so the
   `missing_required_secrets` 400 won't fire for the owner).

**Spec recommends option 2** — zero schema changes, reuses the secrets
pre-seed UX, and the template card in `/templates` can deep-link to
`/marketplace/diploma-outreach-build` instead of opening
`CreateProjectModal`. The kind on the boilerplate row stays a string
the marketplace card doesn't care about.

## Walker / per-kind policy

Add a row to the [per-kind on-failure policy](/architecture/graph-executor#per-kind-policy)
table under `tg_farm` (or whatever kind label we land on):

| Node | Policy | Rationale |
|---|---|---|
| `tg.get_user` | continue | Bio/photo are nice-to-have for templating; fall back to plain `@username` |
| `tg.send_text` (outreach) | fail-fast | If we can't DM, there's nothing else to do |
| `tg.wait_reply` | fail-fast on `timed_out=true` | 24h with no reply = lead is cold; emit `node_failed reason='no_reply_24h'` and let `tg_lead_states.update` (via secondary edge) mark stage |
| `llm.classify_intent` | fail-fast on `intent='ambiguous'` after `clarify_max` | Defensive — no infinite clarify loop |
| `project.create_sub` | fail-fast | No sub-project, no delivery — short-circuit |
| `project.wait_done` | fail-fast on `status='failed'`, fail-fast on timeout | Same |
| `tg.send_text:deliver` | continue | Delivery failure logs, doesn't undo the sub-project |
| `tg_lead_states.update` | continue | Audit-only |

   `node_started` for `tg.get_user` within 1 s — CanvasLive pulses the
   first node green.
5. **Phone check (owner):** within 2–3 s of the canvas reaching
   `tg.send_text`, @avsee4 sends a real DM to @MLM808 with the
   rendered pitch. Owner verifies on a second device.
6. **Reply on @MLM808's phone**: type `хочу визитку` and send.
7. CanvasLive: `tg.wait_reply` finishes (`received: true`), then
   `llm.classify_intent` pulses, then the `visitka` branch lights up.
8. `project.create_sub` finishes within ~10 s — a new sub-project
   appears at `/projects` (parent → see `project_events kind='sub_project_created'`).
9. The sub-project's own walker runs `tg_profile_bundle` DAG: 3–6 min
   to `status='done'` per [visitka-tg-profile](/architecture/visitka-tg-profile).
10. `project.wait_done` flips green on the parent canvas;
    `tg.send_text:deliver` pulses; @MLM808 receives a second DM with
    `готова твоя визитка: https://<slug>.preview.agentflow.website/`.
11. `tg_lead_states.update` writes a row with `stage='booked',
    meta=\{asset:'visitka', sub_project_id: N\}`. Verify in
    `agentflow-agents` pod: `psql -c "SELECT stage, meta FROM
    tg_lead_states WHERE tg_chat_peer='MLM808' ORDER BY id DESC LIMIT 1;"`.

**Target end-to-end:** 5–8 min from "Hire" click to delivered preview
URL. Screenshot the canvas mid-run for the diploma deck.

## Failure modes

| Symptom | Log signature for grep | Fix |
|---|---|---|
| Outreach silently fails (no DM lands) | `[graph-executor] node tg.send_text failed` + `tg.send_text floodwait` / `account_lock_timeout` | Per-handler retry already declared (`max:2`); on `floodwait` honour the wait seconds (handler reads `tg-mcp` error.retry_after) |
| Every `tg.*` node returns `{ok:false, error:'unknown_error'}` despite tg-mcp succeeding | `node_finished payload.ok=false payload.error='unknown_error'` while `kubectl logs deploy/agentflow-tg-mcp` shows `200 OK` for `get_full_user` / `send_message` | Handler was reading `raw.ok` on the MCP SDK `CallToolResult` wrapper (`{content,structuredContent,isError}`) instead of unwrapping. Fixed in [PR #210](https://github.com/lnlockly/agentflow-agents/pull/210) via `src/services/graph-executor/mcp-unwrap.ts` — prefer `structuredContent`, fall back to JSON-decoded `content[0].text`. If you see this regress on a new handler, route through `unwrapMcpResult(raw)` |
| 24h no reply | `[graph-executor] node tg.wait_reply timed out after Ns` + handler `timed_out:true` | Per-kind policy = fail-fast; the parent DAG's `tg_lead_states.update` secondary edge marks the lead `objection meta.outcome='no_reply'`. Owner sees the graph stopped on canvas |
| Sub-project hangs > 30 min | `[graph-executor] node project.wait_done timed out after Ns` | Walker emits `node_failed reason='timeout'`. Investigate the sub-project's own DAG via `/projects/<sub_id>` |
| Classification stuck on `ambiguous` (≥ `clarify_max`) | `llm.classify_intent: ambiguous clarify_rounds=N hit cap` (greppable substring to add in the handler) | Hard cap terminates; spec choice. Tune `clarify_max` or improve the system prompt |
| Walker doesn't render conditional branch | `[graph-executor] edge label '<intent>' did not match handler output` | Walker edge-condition matcher missing — task #13-impl prereq |
| Sub-project DAG fails (e.g. `scrape_tg` 403 on @MLM808 private bio) | parent walker sees `project.wait_done status='failed'`, emits `node_failed reason='sub_project_failed'` | Re-run by re-hiring (idempotent on `project_agents` PK) — the parent project gets a fresh walker pass |
| `tg.get_user` returns null bio | handler returns `{ bio: '' }`, template renders empty section | Acceptable. Brief template tolerates empty `{{contact.bio}}` — the visitka coder fills with a placeholder |
| Edge-condition resolver matches multiple branches | `[graph-executor] ambiguous_edge_match node=llm.classify_intent intent=visitka` | Walker enforces single-match; investigate boilerplate edge labels |
| Loop in graph (mis-edited boilerplate) | `[graph-executor] cycle_detected nodes=[…]` | The clarify retry must NOT be an edge — it lives inside `llm.classify_intent`. Re-check seeded `workflow_schema` |
| Delivery DM blocked by @MLM808's privacy | `tg.send_text: USER_PRIVACY_RESTRICTED` (or tg-mcp passthrough) | Per-kind policy = continue on `tg.send_text:deliver` — sub-project still exists, owner sees it at `/projects` |
