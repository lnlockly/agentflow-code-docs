# Create project flow

## TL;DR

Юзер шлёт бриф → `POST /me/projects` → создаётся row `status=draft` + в background стартует Maestro propose; Maestro заполняет `proposed_plan` (jsonb) → `status=awaiting_approval`. На `POST /me/projects/:id/approve` запускается approval chain: provision pod → workspace_ready → auto-scrape (если есть @handles) → auto-bot (для tg_bot/tg_profile_bundle) → scaffold (только tg_profile_bundle) → execute_in_team → pool-worker drains `plan_tasks`.

## Data flow

```
POST /me/projects { brief }                 routes/projects.ts:573
   ↓ requireSession
createProjectForUser → projects row (status=draft)
   ↓ classifyBriefKind(brief) — regex → LLM fallback
   ↓ status='proposing'  +  spawn runMaestroProposeBackground
runMaestroProposeBackground
   ↓ Maestro agent → propose_project_plan MCP tool
projects.proposed_plan = { agents, steps, auditor_slug }
   ↓ status='awaiting_approval'  +  project_events: 'plan_proposed'

User clicks Approve → POST /me/projects/:id/approve
   ↓
runProjectApprovalBackground (projects.ts:1682)
   ↓
provisionWorkspaceWithRetry (projects.ts:1301)
   ↓ kubectl apply -f <StatefulSet+Service+PVC>
   ↓ kubectl wait --for=condition=ready pod/project-<slug>-0
   ↓ project_events: 'workspace_ready'
   ↓
autoScrapeFromBrief                     — only if brief has @handles
   ↓ Jarvis Telethon → scrape into /workspace/scraped_*.json
   ↓ project_events: 'auto_scrape_done' (or 'auto_scrape_post_ws_failed')
   ↓
autoCreateTelegramBot                   — only kind ∈ {tg_bot, tg_profile_bundle}
   ↓ tries BOT_TOKEN_POOL → falls back to BotFather (if FF_AUTO_BOT_CREATE_BOTFATHER=1)
   ↓ project_events: 'bot_assigned'
   ↓ NOTE: kind=tg_farm skips this step (MTProto user account, not Bot API)
   ↓
scaffoldTgProfileBundle                 — only kind=tg_profile_bundle
   ↓ копирует template в /workspace
   ↓
runProjectExecutionBackground (projects.ts:2294)
   ↓ execute_in_team MCP tool → INSERT plans + plan_tasks rows
   ↓ project_events: 'plan_started'
   ↓
pool-worker startPoolWorker drains plan_tasks  — pool-worker/index.ts:38
```

## DB tables / env / API surface

**DB:**
- `projects` — `id, owner_user_id, kind, status, brief, proposed_plan jsonb, plan_id, workspace_project_name, bot_username, preview_url`.
- `project_events` — `{ project_id, kind: workspace_ready|plan_proposed|plan_started|bot_assigned|auto_scrape_done|…, payload jsonb, created_at }`.
- `plans` / `plan_tasks` — materialized из proposed_plan.

**Env:**
- `FF_AUTO_BOT_CREATE`, `FF_AUTO_BOT_CREATE_BOTFATHER`, `FF_AUTO_SCRAPE_ON_CREATE` — toggles.
- `JARVIS_OWNER_USER_ID=1`, `JARVIS_WORKSPACE_PROJECT_NAME=proj-71506e1l` — singleton pod для платформенных Telethon операций.
- `BOT_TOKEN_POOL` — JSON `[{token,username}]`.
- `AGENTFLOW_INTERNAL` — base URL для internal MCP routes.

**API:**
- `POST /me/projects` — create + propose.
- `POST /me/projects/:id/approve` — kick off approval chain.
- `GET /me/projects/:id` — status polling.
- `POST /internal/projects/:id/admin-approve` (`routes/internal.ts:685`) — bypass approve для платформ-админа.

## Failure modes

| Симптом | Лог-строка для grep | Где починить |
|---|---|---|
| status=draft + 0 events | `propose_project_plan_failed` | `services/projects.ts:1682` (Maestro propose chain) |
| status=approved, 0 plan_tasks | `[auto-bot] getMe network error` | `services/auto-bot.ts:299` |
| Pod не поднимается | `pod_provision_failed` или `failure_kind: node_cpu_exhausted` | `services/projects.ts:1301` (provisionWorkspaceWithRetry) |
| Auto-scrape silently skipped | `auto_scrape_post_ws_failed` | `services/projects.ts:1983` |
| Kind classify даёт `null` | `classify_unknown_kind` | `services/kind-classifier.ts:90` |
| Pool worker не подхватывает | `pool_tick_failed` или paused | `services/pool-worker/claim.ts:33` (paused gate) |

## Frontend entry: CreateProjectModal

The user-facing entry point is **not** the Studio prompt anymore. The
`/projects` dashboard mounts `CreateProjectModal`, a 5-tile kind picker
that pre-classifies the project kind on the client and POSTs
`{ brief, kind, title }` to `/me/projects` directly — the backend can skip
`classifyBriefKind` because `kind` is already set.

| File | Role |
|---|---|
| `agentflow-landing/src/pages/ProjectsDashboard.tsx:43` | Mounts the modal; "New" button toggles `createOpen`. |
| `agentflow-landing/src/components/projects/CreateProjectModal.tsx:48` | `TILES` array (5 tiles). |
| `agentflow-landing/src/components/projects/CreateProjectModal.tsx:24` | `TileDef` discriminated union (`mode: 'project' \| 'external'`). |
| `agentflow-landing/src/components/projects/CreateProjectModal.tsx:213` | `IntakeForm.handleSubmit` — per-kind brief/title shaping. |
| `agentflow-landing/src/lib/agentsApi.ts:754` | `createProject(brief, title, _, _, kind, _)` → `POST /me/projects`. |

The five tiles map to backend kinds (see [Project kinds](/architecture/kinds)
for the canonical enum):

| Tile | `mode` | Backend `kind` | Title shape |
|---|---|---|---|
| AI-визитка | `project` | `tg_profile_bundle` | `AI-визитка @<username>` |
| Telegram-бот | `project` | `tg_bot` | `<bot name>` |
| **TG-ферма** | `project` | `tg_farm` | `<campaign name>` (was `external` pre-task #11) |
| Лендинг | `project` | `landing` | first line ≤ 60 chars |
| Mini App | `project` | `mini_app` | first line ≤ 60 chars |

The TG-ферма tile flipped to `mode: 'project'` in task #11 — it now POSTs
`{kind:'tg_farm', brief, title}` to `/me/projects` and provisions a
project row backed by the cold-mailer or AI-shiller boilerplate
(brief-analyzer picks the right one via the `ферма / cold-base /
AI-shiller / воронка продаж` regex). See
[TG templates matrix](/architecture/tg-templates) for the catalogue. The
backend `autoCreateTelegramBot` step short-circuits for `kind=tg_farm`
because MTProto creds live in project secrets, not the BOT_TOKEN_POOL.

The `tg_bot` intake has **no BOT_TOKEN field** — the platform drains a
token from `BOT_TOKEN_POOL` after `workspace_ready` via
`agentflow-agents/src/services/auto-bot.ts:142`. See
[Auto-bot assign](/flows/auto-bot-assign).

### Boilerplates seeded from agent presets

A handful of `agent_boilerplates` rows do **not** ship their own
scaffolder repo — they reuse an existing agent preset from
`agentflow-agents/presets/`. When the graph executor hits a node id
covered by such a preset, the unregistered-id fallback delegates to
`coder-agent-delegate` with the preset slug. Current mapping:

| Boilerplate | Preset | Notes |
|---|---|---|
| `tg-cold-mailer` (`tg_farm`) | `sales-funnel-tg-farm.json` + `tg-account-operator.json` | MTProto outreach pipeline |
| `tg-ai-shiller` (`tg_farm`) | `tg-ai-shiller.json` + `tg-account-operator.json` | keyword monitor + LLM reply |
| `tg-subscription-gate` (`tg_bot`) | `tg-subscription-checker.json` | channel-membership gate |
| `tg-voice-transcriber` (`tg_bot`) | `tg-voice-transcriber.json` | `useModel(TRANSCRIPTION)` |

See [TG templates matrix](/architecture/tg-templates) for the full
catalogue and per-node handler mapping.

Mobile: tile grid uses `grid-template-columns: repeat(auto-fit, minmax(220px, 1fr))`
so it collapses 3 → 2 → 1 column down to 360px viewport without a media
query.

For full frontend behaviour and the `ProjectCard` kind-accent, see
[Projects frontend](/subsystems/projects-frontend).
