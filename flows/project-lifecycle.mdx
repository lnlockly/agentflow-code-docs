# Project lifecycle

## Post-refactor canonical (2026-05-28)

PR #917 collapsed the lifecycle to a single path. **Deleted:**

- `services/kind-classifier.ts` (the `regex → LLM` classifier).
- `services/projects.ts:approveProject` + `runProjectApprovalBackground`.
- The graph-executor dispatch branch inside `runProjectApprovalBackground`.

What now runs the show:

```mermaid
flowchart TD
  A[POST /me/projects<br/>{brief, kind?, templateRepoFull?}] --> B{Has templateRepoFull?}
  B -- yes --> D[triggerProjectClone]
  B -- no --> C[Template scorer<br/>builtin shortlist + AI ranker]
  C -- match --> D
  C -- no match --> X[HTTP 400<br/>project_missing_template_repo]
  D --> E[Daemon clone into<br/>/workspace/proj-&lt;slug&gt;]
  E --> F[opencode runs in pod<br/>model: openai/flow]
  F --> G[preview-reconciler<br/>per-kind cool-down]
  G -- promoted --> H[status=done]
  G -- 3 consecutive 5xx --> I[demote running]
```

Callers migrated to `triggerProjectClone`: `internal-tg`, `team-manager`, `retry-pinger`. Rows that arrive without a resolvable template return **400 `project_missing_template_repo`** instead of falling through to the old per-kind graph.

The `kind` column survives for backward-compat and per-runtime branching (e.g. preview cool-down: `nextjs=240s, spa=240s, landing=60s, tg_bot=30s`, default 180s — PR #914). Phase 3 collapses it into a 3-value `runtime_class` (`web | tg_bot | workspace`).

The healer, auto-retry chain, finalize gate, and pool-worker drain described below still apply — those weren't touched by #917.

## TL;DR

`projects.status` — финитный автомат: **draft** → **proposing** → **awaiting_approval** → **approved** → **running** → (**done** | **failed** | **cancelled**). Между running и done стоит preview-gate (placeholder hold). Healer тикает каждые 60s — нудит Maestro когда нет прогресса (>10 min quiet), стопает на 15min cooldown. Auto-retry chain (MAX_AUTO_RETRY=3, MAX_AUTO_RETRY_NO_TOOLS=2) переподнимает failed tasks; превышение → amendment dispatch (maestro escalation, bypass per-plan cap).

## Data flow / state machine

```
[draft] (createProjectForUser, projects.ts:132)
   ↓ classifyBriefKind + spawn Maestro propose
[proposing]
   ↓ propose_project_plan MCP tool fills projects.proposed_plan
[awaiting_approval]   ←—————┐
   ↓ POST /me/projects/:id/approve
[approved]
   ↓ runProjectApprovalBackground (projects.ts:1682):
   ↓   provisionWorkspaceWithRetry → workspace_ready event
   ↓   autoScrapeFromBrief (optional)
   ↓   autoCreateTelegramBot (optional)
   ↓   scaffoldTgProfileBundle (optional)
   ↓   FF_GRAPH_EXECUTOR + kind ∈ FF_GRAPH_EXECUTOR_KINDS:
   ↓     runGraphExecutorDispatch (projects.ts:2313) → walker drains workflow_schema
   ↓       (no plan_tasks; status flips done|failed directly — see /flows/graph-execution)
   ↓   ELSE (maestro freestyle path):
   ↓     runProjectExecutionBackground → execute_in_team → plan_tasks rows
[running]
   ↓ pool-worker drains plan_tasks (claim.ts:33)
   ↓   on fail → auto-retry chain (retry_depth++, up to MAX_AUTO_RETRY=3)
   ↓   exhaustion → amendment dispatch (is_amendment_dispatch=true → bypass MAX_PER_PLAN)
   ↓ all plan_tasks → done
   ↓ post-build: finalizePreviewOnDone (post-build.ts:325)
   ↓   preview-gate.checkPreviewGate
   ↓     pass → flip to [done] + event 'project_finalized'
   ↓     fail → event 'preview_gate_blocked' → status stays [running]
   ↓ healer ticks every 60s:
   ↓   no progress > 15min → emit 'stuck_project_detected' warn
   ↓   quiet > 10min → nudge Maestro (cooldown 15min)
   ↓ all retries exhausted + no progress → [failed]
   ↓ user POST /me/projects/:id/stop → bulk cancel pending tasks → [cancelled]

[done] / [failed] / [cancelled] — terminal
   ↓ may be re-approved? — no. user creates new project, может re-propose существующий
       (mutates proposed_plan, обратно на [awaiting_approval]) — см. цикл вверху.
```

## DB tables / env / API surface

**DB tables (lifecycle-anchor):**
- `projects.status` ∈ \{`draft`, `proposing`, `awaiting_approval`, `approved`, `running`, `done`, `failed`, `cancelled`\}.
- `projects.paused_until` — при превышении hourly token budget (pool-worker skip).
- `plan_tasks.status` ∈ \{`pending`, `in_progress`, `done`, `failed`, `cancelled`\}.
- `plan_tasks.retry_depth`, `parent_task_id`, `is_amendment_dispatch`, `depends_on int[]`.
- `project_events` — append-only timeline.

**Env (lifecycle tunables):**
- `POOL_MAX_CONCURRENT=4`, `FF_MAX_TASKS_PER_PLAN=4` (legacy `POOL_MAX_PER_PLAN`).
- `MAX_AUTO_RETRY=3`, `MAX_AUTO_RETRY_NO_TOOLS=2` (constants.ts:44, :52).
- `HEALER_QUIET_MIN=10`, `HEALER_COOLDOWN_MIN=15`, `HEALER_PROGRESS_STALE_MIN=15`.
- `PREVIEW_GATE_STRICT=true`.
- `FF_SELF_HEAL_LOOP`.

**API:**
- `POST /me/projects` / `:id/approve` / `:id/stop` / `:id/re-propose`.
- `GET /me/projects/:id` — status polling.

## Failure modes

| Симптом | Лог-строка для grep | Где починить |
|---|---|---|
| Проект застрял в running | `stuck_project_detected` | `services/pingers/healer.ts:44` |
| Все retry depth исчерпаны | `auto_retry_cap_reached` | `pool-worker/constants.ts:44` (MAX_AUTO_RETRY) |
| Plan_task в in_progress навсегда (pod крэш) | `claimed_at_aged_out` | `pool-worker/claim.ts` (или сweep) |
| Project paused_until не очищается | `rate_limit_paused` | `services/rate-limit.ts` (auto-pinger) |
| Healer не нудит | `healer_cooldown_active` | `services/pingers/healer.ts:30` (HEALER_COOLDOWN_MIN) |
| preview-gate вечно blocked | `preview_gate_blocked` | `pool-worker/preview-gate.ts:211` |
| Cancel race с in_progress task | `owner_stop_race` | `pool-worker/claim.ts:88` (cancelled filter) |
| approval-retry tick failed (bad SQL, every 60s; fixed) | `column pt.project_id does not exist` | `services/pingers/approval-retry.ts:83` — correlate `pt.plan_id = p.plan_id` (plans has no project_id; project→plan via projects.plan_id) |
