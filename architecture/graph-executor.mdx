Implementation differences vs the original contract (below):

- `DEFAULT_RETRY_POLICY = { max: 1, backoffMs: 3000, idempotent: false }`
  (the spec said `max: 0`). One retry by default catches transient flakes
  without doubling the cost ceiling.
- `NodeHandler.inputSchema` / `outputSchema` typed as
  `ZodType<T, ZodTypeDef, unknown>` so handler schemas can use `.default()`
  + `.optional()` on inputs without breaking handler bodies.
- Walker accepts a `buildCtx` factory (production = `defaultBuildExecCtx`,
  tests = stub). Keeps `walker.ts` DB-free so it can be unit-tested.
- Resume path (`resumeSteps: Record<id, { output }>`) decrements
  in-degree on every child of a pre-seeded node so the next frontier
  picks them up. Greppable: `[graph-executor] idempotent_skip node_id=…`.

Failure-mode log strings live in `walker.ts` — see Failure modes below.

## TL;DR

Today maestro proposes a plan, then spawns coder agents that freestyle inside
the workspace until they decide they're done. `agent_boilerplates.workflow_schema`
([`db/schema.ts:1369`](https://github.com/lnlockly/agentflow-agents/blob/main/src/db/schema.ts#L1369))
is a visual hint, not a runtime contract — symptoms are visitka projects
that write `bot_token.txt` but no landing, `tg_bot` projects that ship with
`bot_username=null` (see [bot-pool previous bug](/architecture/bot-pool#previous-bug-pre-194)),
and ферма presets that never enable their poller.

The graph executor turns `workflow_schema` into the execution backbone. The
walker pulls a DAG, runs each node through a typed handler from a registry,
and emits `node_started` / `node_finished` / `node_failed` / `edge_flowing`
events into `project_events` + the `pipeline_runs` view. Deterministic work
(scrape, scaffold, deploy, run migration, write file, expose Caddy route)
lands in code; only nodes that genuinely need generative output (HTML copy,
section text, voice script) call into `coder-agent-delegate`, which is the
fallback handler. Same backbone for `landing`, `tg_bot`, `tg_profile_bundle`,
`mini_app`, `spa`, and ферма runtime ticks — the kind only changes which
handlers register and which per-kind error policy applies.

## Contract

```ts
// src/services/graph-executor/types.ts (new)

import type { ZodType } from 'zod';
import type { ModelType } from '../ai-router/types.js';

/**
 * The minimum a node handler must declare. `kind` matches either:
 *   - `agent_boilerplates.workflow_schema.nodes[].id` (e.g. 'scrape_tg',
 *     'render_landing', 'deploy_caddy') for build-time graphs, OR
 *   - a reserved namespace ('trigger.*', 'output.*', 'tg.*', 'agent.*')
 *     for runtime graphs reused from flow-executor.ts.
 *
 * One registry, two graph sources (workflow_schema + flows.graph).
 */
export interface NodeHandler<I = unknown, O = unknown> {
  kind: string;
  inputSchema: ZodType<I>;
  outputSchema: ZodType<O>;
  /** Pure-ish: every side-effect goes through `ctx.*` so the walker can
   *  observe (and the test harness can stub) every external touch. */
  run(ctx: ExecCtx, input: I): Promise<O>;
  /** Default: { max: 0, backoffMs: 0, idempotent: false }. Handlers that
   *  declare `idempotent: true` are re-runnable on resume; the walker WILL
   *  call them again after `node_failed` if max > 0. */
  retryPolicy?: { max: number; backoffMs: number; idempotent: boolean };
  /** Walker enforces a hard timeout via AbortSignal. Default 120s. */
  timeoutSec?: number;
}

/**
 * Everything a handler legitimately needs. The walker constructs this once
 * per `run()` call; handlers MUST NOT reach around it (no direct
 * `process.env.BOT_TOKEN_POOL`, no naked `callCodeExecTool` import) — that
 * way the walker stays the single audit point for env / pod / LLM access.
 */
export interface ExecCtx {
  projectId: number;
  ownerUserId: number;
  /** `projects.kind` — e.g. `tg_bot`, `tg_farm`, `landing`, `mini_app`,
   *  `tg_profile_bundle`, `spa`. Null only on rows where kind is unset.
   *  Handlers shared across multiple boilerplates (e.g. `link_account`
   *  between cold-mailer and ai-shiller) branch on this via `PROJECT_KIND`
   *  hints in the coder brief — never via `if (slug === ...)`. */
  kind: string | null;
  /** `proj-<slug>` — sanitised per
   *  [`projects-pipeline.ts:478`](https://github.com/lnlockly/agentflow-agents/blob/main/src/services/projects-pipeline.ts#L478). */
  workspaceProjectName: string;
  /** Resolved by `loadTenantKubeconfig` once at walk start; passed to
   *  code-exec callers so handlers never re-resolve. */
  kubeconfigYaml: string;
  /** Pre-bound to `{ownerUserId, project: workspaceProjectName}`; same
   *  surface as today's `callCodeExecTool`. */
  codeExec: <T = unknown>(tool: string, args: Record<string, unknown>) => Promise<T>;
  /** Emits an event to `project_events` AND projectBus AND the pipeline_runs
   *  steps[] stream. Walker fills `node_id`, `kind`, `step_id`; handler only
   *  supplies the payload. */
  emit(kind: NodeEventKind, payload: unknown): Promise<void>;
  /** Routes through `ai-router/instrumented.invokeAI`. NEVER hardcode model id. */
  llm: (modelType: ModelType, messages: LlmMessages, opts?: { system?: string; max_tokens?: number; temperature?: number }) => Promise<LlmResult>;
  /** Output of every previously-run node, keyed by node id. Read-only.
   *  Handlers template via `ctx.steps['<id>'].output.foo`. */
  readonly steps: Readonly<Record<string, { output: unknown }>>;
  /** AbortSignal from the walker's per-node timeout. */
  signal: AbortSignal;
  /** RAG breadcrumb. Set when this run was resumed from a previous failure. */
  resumeOf?: number;
}

export type NodeEventKind =
  | 'node_started'
  | 'node_finished'
  | 'node_failed'
  | 'node_waiting' // emitted by long-poll handlers (e.g. tg.wait_reply) before they block
  | 'edge_flowing';

export interface NodeEvent {
  kind: NodeEventKind;
  nodeId: string;
  nodeKind: string;
  payload: unknown;
  ts: string;       // ISO
  durationMs?: number;
  error?: string;
}

export interface GraphWalker {
  /** Single pass over the DAG. Returns an async iterable of events so the
   *  caller can `for await` and stream to SSE (`/me/pipelines/:id/events`)
   *  without buffering. Walker terminates after the last node fires its
   *  terminal event; long-running ферма triggers are kicked by the poller
   *  loop in `agent-trigger-worker.ts`, not by an in-process loop here. */
  run(input: {
    projectId: number;
    workflowSchema: WorkflowSchema;       // shape mirrors agent_boilerplates.workflow_schema
    ctxOverrides?: Partial<ExecCtx>;
  }): AsyncIterable<NodeEvent>;
}

export interface WorkflowSchema {
  nodes: Array<{ id: string; label?: string; icon?: string; config?: Record<string, unknown> }>;
  edges: Array<{ from: string; to: string; label?: string }>;
}
```

const registry = new Map<string, NodeHandler<any, any>>();

export function registerHandler<I, O>(h: NodeHandler<I, O>): void {
  if (registry.has(h.kind)) throw new Error(`duplicate_handler:${h.kind}`);
  registry.set(h.kind, h);

export function resolveHandler(kind: string): NodeHandler<any, any> {
  return registry.get(kind) ?? coderAgentDelegate;
}

## Execution semantics

- **Topo order** — Kahn sort, identical to
  [`flow-executor.topoSort`](https://github.com/lnlockly/agentflow-agents/blob/main/src/services/flow-executor.ts#L59).
  Cycles → walker emits one `node_failed` with `reason: 'cycle_detected'`
  for the whole graph (no partial run).
- **Parallel where possible** — every node with `in_edges = 0` starts
  concurrently; downstream nodes wait on `Promise.all` of upstream
  outputs. The walker uses a per-node `Promise` map, no `await` in the
  topo loop body.
- **Retry policy** — per-handler. Default `max: 0`. Idempotent handlers
  (every `build.*`, `auto-bot`, `runtime-supervisor.deploy`) declare
  `{max: 2, backoffMs: 5_000, idempotent: true}`. Generative handlers
  (coder-agent-delegate) declare `{max: 1, idempotent: false}` because
  reruns produce new copy.
- **Per-node timeout** — walker creates one `AbortController` per node,
  fires `AbortError` after `handler.timeoutSec ?? 120` seconds. Handler
  must forward `ctx.signal` into `fetch` / `callCodeExecTool` — the
  walker checks `signal.aborted` between awaits and surfaces a
  `node_failed` with `reason: 'timeout'`.
- **Idempotency contract** — handler authors are on the hook. The walker
  re-runs failed nodes on resume; if the handler isn't idempotent and
  fails halfway, the project lands in an inconsistent state. Failure
  mode signature: `[graph-executor] node <id> non-idempotent retry`
  (logged when `retryPolicy.max > 0 && !idempotent`).
- **`node_failed` policy** — walker decides per-kind (see table below).
  `fail-fast` aborts the whole walk; `continue` records the failure and
  proceeds with the children that don't depend on this node's output.

## Templating (`{{...}}` substitution)

Since `2026-05-14` (PR `feat/diploma-preemptive-parallel`) the walker runs
[`substituteTemplates`](https://github.com/lnlockly/agentflow-agents/blob/main/src/services/graph-executor/templates.ts)
on every node's `config` before `handler.inputSchema.parse`. This lets a
boilerplate `workflow_schema` wire downstream nodes to upstream outputs
without per-handler glue.

| Token | Resolves to |
|---|---|
| `{{ctx.projectId}}` | parent walker's project id (number) |
| `{{ctx.ownerUserId}}` | tenant id (number) |
| `{{ctx.workspaceProjectName}}` | `proj-<slug>` (string) |
| `{{steps["<node_id>"].output.<path>}}` | output of a finished upstream node — `<path>` is dot-separated. Quoted form supports IDs that contain dots or colons (`project.create_sub:visitka`). |
| `{{steps.<id>.output.<path>}}` | dot form for simple IDs without dots/colons. |

Type preservation: when the entire config field equals a single token
(`"{{ctx.projectId}}"`), the raw value is returned, so a `z.number()`
schema receives the unwrapped number. When the token is embedded inside
a longer string (`"project={{ctx.projectId}}"`), the result is a string
with JSON-stringified replacement for non-strings.

Unknown tokens are left untouched — zod will surface a real validation
error pointing at the offending field. Walker template module is dumb:
no conditionals, no arithmetic, no loops. For intent-conditional
delivery the diploma flow uses `tg.send_text.text_by_intent` instead of
a templating extension — see
[diploma flow § v2](/flows/diploma-outreach-and-build).

File ref: `agentflow-agents/src/services/graph-executor/templates.ts`.
Walker call site: `agentflow-agents/src/services/graph-executor/walker.ts:313`.

## Per-kind policy

| Kind | On node failure | Coder fallback | Notes |
|---|---|---|---|
| `landing` | fail-fast on `deploy_caddy`, continue on `seo_optimize` | yes on `pick_theme` / `generate_sections` / `seo_optimize` | `deploy_caddy` failure means no public URL; SEO can be retried by an owner-message |
| `tg_bot` | fail-fast on `request_token` + `deploy`, continue on `smoke_test` | yes on `scaffold_aiogram` / `self_heal_loop` | smoke test failure → walker fires `coder-tg-bot` brief to auto-fix; matches today's auto-tester ladder |
| `tg_profile_bundle` | fail-fast on `scrape_tg` + `deploy_landing` + `deploy_bot` | yes on `render_landing` / `wire_designapi` / `booking_flow` | scrape failure = no source data, render is impossible |
| `spa` | fail-fast on `scaffold_nest` + `deploy`, continue on `admin_panel` + `multi_tenant` | yes on every `scaffold_*` + `admin_panel` | tenants ship without an admin panel rather than not at all |
| `mini_app` | fail-fast on `scaffold_vite` + `deploy` | yes on `tg_webapp_init` + `routes` | manifest-light kind, mostly coder fallback |
| `code_only` / `api` | fail-fast on `deploy` only | yes on everything else | research kinds are 1-2 nodes; fail-fast is overkill |
| ферма (`agent_triggers.tg.new_message`) | continue on every lead-stage failure | n/a (no build-time graph) | walker runs once per poll tick from [`agent-trigger-worker.ts:318`](https://github.com/lnlockly/agentflow-agents/blob/main/src/services/agent-trigger-worker.ts#L318); a single lead failing doesn't abort the others |

`continue-on-error` writes a `node_failed` event but lets the topo walk
keep dispatching downstream nodes that don't transitively depend on the
failed node's output. The walker computes the dependency closure at start
time so the rule is deterministic.

## What blocks unconditional rollout

1. **Handler coverage** — every node id in every shipped
   `agent_boilerplates.workflow_schema` row needs a registry entry OR a
   verified coder-agent-delegate brief. Task #8 enumerates 26 node ids
   across the 5 seeded boilerplates ([`seed-boilerplate-workflows.ts`](https://github.com/lnlockly/agentflow-agents/blob/main/src/scripts/seed-boilerplate-workflows.ts)).
2. **Coder brief contract** — `coder-tg-bot`, `coder-landing`, `coder-spa`
   prompts must accept a `{node_id, output_expected: string[]}` envelope
   and reply with a `FILES_WRITTEN: [...]` block. Today they freestyle;
   change is ~30 lines per prompt.
3. **CanvasLive event shape** — already compatible (PR
   `lnlockly/agentflow-landing#149`). Verified above.
4. **Coder timeout discipline** — walker enforces `timeoutSec` via
   AbortSignal. Today coder-agent runs unbounded; we add a brief-side
   "If you can't complete in N minutes, reply with `partial: true`"
   sentinel. The walker treats `partial: true` as `node_failed` with
   `reason: 'coder_partial'` so the per-kind policy decides retry.

## Migration path

1. **Phase 1** — walker built, `FF_GRAPH_EXECUTOR=0`. PR lands but does
   nothing in prod. Unit tests exercise the registry, topo, retry,
   per-kind policy.
2. **Phase 2** — `FF_GRAPH_EXECUTOR=landing`. Easiest kind; only four
   nodes, only one is generative. Monitor for 1 week:
   `project_events.kind='node_failed'` per project ÷ approve count.
3. **Phase 3** — `FF_GRAPH_EXECUTOR=landing,tg_bot`. `tg_bot` exercises
   the `request_token` (auto-bot) handler — this is the path that fixed
   the [pre-#194 perpetual-lease bug](/architecture/bot-pool#previous-bug-pre-194)
   and the walker should keep it deterministic.
4. **Phase 4** — add `tg_profile_bundle` (visitka). Most-failing kind
   today; expect the walker to surface clearer failure signatures.
5. **Phase 5** — ферма (`trigger.tg.new_message`). The walker runs once
   per poll tick, terminates, lets the
   [`agent-trigger-worker.ts:318`](https://github.com/lnlockly/agentflow-agents/blob/main/src/services/agent-trigger-worker.ts#L318)
   loop schedule the next tick. No continuously-running walker process.
6. **Phase 6** — remove maestro freestyle for kinds with graphs. Maestro
   stays for `code_only` / `research` (no DAG).

## Walker persistence (pod-restart resume)

Since `2026-05-14` (PR `feat(graph-executor): persistent walker state survives pod restarts`)
the walker survives pod restarts via a single-row-per-project state table
plus a 30s pinger that reclaims stale walkers atomically.

```
┌─────────────────────────────────────────────────────────────────────┐
│ walker.ts (in-memory)             │ walker-persistence.ts (DB)     │
├───────────────────────────────────┼────────────────────────────────┤
│ executeNode(node) {                │                                │
│   pushEvent('node_started');       │ ── upsertWalkerStep(           │
│                                    │      project_id, current_step, │
│                                    │      'running', payload)       │
│   setInterval(10s) ──────────────► │ ── heartbeatWalker(project_id) │
│                                    │      UPDATE last_heartbeat     │
│   await handler.run(ctx);          │                                │
│   stopHeartbeat();                 │                                │
│   pushEvent('node_finished');      │   (next executeNode upserts    │
│ }                                  │    the next current_step_id)   │
│                                    │                                │
│ // walk complete OR cycle          │                                │
│ if (persistState)                  │ ── clearWalkerState(project_id)│
│   await clearWalkerState();        │      DELETE FROM walker_state  │
└───────────────────────────────────┴────────────────────────────────┘
                                            │
                                            ▼
                            graph_executor_walker_state row
                            persists across pod restart
                                            │
                                            ▼
┌─────────────────────────────────────────────────────────────────────┐
│ pingers/walker-stale.ts (30s tick, 60s threshold)                   │
├─────────────────────────────────────────────────────────────────────┤
│ rows = selectStaleWalkers(60s, 5)                                   │
│ for row in rows:                                                    │
│   claim = claimStaleWalker(project_id, row.last_heartbeat)          │
│     // atomic: UPDATE … WHERE last_heartbeat = $seenAt RETURNING    │
│     // (loses the race → another pod already grabbed it)            │
│   resumeSteps = loadCompletedSteps(project_id)                      │
│     // SELECT payload FROM project_events WHERE kind='node_finished'│
│   runGraphExecutorDispatch(…, { resumeSteps, resumeAttempt }) ──────┤
└─────────────────────────────────────────────────────────────────────┘
                                            │
                                            ▼
                       walker resumes from current_step,
                       skips completed nodes via in-degree decrement
                       (`[graph-executor] idempotent_skip node_id=…`)
```

### Schema

```sql
CREATE TABLE graph_executor_walker_state (
  project_id              integer PRIMARY KEY REFERENCES projects(id) ON DELETE CASCADE,
  current_step_id         text NOT NULL,
  step_status             text NOT NULL,          -- 'running' | 'waiting'
  workspace_project_name  text NOT NULL,
  started_at              timestamptz NOT NULL DEFAULT now(),
  last_heartbeat          timestamptz NOT NULL DEFAULT now(),
  attempt                 integer NOT NULL DEFAULT 1,
  payload                 jsonb
);
CREATE INDEX idx_walker_state_heartbeat
  ON graph_executor_walker_state (last_heartbeat);
```

One row per project. Only the *current* step is stored; completed steps are
re-derived from `project_events.kind='node_finished'` so the table never grows.

### Key knobs

| Knob | Value | File |
|---|---|---|
| Heartbeat cadence | 10s | `walker.ts` (`HEARTBEAT_INTERVAL_MS`) |
| Stale threshold | 60s | `walker-stale.ts` (`WALKER_STALE_THRESHOLD_SEC`) |
| Pinger tick | 30s | `walker-stale.ts` (`WALKER_STALE_TICK_MS`) |
| Resume cap per tick | 5 projects | `walker-stale.ts` (`WALKER_STALE_MAX_PER_TICK`) |
| Persistence default | OFF in `runWalker`, ON in `runGraphExecutor` | `walker.ts` (`persistWalkerState`) |

Tests stay DB-free because they call `runWalker` directly (default OFF);
production callers go through `runGraphExecutor` which forces ON.

### Resume semantics

- `runGraphExecutorDispatch` emits `graph_executor_resumed` (with
  `resume_attempt`, `resume_step_count`) when invoked with `resumeSteps`,
  else `graph_executor_started` — greppable for ops.
- `attempt` column increments each time the pinger reclaims the row, so
  `walker_state.attempt > 1` is the canonical "this walk has restarted N times"
  signal for ops dashboards.
- All persistence calls are best-effort: `try/catch` with
  `[walker-persist] …` warn logs. A DB blip never aborts the in-memory walk.
- Atomic claim (`UPDATE … WHERE last_heartbeat = $seenAt RETURNING`) guards
  against two pods double-resuming the same project.

## Risks & open questions

| Risk | Mitigation / open |
|---|---|
| Coder-agent doesn't know which path to write its output to | Brief envelope declares `output_expected: ['/workspace/.runtime/theme.json']`. Handler reads the file after the coder reply and validates against `outputSchema`. A reply without the file → `node_failed`. |
| Sub-graphs (a node whose handler runs its own DAG) | Deferred. The walker is a single-level executor; recursion needs an explicit `kind: 'subgraph'` node + bounded depth. Revisit when a real use-case lands. |
| ферма long-running poll | Walker runs once per tick. Poll loop owns scheduling. We do NOT spawn a long-lived walker per project. |
| LLM cost from coder fallback | Each coder-agent-delegate call charges through `agent-invoke` (existing budget gates). Walker's per-node `retryPolicy.max` caps repeat charges. |
| `pipeline_runs` view drift | Adding a `node_events` LATERAL source is an open question for task #7. For Phase 1-2 we map `node_*` events to synthetic `plan_tasks` rows so the view shape stays unchanged. |
| Handler accidentally reads `process.env.BOT_TOKEN_POOL` directly | Lint rule (banned import) + code review. `ExecCtx` does not expose raw env; pool reads stay inside the `request_token` handler that wraps `autoCreateTelegramBot`. |
| What happens to `projects.proposed_plan` | Walker ignores it. `workflow_schema` is the contract; proposed_plan stays for backward-compat with maestro freestyle until Phase 6. |

## Foundation rebrand (kind=spa, github_repo mode)

When a SPA project clones a GitHub foundation (`projects.foundationMode='github_repo'`), the `admin_panel` handler in `src/services/graph-executor/handlers/spa.ts:519` runs a brand rewrite pass before the Procfile + build step. The pass lives in `src/services/foundation-rebrand.ts`.

### Why

Cloning `mickasmt/next-saas-stripe-starter` or `lnlockly/golden-connect-template` leaves the rendered landing page hardcoded with the template's brand strings — `<title>SaaS Starter</title>`, `name: "Golden Connect"`. The user briefs "Cookora — рецепты из холодильника" and lands on a 200-OK page that still says "SaaS Starter". Observed on projects 1293, 1327, 1361 (2026-05-22).

### Surface

| File | Replacement |
|---|---|
| `config/site.ts` / `src/config/site.ts` | `name: "SaaS Starter"` → brief-derived name; `description:` rewritten when template-shaped |
| `package.json` | `name` slugified from brief; `description` rewritten when template-shaped |
| `README.md` | First `# <template-name>` heading → `# <brief-name>` + one-line tagline |
| `app/layout.tsx` / `src/app/layout.tsx` | Probed but not rewritten (Next.js renders title from `metadata` exported elsewhere) |

The rebrand derives `{site_name, site_description, hero_title, hero_subtitle}` from the brief via one `useModel(ModelType.TEXT_LARGE)` call, parses STRICT JSON, falls back to `SAFE_DEFAULTS` on parse failure. Banned words (`free`, `бесплатно`, `platform`, `protocol`, etc.) are stripped post-LLM.

### Idempotency

The rebrand writes `.runtime/.rebrand_applied` on success. Subsequent admin_panel passes (e.g. graph-executor resume after pod restart) detect the marker and skip the LLM call entirely. To force a re-rebrand: delete the marker.

### Production Procfile speedup

Same handler upgrades the Procfile `web:` line from `npx next dev` → `npx next build && npx next start` (with fallback to dev on build failure). First paint drops from 40-60s (dev compile-on-demand) to sub-second. Owner sees their preview once; no HMR needed.
